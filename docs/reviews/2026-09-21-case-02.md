# 真实案例 CASE-02 复盘

## 范围与证据边界

本记录来自一次 dev Skill 0.5.5 的真实 Android 小需求报告。需求输入由一句文档和 Figma 视觉稿组成，修改跨两个模块，最终编译、结构检查、交付核对和真机视觉验收均由执行方报告通过。原始业务仓库、需求号、提交号、Figma 节点和图片不进入本公开仓库。

维护者未独立重跑业务构建、真机和 Figma 导出；因此本页记录执行方的实际反馈和可由 Skill 源码复核的流程摩擦，不把产品结果当成维护者独立验证。

## 已观察到的价值

- 在写代码前发现了设计只覆盖一种会话场景，需要确认另一场景的行为。
- 发现了图片是跨界面共享资源，避免只更换一处。
- 保留了产品名称与代码资源名不一致的映射，降低后续误判。
- 在入库前实测了透明资产，拦下了带不透明背景的导出物。
- 通过逐张核对排除了不属于目标状态的合成按钮变体。

这些证据支持“多来源对齐、共享资源影响核对、素材入库前验证”在实际小需求中有价值。本案例没有出现构建通过但产品行为错误的情况。

## 时间与使用成本

- PRD 分析约 2 分 41 秒，其中模块调查约 1 分 14 秒。
- Figma 对齐约 11 分 39 秒，是可量化阶段中最长的一段。
- 开发和首轮素材阻塞判定约 4 分 50 秒；一个模块级编译约 1 分 41 秒。
- 资产处理、完整构建、收口和真机验收未完整计时，不用已知片段推算总耗时。
- 共有三次业务澄清和一次概念解释。来源、intake、requirements 和 decisions 在澄清及收口时反复同步，是本次主要记录成本。

## 对 0.5.5 的判定

### 确定性契约问题

1. `spec/prd-intake.json` 的来源 `kind` 只允许 `document` 和 `html`，不能自然表达 Figma/设计来源。这与 Skill 已支持 `figma` 动作的用户模型不一致。
2. 注册新来源后，intake `sources` 与 `feature.prd_paths` 必须手工双向同步。校验能发现不一致，但没有单一的登记操作来避免重复填写。

### 流程采用缺口

1. 报告中“每条需求需要 task”、“approved decision 需要 chosen”、“mapped intake 需要 aspects”都已由 develop 阶段校验，却到收口才集中补齐。这说明新增 Figma 来源和第二条需求后，Agent 没有及时重跑 develop 边界校验。
2. 本次没有使用 0.5.4 的 `module_context` 计划，跨模块定位依赖手工搜索。因此该案例不能证明模块档案会节省时间或减少遗漏。
3. 整个开发期间一直出现 `impact checklist missing` 警告，但 Agent 边调查边改代码，未在首次业务修改前建立清单。现有机制只在 `impact_required=true` 后才强制执行，新能力可被 Agent 未采用而绕过。

### 项目特定摩擦

某库模块的预期 Gradle 任务名不存在。这不是通用 Skill schema 缺陷，但说明候选门禁应从当前项目的真实任务中确认，不能仅根据 Android 命名规律推测。

## 后续决定依据

- 优先修正“新功能可以不采用影响清单”的绕过路径，并把“每次来源/需求/决策含义改变后重跑 develop 校验”放到执行顺序。
- 设计来源类型和来源路径双写是可重现的契约摩擦，可作为下一个小版本的独立修正。
- “一句话 + Figma”轻量 intake 属于产品取舍。本次确认了重复填写，但尚未分离哪些字段能安全自动生成，暂不直接删减证据链。
- 下一个真实局部修改应显式启用 `module_context` 和 impact checklist，分别记录阅读范围、过期档案、影响补充、误阻塞和耗时，才能评价 0.5.4/0.5.5 的新机制。
