# Android 静态模块候选：真实项目只读核对（2026-09-24）

本次只评估 0.5.19 已安装 Skill 中的 0.5.16 静态 Gradle 候选发现能力，不运行 Gradle，也不发布或更新业务项目的 scan 基线。将项目根 settings 与 49 份 build.gradle(.kts) 复制到 `/private/tmp` 隔离目录，调用现有 `discover_gradle_candidates`；候选只写在隔离目录。业务项目执行前后的 Git 状态一致，原有未提交文件未触碰。

## 判断与边界

主 settings 通过 `apply(from = ...)` 加载外部脚本，而发现器只解析根 settings 的字面 `include`。现有 `gaps` 会提示 `includeBuild`，但不会提示这个被加载的 settings 脚本，因此不能仅凭“30 个模块、19 个缺口”判断调查范围完整。直接扫描外部脚本的字面 `include` 也不够：本例使用列表迭代并设置 `projectDir`，还包含 React Native 自动链接；静态工具不能把它们自动提升为已确认模块。

本次未执行 Gradle 项目枚举。项目 settings 存在依赖自愈逻辑，运行 Gradle 可能触发下载或清理缓存，不属于只读测量。没有对真实运行时模块全集、自动链接结果、业务归属和端到端扫描总耗时作结论。

## 下一步

优先做小修正：静态发现器遇到 `apply(from=...)` 或等价外部 settings 加载时，至少输出路径与行号的人工复核缺口；对未识别的 `add(..., project(...))` 依赖表达式也应提示，而不是静默遗漏。合成测试覆盖这两种语法，再用本次隔离副本复核提示是否出现。是否进一步解析动态列表与项目目录映射，应在测量误报和维护成本后决定；不得把候选直接写入正式模块目录。
