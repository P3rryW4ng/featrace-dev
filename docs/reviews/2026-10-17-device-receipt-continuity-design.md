# 设备回执适用性延续：最小设计评审

日期：2026-10-17。**候选设计，未批准实现或改变任何现行回执。** 关联既有GAP-26（无关改动重复验收）、GAP-33（设备执行与日常门禁），同时触及GAP-32的复用摩擦，不另建重复编号。0.15.1已安装但没有本能力；B1只处理自动检查身份，不能代替本方案。

最新收敛见[待批准最小批次](2026-10-17-device-receipt-minimum-batch.md)：明确同文件无关增量需审查、旧认证命令拒绝新类型、成本不划算时回退重测；本页保留详细背景，未授予实现权限。

## 1. 现行源码与本次触发

[regression_execution.py](../../skills/dev/core/scripts/regression_execution.py) identity第70～73行比较原tested_revision与当前整个非workflow Git树；不同直接拒绝。它还绑定整个requirements数组、decisions、除执行历史外整个fix对象、证据/包身份文件和来源权威。current_evidence第139～155行重算输入完整相等，audit-delivery通过它认可未进日常门禁的FIX测试。故不只是代码树变化：无关决策/整个fix说明更新也可能失效。原有失败/跳过/伪造身份拒绝和锁内重捕获应保留。

实际FIX-001/002最新设备回执以55434ba65c为执行版本。到读取时业务HEAD的非workflow差异为六文件：确认页Screen/ViewModel、两份strings.xml、两份确认页测试。Deposit页与原两份回归测试未变，但金额换算的显示还经过确认页，不能仅凭目录不变认定不相关。维护侧只核对文件和合同，没有做完整行为适用性审查，也不为这两项预先判支持。

## 2. 目标与不做的事

新增一种有据的“原设备观察仍适用当前目标”结论；不是重签原回执，不声称新包在设备执行过，不跳过产品验收、现行自动门禁或最终独立复核。不解决全部人工验收摘要、依赖自动发现、全量记录归一化、attempt并发或通用升级。

保留两个身份：**execution_identity**来自不可改写的原回执/原装机包/原始断言及执行时间；**review_target_identity**是当前干净已提交代码树和当前相关合同。两者可以不同，审查解释差异，不能把旧包SHA填成新包SHA。设备/API/账号条件仍是旧观察边界，不自动外推跨机型或新系统。reviewed_at与executed_at分列。

## 3. 推荐的最小处理路径（拟议接口，不是已存在命令）

1. 显式选择feature/FIX/TEST对、该TEST最新有效的原始设备执行条目及摘要。按每个FIX的全部必要TEST分别核对，不能凭一个回执覆盖其他TEST。第一版不支持多层“延续的延续”，不跳过后续失败、撤回、跳过/未知或新的矛盾观察。
2. 冻结原回执及其原始证据/包身份，原/当前Git树和完整差异，原测试源/断言、当前FIX预期/案例以及相关来源/决定。冻结完整当前记录作为审查输入，比较粒度可针对相关合同，但不能静默排除决策、资源或构建配置。历史说明缺失/原包无法归因时停止，不靠今天重建包补证。
3. Agent调查直接/传递调用、渲染/导航、资源覆盖、构建/依赖/初始化、环境前提及测试装配，提交明确的实际依赖与差异理由。机器可检查路径、哈希、改动覆盖和冻结未漂移，不能证明依赖清单完整或语义独立。
4. 每批一个全新上下文只读审查，同批多个FIX/TEST可以共享调查材料，但逐对给supported/affected/unknown/partial及反例。不为设备复用再审全部45行。不相关文件不能仅凭名字放行；共享文件有增量时，完整diff及相关符号/资源/调用链必须表明确实不改原断言路径，否则重测。
5. 只对完整支持原FIX案例、且身份/证据无争议的目标原子追加“reviewed_continuity”。原始执行回执保留；保存原条目位置/哈希、新目标、共享审查事件及每对结论。输入改变则拒绝应用，正确更正不能为保护摘要而隐瞒。
6. audit只在原执行有效+延续对当前输入有效时接受该FIX/TEST的设备证据；报告/视图/最终复核清楚显示“原设备执行＋当前适用性审查，未重跑”。失败或未知仍需受影响的实际回归，不能转豁免或假装当前执行通过。

“不在已登记依赖中”不是充分证据。资源新增必须核查原key、配置和覆盖顺序；共享确认页代码变化需核对是否影响原金额显示。FIX-001的设备绘制机制未查清，会提高unknown的可能性；若审查无法排除当前改动影响，仍应重测。设计不承诺本次两个FIX必可免测。

## 4. 存储和旧读取器：必须同时设计

优先沿现有fixes.json保存一份批次审查事件，各FIX的regression_execution_history只追加有类型的新条目并引用原始执行及批次，不复制私密证据文字。原条目schema 1不改；新延续条目需独立类型/版本，不能伪装成schema 1的execution。

旧validate_receipt仅接受schema_version=1，因此新条目必须使旧fix校验器明确拒绝，而不是忽略新字段后沿旧绿灯放行。现行fixes.validate_regression_scope还读inputs.fix_id，新解析器必须保留关联约束；不依赖顶部新增字段被旧reader忽略。共享事件不能孤立改变生效范围，引用/摘要错或跨feature/FIX/TEST拒绝。具体字段格式和版本选择在获准实现时再定；改变共享记录合同预计需要中间位版本，不能仅按发布次数升patch。

最少改动面：regression_execution中的解析/冻结/应用/有效性、fixes校验与展示、audit调用、stage_view/claim_review的摘要和回读、device-regression说明及对应测试。最终复核必须绑定当前延续，不只读取旧设备执行；全部读者核对不能留给后续补丁。无需独立Skill、全项目新依赖库或第二回归结论文件。

## 5. 拟验收矩阵（未执行）

| 输入/变化 | 必须得到的结果 |
|---|---|
| 独立功能/不参与原测试的文件变化，有完整归因与新审查 | 原执行时间/版本/包SHA不变，当前适用性单列，正常门禁不自动复用 |
| 同一strings文件新增无关key，或共享文件只增加不相关成员 | 机器不直接放行；审查证明原路径/资源配置不变才可支持 |
| 相关渲染/金额/导航逻辑改变，新增初始化影响原路径 | affected或unknown，要求定向真实回归 |
| 原包身份不明、只有前缀哈希、原测试源/断言缺失 | 拒绝，不能用新包倒推过去 |
| 最近有失败/撤回，却选更早passed；跳过或编译当执行 | 拒绝，不通过旧绿灯掩盖 |
| 当前业务脏、Git/依赖读取失败、外部动态依赖无法核对 | 拒绝/unknown，不认证新目标 |
| 原证据更改、相关产品意图改动、实际案例不完整 | 延续失效或partial，补当前要求的证据 |
| 批次冻结后代码/记录/证据变动；应用期间漂移 | 应用拒绝，不能留部分生效的条目 |
| 跨feature/FIX/TEST引用、循环/篡改共享事件 | 拒绝，保留原始历史 |
| 老读取器遇新条目；新读取器遇旧记录 | 老读取器明确拒绝新条目；新读取器兼容旧执行，不自动迁移 |
| 重复应用、同批多FIX及一个partial | 幂等/明确重复拒绝；仅显式支持项可原子应用，不能批量涂绿 |
| 未安装当前新包 | 可表述代码目标的分析适用性，不能写成当前设备包运行通过 |

另需安装版原生审查正反例，尤其“同文件无关资源新增”与“隐藏的全局影响”；只有确定性夹具不能证明Agent判断准确。当前不执行演练、不新增测试。

## 6. 代价、实施顺序与批准边界

新增维护成本是类型/版本兼容、一次批次独立审查、引用/摘要验证及所有读者同步；依赖调查与全diff读取可能比10～15分钟设备会话更贵，不能预设省时。应在适用案例记录批次墙钟、调查/审查轮次、回归避免与实际执行次数、误放行/误阻塞；计费费用无账单则未知，不用token原始值直接计费。不能从代码行数给出可信人天估算。

建议先评审这份方案与成本选择，再单独批准最小实现，覆盖以上确定性和原生反例后发布；正在等待后端的Bug不被这项设计打断，也不据此重登记回执。若直接定向重测更便宜且已授权，可选择重测，不为“复用成功”强行新增昂贵审查。8025复盘仍按用户安排最后做。
