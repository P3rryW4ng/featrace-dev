# 环境绑定与未完成任务治理：顺序评审

2026-10-27。源码88c83d3，正式/CC0.29.0合同5/15文件；另有已验证的CLI查询默认小修候选。按环境、治理顺序核对代码与原隔离证据，再执行临时合成因果探针。运行资源、测试和安装均未改，冻结输入前后相同；本轮没有重跑289项，也没有业务、设备、网络或迁移操作。维护报告不是新的运行指令。

## 结论

**现有局部事实/按需验证架构有必要保护，没有整套替换的证据。两处模型边界需要明确，一处局部冗余已确认：**

- 环境身份是保守预设，既存在过宽失效，也不能覆盖所有动态工具依赖。不能全局去掉PATH，也不能仅凭顶层解释器绝对路径就断言无需环境。
- completed-only清理能保护在途工作，但不能表达“用户已经终止，且没有交付”。这是生命周期能力缺口；增加状态需要同时处理读写者、失败和知识交接，不能靠改字/直接删文件替代。
- compact已完成压缩后仍重复写盘、再次计cleaned，属于可以独立修正的幂等性与报告问题，无需改任务合同。

## 一、环境绑定

### 当前机制与保护目标

`task_inputs.py:11–12,153–155`把PATH/JAVA_HOME/SDK/Gradle/语言/时区/PYTHONPATH/NODE_OPTIONS/CI与额外env_keys合并进入一个输入摘要；env_keys只能增补。`task_workflow.py:420–438`另绑定实际顶层可执行文件字节、argv、选定文件/资料、约束、实质策略和执行协议；`execution_profile:441–443`只给当前/不匹配，原事实没有足以分解旧环境与文件差异的分类摘要。`run_check:521–526`仅在摘要、产物与时效都适用时复用。原环境值未存是有意的隐私保护，不应为诊断转而永久记录全部环境。

此前Agent接续中只有PATH摘要不同，原环境当前摘要仍匹配原事实；这证明保守环境差异带来了真实重测，但不是任意脚本都可以省略PATH的证据。

### 新的正反因果证据

见[原始结果](../evaluations/environment-lifecycle-review-20261027/environment.json)：

1. 绝对Python解释器、固定纯输出脚本，两个空目录分别前置PATH：输出相同，当前输入摘要不同。
2. 同一纯Python脚本只改无关JAVA_HOME：输出相同，摘要不同。跨工具链默认集合确有保守成本。
3. 同一绝对Python调用`subprocess(["synth-tool"])`，PATH选择A/B合成工具：输出确实改变。全局忽略PATH会漏掉真实差异。
4. PATH不变、替换合成子工具字节：只声明脚本时摘要不变但输出改变；把该子工具加入已有external_inputs后就能检测。环境变量摘要不是完整工具链身份；现有外部输入已经可用于真实依赖，不应另造重复工具注册表。

四组探针只证明所构造场景，不证明动态依赖发现完整或所有失效都多余。

### 可选方案与建议

| 方案 | 判断 | 理由 |
|---|---|---|
| 保持严格默认但不解释 | 安全优先可继续使用，体验不足 | 无法清楚区分为什么旧结果不可用，容易被误认为授权或上下文丢失 |
| 全局删除PATH/JAVA_HOME等 | 拒绝 | 跨工具、嵌套命令与构建可真实依赖；保护下降 |
| 每个检查自行声明“不影响”但进程仍继承全部环境 | 拒绝 | 声明没有改变执行事实，遗漏项仍可影响结果 |
| 严格默认 + 分类诊断 + 明确受控环境 | 建议方向 | 保留安全缺省；只有实际隔离未选变量，才收窄输入绑定；选定工具链仍用已有输入机制 |

**可先开发的有限项**：在原查询/结果路径给出“不复用”的有限分类与下一步，将“旧结果不适用”和“新执行缺批准”分开；不放宽现有reuse/ask/deny。仅为新执行采集有限组件摘要，不存原始环境值，不回填老事实。缺少历史组件时明确“历史未采集，不能细分”。不得为诊断重复扫描整个输入或声称已找到具体旧变量。

**涉及模型的下一批**：为确有需要的本地检查设计受控环境模式：执行器真的只传经选择的环境；未明确选择时继续当前严格继承。配置、传入环境摘要、实际命令和已声明工具链共同绑定；真实来源/输入变化仍失效。不是沙箱或远端状态监控，也不能证明未声明动态文件。新增命令字段/执行语义要按协议/合同发布处理，旧任务固定原工具，不加任意前驱白名单。

验收反例至少包括：未用宿主变量改变不会改变受控子进程；被选择变量/工具字节改变必须失效；绝对解释器嵌套查找仍安全；未声明变量在子进程确实不可见；继承模式与真实deny/过期/失败不被绕过；老事实无分类数据不伪造来源。

## 二、未完成任务治理

### 当前机制与实际缺口

`cleanup:946–988`仅接受complete，先检查保留期、未知文件、所有权和必要长期摘要；`maintain:1057–1085`只轮转有限任务，跳过未完成，按回执保留策略处理完成项。`storage:1015–1055`统计整体文件使用量（10万条上限、可能partial），只对选定页解析任务状态，明确counts_scope=selected_page。它不是全局容量配额或跨机器数据库。

**“7天会全部删除”并不成立**：manual不自动清理；compact保留精简回执，数量仍增长；forget仅对满足真实权限/期满/交接条件的完成任务删除记录。未完成、缺失交接、不可读或未知资料不自动消失。回执保留原策略，不因项目后来改策略而静默改写。

已有200/800空草稿规模证据不是50人真实项目压测；只确认未完成记录按量累积。不能据此设定一个看似科学但没有负载依据的全局阈值。

### 本轮新增因果核对

- 合成任务完成、模拟8天后按compact维护：首次清理成功；第二次仍cleaned=1，记录updated_at/checksum再次改变，即使没有剩余日志。原完成时间没改，没有发现负面事实被误删；确认的是重复元数据写盘与清理计数不准确。
- 对已经压缩的完成任务，已有显式cleanup --forget可以移除记录且保留代码；缺口不在所有完成项都无法删除。
- 草稿创建时间设为20天前（保存时间仍是本轮，不代表已闲置20天），仍正确拒绝CLEANUP_REQUIRES_COMPLETE；公开入口没有retire/cancel。它应继续保留，不能为了容量伪装交付。

### 建议分开处理

**G1，可独立小修：压缩幂等性。** 再次维护已压缩且无剩余自有输出的记录时不改updated_at/checksum、不虚报新清理；轮转仍能推进。不能只凭“facts缺失”就提前返回，必须保留部分中断、剩余附件/未知文件和必要交接检查；显式forget仍可处理压缩回执。无需新状态/数据库或合同。

**G2，需要设计批准：明确的非交付终止。** 增加任务层retire（最终名称开发时固定），与“暂停”、complete和逐承诺defer分开。只依据真实、已有同范围终止决定执行；不因超期或容量自动代替用户决定。终止回执明确not-delivered，不制造supported、不解除原失败。必要未解决问题/真实约束先落到项目既有简短问题位置，保留原对象、条件、时点及证据身份；不是永久保存全部日志。之后才按明确保留策略清理自有过程。恢复工作须显式调查当前状态，不能把终止回执当当前通过。

这触及begin/plan/run/observe/assess/correct/close、failure/deferral、list/status/storage、prune/cleanup/maintain、接续与旧读取器，属于生命周期合同变更，不可冒充一行清理补丁。新合同服务新任务；不自动迁移、终止或删除旧业务。旧积压如需处理必须另外明确选择与授权，不能承诺新状态自动治理旧资料。

**G3，策略边界。** 复用现有总量/陈旧页查询与轮转，不立即增加永久索引、常驻后台或团队分布式存储。可设计有限治理预览，区分可清理完成项、缺交接项、活跃/已停止未终止项、未知文件；不能把页内统计说成全局。若以后需要容量预算，应由实际负载和使用者确认，优先告警/明确处置，不自动删失败，不因全局清理阻塞无关业务交付。

验收反例包括：重复compact无写入/准确计数；中断剩余输出仍收尾；未知文件/交接丢失保持拒绝；retire不得结项计通过或吞失败；任务忙时不终止；终止后不可继续写运行事实；到期仅删明确自有文件；旧任务/其他任务/外部原件不动；恢复不重签旧事实。

## 建议开发次序与审批边界

1. 已验证的CLI分页小修 + G1压缩幂等性，作为局部修正；保留289项既有证据，新增行为变化才执行对应全套。
2. 环境差异的有限诊断：不放宽复用，旧事实缺数据明确未知；先核清数据/协议变动边界。
3. 受控环境模式与非交付终止生命周期形成一次明确的合同方案，经产品所有者批准后开发；不先堆提示词、默许删环境或后台删任务。
