# 项目结构与文档一致性复核（2026-10-08）

复核起点：`bb00c26`，源码与 Claude Code 安装版均为 0.5.37，工作区起初干净。本次是结构、文档职责与关键代码契约的静态审查，不是新的完整功能验收，也不重跑或改写历史测试结论。

## 方向与实际结构

未发现北极星发生偏移：目标仍是把已有项目中变化的产品意图推进到可验证、可接续的交付，同时保护旧行为。当前 L1 有真实案例，L2 推进中；自动化及多 Agent 的真实净收益仍未证明。

```text
featrace-dev/
├── README.md / README.en.md       使用者入口、安装、日常操作
├── PRODUCT.md                    产品目标、边界与成功指标
├── MAINTAINER.md / ROADMAP.md     当前交接 / 当前队列和完成条件
├── skills/dev/                   自包含运行包，76 个文件
│   ├── SKILL.md                  dev 总入口与阶段路由规则
│   ├── core/references/          23 份按需加载的流程说明
│   ├── core/scripts/             34 个脚本文件（含内部辅助模块）
│   ├── core/schemas/ + assets/   结构约束与初始化模板
│   ├── profiles/                 Android / Generic 适配
│   └── specialists/              Build / Verify 两个专家说明
├── scripts/install.py            分发完整运行包与安装版本标记
├── tests/                        回归测试和合成输入
└── docs/                         使用指南、决策、证据、审查与历史
```

业务项目的 `.agent-workflow/` 是共享事实存放位置，不是本仓库中的集中服务或数据库。多个专家不能同时随意写入它：Build Worker 交回候选，路由统一核对并串行更新记录。Requirement、Scope、Repair、Deliver 目前在主 Agent 中按阶段加载；Build 可保守选择两个隔离 Worker，Verify 仅明确请求时使用独立上下文。

`docs/evaluations/` 有 650 个已跟踪文件（含原始合成证据）。数量较多，但安装器仅分发 `skills/dev/`，这些材料不会整体进入运行包。维护时仍应从验证索引按需打开，不把整个证据目录载入上下文。

## 发现与处理

| 发现 | 影响 | 本次处理 |
|---|---|---|
| 使用指南的旧发布小节同时写“本机为 0.5.33 / 0.5.34 / 0.5.35”，首节又写 0.5.37 | 同一文档看起来有多个当前版本 | 整理为当前执行机制；历史版本转由 CHANGELOG 和原评估承载 |
| 流程图由无参数 dev 直接连到 next | 容易误解为激活就开始工作，与 session-mode.md 的激活边界相反 | 增加等待后续请求节点，明确激活本身不扫描、不开发、不写记录 |
| 图下注释称独立 Verify 外“其他阶段不拆分” | 与已经存在的 Build 专家、两 Worker 路线冲突 | 明确 Build 的条件式派发及剩余四阶段的同 Agent 加载 |
| PRODUCT 的当前完成边界重复列出旧版本实现 | 产品方向文件易变成第二份过时进度表 | 保留结构与边界；具体版本、队列及测量结果引用各自责任文档 |
| 架构 A56 的历史“下一步”未连接最新对照；路线图只引用 A42–A54 | 接续时可能遗漏任务视图与全文差异检查，或重做已完成对照 | 保留原决策，追加带日期的证据链接；路线图引用扩至 A57，并强调决策不是当前队列 |
| Agent 在对照中用单篇 reference 标题推断安装版本 | 同一个 0.5.37 安装包被说成不同版本 | 维护说明明确源码读 VERSION，安装读 `.feature-delivery-install.json` 并核对哈希；reference 标题不代表整包版本。尚未修改运行提示，真实使用继续观察 |

以上是文档表达与责任边界修正；不修改北极星、默认派发策略、命令、记录结构或运行版本。
