# 2026-11-06 F06复用与检查组合评审

基线234c111，正式/CC0.30.6合同6。业务只读：核对F06原任务、c38500ea四文件修复和该提交的data/payment构建文件，不改变后来F08代码，不执行业务Gradle/设备操作。

## 原因核对

F06把多种页面/交互放在ui-render一个标准中，inputs包含修复的WalletExchangeConfirmViewModel。现有observation_stamp按声明文件身份判断，不能从无关分支的语义证明自动保留旧运行事实。因此“登记首轮就能复用24场景”未成立；原首轮未登记，不能事后补造原事实。整轮重跑缺少先行影响调查是CC报告的偏差，但工具可能拒绝旧观察是实际机制边界。

六项检查都显式cache.mode=never。即使缩小输入且身份不变，再次run也不会复用内核执行；仍需区分是否有必要发起检查和Gradle自己的增量复用。CC只归因输入变化遗漏这一配置因素。

data/payment在c38500ea明确implementation依赖domain/payment；仅凭不调用ConfirmExchangeUseCase，不能删除domain执行输入。当前inputs是选定路径清单，不是“整个domain目录”；input_sets为空，不能据此证明执行依赖已完整或安全缩小。未调查完整Gradle任务图/工具链，不认证缓存安全。

必要项至少类型检查、domain及feature单测三项；CC标题“两项必要”不符自己的表格。assembly把apiCheck、impl测试和dev-app打包捆绑；gates把四规则、架构、分层与三模块lint捆绑。它们的变化原因可能不同，值得在新计划按不同输入/触发原因分组，但不要求每个Gradle task一个检查。新包的必要打包、项目强制门禁及实际依赖不能凭“CI还会跑”删除。

六项修复后命令的记录窗口为09:47:37–09:48:51Z，约74秒（含间隔）；不证明全部可省。整轮走查及估计补跑1–2分钟来自CC补核，不把约9分钟当实测节省。没有运行真实Gradle依赖分析，哪些门禁可免仍需项目规则和实际任务输入决定。

## 修正与架构取舍

1. 当前指引明确文件粒度边界：适用旧观察保留，不承诺同文件无关分支自动复用；禁止删实际输入、改原时间/重新登记旧观察绕过。复合标准按真实独立依赖/判定划分，不拆成逐像素台账。
2. Android明确检查组合的选择依据，cache never与内层缓存区分；拆组合保留真实执行输入和项目要求。
3. 不改内核。若需要“文件已改但某场景仍适用”的采用能力，应专项设计显式的新适用性证明、旧观察关联、实际差异、当前未知/失败保护及审查边界。这改变事实采用合同，不能靠一句静态说明或隐藏哈希实施。当前只提出设计问题，未获架构替换批准，未开发。
4. 不强制采集所有场景或全面重跑；真实适用性不足的相关承诺才补证，已知过宽标准在新任务规划时合理分组。旧F06不重建、不重测。
