# 0.5.20 普通 Scope 请求隔离演练（2026-09-24）

目的：上一轮明确要求 Agent 说明“候选是否完整、哪些配置需人工阅读”，这可能提示了答案。本轮从相同 Gradle 声明的**全新 Git 副本**开始，使用已安装 Claude Code 2.1.281 与 Skill 0.5.20，只提出常见的 `/dev scan` 请求：“了解有哪些模块、它们之间如何依赖；只做调查，不改业务代码”。提示没有点名外部脚本、动态依赖、缺口或完整性。副本含 52 个已登记输入文件；原业务项目未被访问或修改。

## 观察

执行轨迹表明 Agent 读取已安装 Skill 的基线和模块说明，运行 `scan-prepare` 后查看静态候选，再打开根 settings、被加载的 settings 脚本与应用构建声明。它注意到 0.5.20 新增的两条行号缺口：外部 settings 加载、动态配置名的 `add(..., project(...))`；随后从外部脚本人工核出 16 个模块，说明自动候选只含 30 个静态模块、166 条边和 21 条缺口，且 React Native 自动链接仍无法核实。Agent 没把这 16 个模块误称为脚本自动发现的候选，也没有运行 Gradle。

这证明**普通 `/dev scan` 表达下，Agent 有读取并追查缺口的行为**，但不能单独证明新提示的因果效果：Agent 在读取候选之前，已经直接打开了被加载的 settings 脚本。没有与旧版本同条件对照，也不能推断所有自然表达都能触发。

Agent 随后继续完整 scan：手工建立 46 个模块的正式目录，生成图，撰写基线草稿并 `scan-publish`。输入文件 52/52 的 SHA-256 均不变；只有隔离项目 `.agent-workflow/` 新增。质量配置验证显示 **0 个已选门禁**，并明确输出 `SELECTION_REQUIRED`；因此基线已发布不等于项目质量已验证。整次调用 14 轮、约 113.4 秒，CLI 报告费用约 0.828 美元。原始轨迹留在本机临时目录，SHA-256 为 `48478d6b4edbb6b285bc80a84d28bb467f22ba338d29dba74bba602d134744b7`；不上传项目配置样本。

## 发现的后续问题

1. **候选图整批丢失，确定性缺陷。** 候选发现器保留了 17 条指向未被静态 include 的目标边，并为目标登记缺口；但图读取器要求每条边的两端都出现在静态候选模块表中，于是报 `Gradle candidate artifact is invalid: candidate edge is invalid`。生成的图只有 46 个正式节点和 180 条正式边，候选边为 **0**，21 条候选缺口也没进入图；图仅保留一条总括错误。正式目录可照常生成，使丢失的待审信息不显眼。这是生成与读取契约不一致，需单独修复并测试未知目标仍保留待审边/缺口、已知候选正常显示、损坏记录仍拒绝。
2. **条件关系被压平。** Agent 从限定若干构建变体的 `add(..., project(...))` 推出应用到调试模块的依赖，并将其写入正式 `depends_on`，图显示为无条件 `declared` 边。文字说明保留了“仅非生产变体”，但机器可读关系没有条件字段；后续范围分析可能误以为所有变体都依赖它。应明确条件关系的登记规则，或在现有模型中保留为待审说明，避免无条件提升。
3. **构建注释被提升为模块职责。** 隔离副本不含业务源码；正式目录仍写入“纯接口”“图片 SDK 只能放某模块”等基于构建注释的职责主张。Agent 在最终回答中承认无源码，但正式 JSON 的单条摘要缺少逐项证据等级。真实项目采用前应区分“构建声明/注释约定”与已核实实现，不能把本次目录当作业务行为档案。

本轮不是端到端交付、真实业务 scan 或 Verify A/B。下一步优先修复第 1 项，因为它会直接丢失图中的待审证据；第 2、3 项作为正式目录准确性与成本验证的一部分处理。修复之前，直接读取 `candidates.json` 的缺口，不以 `graph.json` 为空断定没有未审关系。
