# 共享分类与独立评审触发条件评审

2026-10-26；对象：0.26.1、合同3。源码main为1d9e066；当前正式来源abac4f1。只读核对运行实现、现有测试和上轮隔离原件，没有新运行测试、派Agent、操作设备或更改业务记录。本文是候选方案，不是已经生效的运行规则。

## 结论

存在局部设计耦合：**影响范围分类shared被直接作为独立评审的充分条件，而共享事实本身没有统一的调查要求。** 建议保留当前主张/事实/局部评审架构，替换这条无条件触发及对应指引，而非重构整个验收内核。共享调用决定影响面和必要验证；另一个上下文是否值得加入，需要依据项目明确规则、错误后果、影响可控性与现有证据的盲点判断。

本轮证明了当前条件确实是无条件约束，不能证明所有既有共享评审都多余，也没有定量证据承诺减少多少分钟。真实共享、复杂交互或高风险变更的独立审阅仍有价值；它不能替代缺少的运行观察，更不能靠更多Agent解决资料或环境缺口。

[架构原则](../decisions/architecture.md)明确按实际风险/项目规则审查；现实现是其中较保守的具体政策，存在收窄空间，不能把原则当作已实现的低风险免独审路径。源规则仍有效，未批准并实现替代前不能指导CC删shared标签规避。

### 上轮例子的复核与混杂因素

- SC-02：errorBox实际服务注册与居住国两个页面；共享成立，相关渲染确实要覆盖。其项目AGENTS同时要求共享代码使用真正的新上下文评审，因此当时评审有规则依据。不能用“本可更轻”追溯认定执行越界，也不重开它。
- SC-04/05：实际项目可见调用中，Python message只被单测调用，浏览器没有接到它。计划分别写“shared error mapper”“shared domain behavior”，缺少多业务消费者或对外共享契约的依据。应判为**共享分类/必要性论证不足**，不武断判它绝不共享；公开库入口、插件、反射调用也可能构成共享契约，需另查证据。
- 夹具AGENTS写“For shared code, independent review must use a genuine fresh context”；这句话至少约束评审方式，对“每个shared都必须评审”的含义不够清晰，执行者也将其解释为强制项。它与Skill的明确强制规则共同影响结果，当前样本无法区分二者各自的成本贡献。
- SC-06和后续任务也采用同一项目规则，不能当作去掉内核条件后的对照。上述案例均未让评审导致父需求全部重测；问题集中于是否值得触发额外上下文。

上述原件已只读核对；精简身份与计数见[上轮结果](../evaluations/isolated-agent-20261026/results.json)。没有测量不触发评审时的同等质量结果，不宣称评审无收益、必然漏验或固定节省比例。

## 候选决策方式：先影响，再选择验证与评审

### 1. 调查共享事实

从本次实际改变的函数、组件、资源或契约出发，找实际消费者及传播路径。记录在既有reason/范围说明中即可：改变什么→哪些调用会受到何种影响→哪些等价、哪些有差异。

不以文件名、多个测试、公共目录、import数量、同一个文件被改或“可能以后复用”判定业务共享。多个真实调用只是共享证据之一；有明确对外兼容承诺的公共API，即使仓库找不到外部调用，也可能共享。动态调用查不清时标局部未知，不能把“没搜到”当不存在，也不默认升级全业务复验。

### 2. 据影响选择测试

实际共享扩大到受影响的展示变体、调用契约、状态或交互；等价调用可用代码依据加代表性检查，不机械地每处完整走流程。纯展示不测未改业务逻辑，交互、状态、权限、支付不能被UI标签掩盖。独立评审与测试是两项选择，不以复核替代缺证，也不因为多测试自动取消必要审阅。

### 3. 决定是否需要独立上下文

| 条件 | 候选处理 |
|---|---|
| 当前有效项目/用户/发布规则明确要求 | 按其范围执行；若与目标冲突，先说明影响并由有权者裁决，不擅自覆盖规则 |
| 影响涉及权限/资金/数据丢失、对外契约兼容、跨模块共享状态/生命周期等，错误后果严重或难以恢复 | 对相关高风险主张独立评审；即使只有一个调用也适用 |
| 多调用机制存在实质差异、因果链复杂、影响说明有难消除的盲点，第二视角可以提供实质核对 | 先做能自行完成的调查，再对明确问题局部独立评审；不是笼统因“未知”全量派审 |
| 私有或共享的局部展示/简单纯函数变更，影响已查明、差异和充分断言可直接核对，且无强制规则 | 可不独立评审；说明调用、证据、无须第二视角的理由，仍完成必要自查和测试 |
| 缺设备、缺原始需求、缺凭证或没有对应运行事实 | 解决该缺口或诚实保留阻塞；派评审者不能把缺事实变成支持 |

不设置多调用数量阈值、改动行数阈值或总风险分。上表是因果判断要求，不是声称能用程序自动判断所有语义的分类器；第二视角也不保证独立无误。仅在确需独立审阅时传原始意图、相关差异/调用、选定事实与待核问题，不传预设“应通过”的答案。

## 实现选择与建议边界

比较四种路径：

1. **仅收窄shared定义**：可纠正SC04/05的无据标签，改动小；但所有真实低风险共享展示仍被强制评审，根本耦合仍在。
2. **保留分类、替换无条件强制（建议）**：shared描述传播事实；review描述独立核对需求。复用现有independent/reason/criteria，明确新计划选定标准；修正对应指引、示例与旧政策测试，不新增永久地图、评分系统或迁移合同。
3. **只删guard、不补调查与反例**：不可采用。会失去原保守保护，却没解释谁负责发现必要共享/高风险审阅。
4. **新建全量调用图/自动风险引擎**：当前没有必要性证据，成本和误判面更大，暂不开发。

建议路径2，但属于**拟议的运行政策变更，待批准实现**，本轮不执行。开发时还需明确：内核继续验证已声明的评审范围/出处/事实有效性，Agent负责语义调查，项目约束继续生效；若需要把某条明确“必须独审”的项目规则做机器强制，应另查现有策略能否表达，不能假装reason字符串已经实现这项能力。当前也没有完整自动解析项目规范的保障。

替代的保护目标不是“所有shared必有第二个Agent”，而是“影响面有因果调查、必要独立核对不能省、结论有充分事实”。不以重新标记旧任务免除已约定评审，不改旧回执/失败、不迁移任务。若确需更正现任务，使用正常授权的局部重判；真实运行失败继续必须由针对性新事实解决。

实施前检查所有读写者：plan校验、review_required、review-input、assess、status/close、标准摘要和执行协议依赖、运行指引与使用图。分类与评审选择若影响身份，需实测局部改评审是否错误触发执行失效，不能承诺改字零重跑。旧计划省略criteria的保守全局语义暂保留，新计划显式范围；现有真实出处、选定事实、负面/失败保护及权限边界不删除。

特别区分两件事：同版本只改变review选择，criterion_stamp按相关标准更新；修改validate_plan的实现后升级工具，则整个被采集函数的AST会改变协议身份。前者已有局部范围设计，后者是本轮静态发现的实现边界。优先在开发设计中评审能否分离“执行所需有效性/权限校验”和“验收策略校验”的协议采集边界；不得直接把validate_plan从身份里排除，因为它还校验执行输入、环境和缓存等真实保护。若最终不分离，应固定旧活动任务使用0.26.1、新任务用新版，清楚报告升级限制；不引入任意旧哈希白名单、不自动迁移或改写原事实。当前没有执行候选升级探针，未把这项耦合定性为已发生的业务重复运行。

## 开发验收反例（尚未执行）

| 场景 | 预期与反例 |
|---|---|
| 私有样式/仅测试调用的纯函数 | 不因目录名或测试数强制shared/独审；仍验证真实目标与语义 |
| 两页面共享图标/间距，证据充分且无强制规则 | 标shared、覆盖相关变体，可有据不独审；不能复验整个父PRD |
| 共享校验/导航/状态或公共契约改变 | 调查实际差异和风险；需要时只审相关主张，不能用低风险分支绕过 |
| 单调用资金/权限问题 | 不依赖shared标签仍识别高风险并独立核对 |
| 项目明确要求共享改动独审；条件含糊的项目规则 | 前者保留强制，后者定位原文和权威，不把全部规则覆盖掉或反复问已解决选择 |
| 漏掉动态调用或待决产品边界 | 只阻塞相关动作，不能自动当无影响/通过；独审不能替代原件缺失 |
| 增减review范围但代码/检查输入不变 | 仅相关判定需要更新，不为登记、换上下文重跑；原事实身份不变 |
| 已观察到运行失败、假出处、错误事实摘要 | 仍拒绝结项；不能删shared/review或仅静态证明来消除失败 |

程序反例只能证明声明行为；至少用无强制共享条款的干净夹具做一组真实Agent前向验证，并与有强制条款的反例区分，避免重演本轮混杂。规格先固定，执行者只拿正常请求与资料，保留失败与额外成本；用户授权前不派评测Agent。维护脚本变化按仓库要求完整当前套件一次；同次日志复用，不加评分门禁。没有可比基线只报告本次成本，严重漏验不能以提速抵消。
