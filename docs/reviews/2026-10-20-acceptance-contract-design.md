# 验收合同替代设计：主张级判断与完整交付组合

> This draft is superseded by the [final development plan](../designs/acceptance-v1-plan.md). Historical design reasoning below is retained; no implementation is implied.

日期：2026-10-20。状态：**设计建议，待批准开发**。基于main `3f5ddcee232bea98ed09f8dab5e3f9ac2837658e`、0.18.4运行实现及上轮未提交的[底层评审](2026-10-20-acceptance-architecture.md)。本轮只设计及维护文档更新，没有运行候选、测试、迁移、安装或发布。本文接口与字段均未实现。

## 1. 决策与可证伪目标

选择分层替代：保留原始事实/输入检测/失败保护，替换单需求中“共同语义输入变化使全部验收与终审当前性一起失效”的判断。不是只为旧全局戳增加例外，也不是从零重写执行器。若等价对照无法减少重复判断或引入误放行，停止扩大，不以已经开发为由迁移用户。

首批纵切必须同时打通：要求版本→事实引用→独立覆盖/适用性判断→全部主张的交付组合。只改manual_scope摘要而让最终claim_review仍整批重做，或只改终审却保留所有行的全局摘要，都不算完成。普通next/check路由不新增用户命令或必填台账。

必须兑现的场景：同一执行输入，修改一个局部验收或一条有明确局部范围的决定，受影响主张重新判断；其余主张经过对完整差异的有据排除，可以引用原判断，而不重签旧观察或逐行重新登记。全部活动主张仍需在最终组合中有当前结论。未知影响阻断，不能按文件类型或依赖清单未命中自动免验。

## 2. 首批支持范围与明确限制

| 范围 | 首批决定 |
|---|---|
| 证据种类 | 直接登记的manual观察（passed/waived/failed/unavailable原件）与现有自动合同2的完整attempt引用；每条主张使用明确的事实引用 |
| 项目执行模式 | 首批要求已显式准备execution_contract2的兼容项目；复用当前attempt，不修改check_runs执行器。旧合同项目不得自动升级或承诺免跑 |
| 代码变化 | 仍完整检测代码/配置/资源/规则变化；相关物理执行失效仍按既有规则处理。本批不实现按文件闭包复用单项检查 |
| 需求/决定变化 | 以完整变化清单作漏项检测，以逐主张判断传播；不以整个decisions.json字节变化直接撤销全部判断 |
| 历史采用 | 只迁移可完整核验的直接原事实。已有carry/annotation/adoption/设备复合链若无已实现并验证的只读适配，整项prepare拒绝并报告，不能跳过其活动行或伪造新执行 |
| 多观察组合 | 首批不提供任意历史观察拼接，也不从retired挑最有利结果；冲突/互补留缺口，列入后续设计，不借此扩大首批 |
| 设备FIX/模块档案 | 原有执行、连续性与档案规则继续独立生效；本批不声称消除其全局失效成本 |
| 终审 | 完整活动集合审计保留；独立判断仅重做确有变化或未知部分，已审的共同差异按明确引用复用；不减少最终需满足的主张集合 |

重要接入限制：[check_runs.enabled](../../skills/dev/core/scripts/check_runs.py:68)是项目级标记，[selection](../../skills/dev/core/scripts/check_runs.py:93)按需求保存。给旧项目启用合同2需要盘点同时参与的活动需求、选择与宿主版本，不是“只升级一个feature”。若没有这一批准/准备，继续0.18.4，不能把候选试点当已接入。只读历史交付不自动重新认证、不改complete；明确要求认证当前版本时才进入当前合同。设备连续性仍整体绑定部分权威输入，本批后的总收益可能仍被它限制，必须实测披露。

## 3. 一个事实来源，四类职责

沿用原需求、决定、来源、任务与原始证据文件，不再复制另一份产品规格。

| 职责 | 唯一事实/记录 | 规则 |
|---|---|---|
| 执行/观察事实 | verification.json原history、现有check-runs、设备原回执及归档件 | 不改原时间/版本/结果；失败和撤回保持可见；引用必须验证摘要及完整来源 |
| 主张身份与版本 | verification.json新增acceptance字段 | 稳定key与内容版本分离，精确引用原规格和当前locator；不是独立PRD |
| 当前判断及共享变化审查 | 同一acceptance中的追加事件 | 独立审查的覆盖/适用性判断只存一次，状态、验收和终审共享读取，不再重写同义结论 |
| 最终交付组合 | claim-review.json新生成清单 | 只引用当前主张版本与有效判断；不是第二份人工编辑的判断账本。完整集合校验仍执行 |

建议verification.json使用下一未占用schema6及`acceptance_contract:1`，并以最低reader版本保护。现有items/retired/history保留原事实；schema1–5仍支持其原合同。新格式下旧manual_scope_ref不再作为活动判断来源，只作已冻结的历史出处。格式和版本号需在实施前完成字段校验表，不能只改max schema常量。

建议字段（名称可在实现审阅时调整，语义不可模糊）：

- `acceptance.generation`：并发比较用版本号；任何受管写入更新，不能把它当业务变化证据。
- `acceptance.claims`：`claim_key`、当前`version_digest`、`row_locator`、`kind`、`source_refs`、`context_refs`、`predecessor_refs`、`fact_refs`。只存规范引用与摘要，不复制整份PRD。
- `acceptance.assessments`：不可变事件；包含冻结完整输入摘要、完整差异索引、审查者、逐变化影响分类、被影响主张判断、明确排除影响的目标集合及理由、引用旧判断、负向与事实障碍、事件摘要。可在一次事件中共同审查多个目标，不能只给一个“整批supported”。
- `acceptance.frontier`：当前活动主张与有效判断引用；指针不是权威，resolver必须重新验证引用、负向与输入。不能通过删指针使旧拒绝消失。

字段约束草案：schema与contract必须为精确整数；feature_id与目录一致；generation为非负整数且写入只递增；claim_key为feature内唯一的helper分配标识，版本/事件/原件摘要为规范序列化的SHA-256。locator是类型化的requirement/impact定位，不允许任意文件替换权威。source/context引用包含源ID、相对路径、JSON Pointer或精确片段定位与捕获摘要，解析出界、重复冲突或目标文本不符均拒绝。事实引用必须包含原容器/条目位置、原结果摘要、原测试身份和原件引用；自动事实另有完整attempt与result摘要。引用存在不是覆盖证明。

判断事件的目标集合必须与请求集合逐项一致，verdict只允许supported/partial/unknown/approved_waiver；豁免需合法原授权。每项输入变化必须有affected/unaffected-with-evidence/unknown分类和目标范围，重复、缺失、未注册分类或未知字段不能静默忽略。未受影响引用需旧判断摘要、版本/事实不变证明和本事件排除依据；新判断需required_scope/observed_scope/evidence_refs/counterexample_check。审查者字符串不证明独立，实际宿主须提供新上下文只读审查；没有这一能力保持provisional。

claim-review生成组合建议schema2，含feature_id、合同/世界输入摘要、精确活动主张版本集合、每项judgment_ref和required_gate_refs、明确blockers。没有完整集合、current引用或独立判断时不得生成可交付组合。Git HEAD只作修订标签，内容/规则与实际环境身份决定适用性；工作流提交不应单独毁掉相同输入的判断。schema6完整字段允许表及所有错误码应作为W1规范产物固定，不把未知字段按“说明”排除。

不再新增每行“通过记录”来证明同一观察仍适用；采用/复核只追加判断事件。普通用户继续读verification.md、状态和交付报告。

### 身份、版本与条款调整

`claim_key`由helper分配不含产品含义的唯一值；首次prepare与行一对一，重复文本也不得合并。沿用现有row id作为定位别名，不能依靠其序号或文本哈希判断同一个主张。规范中的精确source aspect、approved decision或preserved behavior仍是权威。

主张内容版本绑定自己的陈述/验收标准、前提/例外/否定、明确共用约束及权威投影。父条款全文和其他决定仍在全局观察输入中；其变化必须被完整差异审查，不允许通过没有登记为依赖就忽略。父条款变化到底只说明某一AC还是影响所有子项，由独立变化审查确定；未覆盖变化就是未知。

`sync`只生成待对齐关系和新版本/新主张，不提供支持。已有AC改字、插入、重排、拆分/合并时：确有稳定来源映射且一对一才可提出同key新版本；有歧义则新key并保留旧项，不能按相似文本自动继承。拆分/合并记录前身关系只用于追溯，不继承通过/豁免。

## 4. 两种摘要的职责不可混用

**全局观察输入**继续覆盖业务树、实际执行输入/规则、来源全文索引、需求/决定/影响/任务语义与原始产物身份；用于发现所有变化及冻结/漂移检测。外部环境没有可靠身份则明确未知，不能以代码相同替代。允许字段白名单仅限已有明确进度控制（例如feature.status、任务进度等）；status_note等自由文本不自动忽略，因为可能藏有新限制。

**主张判断输入**绑定该版本的权威、真实事实/断言/包与环境、适用性及其引用的共同审查。不得直接绑定整份其他判断历史或无关决定文件。未分类的新字段/决定/来源差异必须进入共享差异审查，不能使用忽略清单绕开未知。

输入变化后的算法：

1. 捕获当前完整输入，并与最后已审全局输入逐项比较；新增/删除也列入。源文件和JSON字段用精确路径/片段定位，不能让Agent只报告它认为有关的变化。
2. 没有变化：验证当前引用、最新失败和生命周期后读取现有判断；不执行、不迁移、不重写history。
3. 有变化：状态先为needs_review，先前事实/判断保留历史；生成一份共同差异材料。初始目标传播可以用已登记关系辅助，但未登记变化不能自动排除任何目标。
4. 新上下文审查者对每项变化分类：affected、unaffected-with-evidence、unknown。逐项覆盖完整变化集合，并明确所有当前主张在新世界输入下的归属。相同理由可共享，但必须列出目标集合、调查入口与未覆盖项。
5. affected主张获得当前实际证据后再判；unaffected目标引用旧完整判断和本次影响排除依据；unknown保留缺口。旧主张已partial/unknown或有较新失败时，不能只因“代码没变”重用为supported。
6. helper检验完整变化覆盖、当前集合覆盖、版本/引用/事实哈希、负向前沿和冻结输入。结构校验不宣称能证明语义；独立审查责任和反例仍存在。缺一项就拒绝apply，不能只让遗漏目标继续保留绿色。
7. 一次保存事件与指针，不逐行改事实结果。交付组合使用本次排除证明加旧判断，不凭旧supported盲继承；共同输入再次变化时只读显示待审，重新完成对应差异处理。

这并不承诺任意变化后无需审查全部集合。它减少逐行重录与重复原件阅读；共有权威变化不明确时，仍可能整组审查/补测。若所有“排除影响”每次都要读完整原件、成本不低于原机制，候选必须如实判收益不足，而不是靠换术语宣布成功。

## 5. 统一resolver与读者契约

建议在一个新模块`acceptance_contract.py`中集中新合同逻辑，避免每个helper各算新戳。它替代活动分支，不是又一层fallback。以下是内部接口约定，不是已实现API：

| 接口 | 输入/输出 | 禁止事项 |
|---|---|---|
| `inspect_contract` | 版本、读者能力、原事实可核验性和准备阻塞 | 不自动prepare或执行 |
| `reconcile_claims` | 当前活动来源→一对一key/版本候选及歧义 | 不推断通过、不自动确认权威 |
| `capture_assessment` | 当前完整输入、变化、目标与原件引用→冻结请求 | 无法读全/存在未结束进程就拒绝 |
| `apply_assessment` | 冻结请求+独立返回→单次不可变判断事件 | 不重签原事实、不用较早成功越过负向 |
| `resolve_claims` | 当前输入+合同记录→逐项判定和明确原因 | 不执行、不写入、不靠fallback凑绿 |
| `compose_delivery` | 全部当前主张+必需检查/回归等→组合清单 | 不改变产品状态或替代其他门禁 |

内部输出分开`fact_status`、`applicability`、`coverage_verdict`、`delivery_eligible`。外部passed/retained/waived等旧展示可由映射适配，不能压缩成一个无法解释的stale；展示未决定前不删除已有状态。当前活动主张与必需门禁的集合必须精确，不得将gate行当业务覆盖结论。

### 自动、手工和负向规则

- gate行读取合同2当前完整attempt；命令全过只证明检查执行。自动需求行仍需当前完整断言覆盖判断，不能直接借gate绿灯。
- manual结果是观察事实，不表示独立审查完成；同一个当前判断同时供Verify、审计和终审读取，避免先逐项沿用审查再把同一材料独立审一遍。
- 必需检查仍整组执行；任何代码/测试/选择/环境输入变化都由原check_runs判定，首批不拼接不同attempt的gate结果。
- 最新失败/撤回、未执行、进程未结束与原件缺失均保留障碍；没有新证据/权威不能仅换reviewer把同一负向变正。负向针对明确主张/版本与事实范围，不能以新key逃避同一问题；新版本必须显式处理其前身负向。
- 豁免只支持原授权的范围/条件/期限及风险，不能由依赖排除或文字相似继承。先前豁免与本次非豁免部分分开判断。

## 6. 文件与命令的具体接管清单

| 文件/入口 | 新合同下的处理 | 保留/退出 |
|---|---|---|
| verification.py | schema6分派、sync版本关系、record真实事实、status/validate/impact_results调用统一resolver；run继续真实执行 | 全局context/manual_evidence_stamp等仅供schema1–5历史合同，不再给schema6算活动戳 |
| claim_review.py | capture/apply/check接入独立assessment和完整集合组合，生成claim-review新清单 | 不再以一份全量input_digest强制所有判断重写；旧审核作为不可改历史原件 |
| verify-inputs.py、feature-status.py、closure-route.py | 展示同一resolver的接续/缺口；历史交付与当前认证分开 | 不再各自判断schema6当前性，0.18.4重复分类分支被替代时删除 |
| audit-delivery.py、validate-feature.py | 保留项目/修复/来源/任务前置项，schema6业务覆盖改读统一结果 | 不允许旧全局摘要结果补救新resolver的阻塞 |
| impact.py、stage_view.py、render-workspace.py | 通过对应验证入口取得当前判断与原件引用；生成视图不作权威 | 视图不得另算当前性或复制通过记录 |
| evidence_carry.py、manual_scope.py | schema6拒绝record/retain/carry/prepare-batch/apply-batch等旧活动写入，给出新入口 | 不再为schema6维护另一条current/apply通路；旧格式原件适配保持只读 |
| evidence_adoption.py、evidence_annotations.py、result_corrections.py | schema6不支持的历史/更正写入在写前拒绝；事实说明更正如需启用，必须设计成追加注解并使相关判断待审 | 首批不冒充兼容所有复合链，不通过伪造schema降级调用旧writer |
| check_runs.py、check_identity.py、project.py | 复用现有事实、范围和进程保护；不改物理执行单元 | 不删除全局扫描和最新attempt保护 |
| regression_execution.py、regression_continuity.py、module_context.py | 保持自身验证义务，组合交付时检查当前结果；遇到schema6读取必须显式支持或准备前拒绝 | 不声称主张重构已解决设备/模块过期 |

所有直接读取verification/claim-review的脚本、专业入口、参考规范和测试都需登记在开发前的读写清单。上表是已调查的最小集合，不是承诺只改这些文件。未完成参与读者兼容不得prepare真实需求。

## 7. 冻结、并发与提交模型

事实、判断及当前指针尽量保持在现有verification.json的一次原子替换中；生成视图与claim-review组合不是第二权威，失败可重建。prepare、capture/apply沿用既有文件锁/工作区执行锁和写前后身份核对，固定锁顺序以避免死锁。新writer不能绕过no_unfinished；旧代码直接写文件的外部行为不能靠声明禁止，仍需漂移拒绝和宿主协作。

apply必须比较冻结世界输入、原件哈希、主张关系和generation；输入变动、审查部分返回、并发指针变化都无写入拒绝。正负判断同样保存；完全负向事件允许保存但不生成通过。相同冻结输入/同一返回重复apply幂等；同一事实的相反返回不能抢先覆盖负向，需要新证据/权威并记录原因。

若目录/格式转换涉及多文件，prepare先生成完整候选与清单，在任何活动切换前核验；以verification.json中的合同标记作为提交点。切换后旧claim-review文件按带哈希的历史引用保留，新生成组合可重建。中途失败不得把部分新格式交给旧读者；具体文件提交顺序须在实现中用故障注入验证，不能仅宣称跨文件原子。

1. 只读preflight：列出参与宿主/工具、schema、自动合同、活动需求、复合来源、原件/包身份、设备与模块义务、后台进程和未提交改动。列出预期收益及仍会重跑部分。
2. 用户明确批准准备范围；项目级自动合同2准备若尚未完成须单独确认参与范围，不能藏在feature升级里。不迁移所有已结项需求。
3. 为首批支持的活动事实建立精确只读引用与claim key，保存原数据/原review文件哈希与候选。failed/unavailable/not_run原样进入障碍；旧passed/waived不直接变成当前独立supported。
4. 在候选中完成来源关系与初始独立判断，验证新旧视图边界后切换合同。不能通过一次prepare即继承全部旧通过；无法恢复原条件就拒绝并留原项目不动。
5. 新合同激活后，旧活动writer拒绝；所有新读者统一分派，新主张判断不回退到旧context/carry戳。旧schema1–5兼容分支只服务未迁移需求，其继续支持范围与停止策略在发布时明示。
6. 不能保证任意旧二进制遵守新标记。已知旧load_plan会拒绝schema6，但直接改其他JSON的旧脚本仍可能写入；上线前必须更新参与工具并禁止混用，未知读者阻止prepare，而非声称schema号提供万能隔离。
7. 切换前可恢复原备份；切换后产生新事实/判断则不能自动降级。需要显式恢复时保留新增原件，独立核对旧合同能否认证；否则停用当前认证，不能删除事件找回旧绿灯。

每个迁移后的需求只有一个活动写入合同。隔离对照可以双跑，但真实项目不双重记录。被新resolver接管的旧诊断/戳/写入必须在同批停用，不把删除旧分支无限推迟；允许遗留需求只读适配不等于继续给新需求写旧合同。正式版本若实施本设计应按数据与流程变化评估中间位升级（候选0.19.0），最终发布时再确认，不能直接作为0.18.5提示修补。

## 9. 实施拆分与验收

| 批内步骤 | 产物 | 完成条件 |
|---|---|---|
| W1 | 精确schema、读写者清单、旧格式/不支持矩阵和迁移提交点 | 所有活动读者列明；缺一个不可进入真实prepare |
| W2 | claim identity/version与完整变化捕获、统一resolver | 新增/删除/共用约束/歧义不漏；新key不能藏前身失败 |
| W3 | 独立assessment捕获/一次应用与完整交付组合 | 受影响与未知留缺口；未受影响引用有排除证明；无重复事实登记 |
| W4 | 普通路由、全读者接管、旧writer停用 | 状态/审计/终审同结果；无旧fallback和双写 |
| W5 | 故障注入/等价对照、备份恢复、旧读者拒绝 | 正反例过关；新方案更慢或不足也如实记载 |

W1–W4是一个最小可用纵切，不分别发布成永久并行的半套合同。脚本变更按仓库规则完整回归；开发先定向定位再跑最终完整套件，避免为每次测试调试重复全组。没有证据承诺具体工时/模型费用：工作触及多读者，规模明显大于0.18.4；若无法在清楚边界内落地，应缩小支持来源而非省略读者保护。

验收矩阵至少包含：

- 同事实改进度字段：无物理执行、无重复原事实；只更新展示或必要组合。
- 单个AC变化：新版本未获证据前不可通过；经完整差异排除的其他主张不逐行重记/重审原件。
- 无关/相关决定新增：前者有独立排除证明才复用，后者传播；遗漏的新决定一律未知。
- 父陈述或共用限制变化：不能按单AC引用假定局部；至少一个共享影响反例必须让多项待审。
- 共享资源、主题、导航、构建或fixture变化：现有执行身份失效照旧，候选不能借审查省掉必要执行。
- 旧报告/最新失败/部分运行/未结束进程：阻断，不拼不同attempt或找旧绿灯；失败主张换key仍被拦。
- 新断言、旧包、原件损坏、环境不明：不以相同代码或哈希齐全替代覆盖，保持未知/失败。
- AC重排、重复文本、拆分/合并、遗漏活动行：关系有歧义时不继承；最终集合必须完整。
- 旧豁免、新授权范围变化、原批准缺失：不自动移植；无用户产品决定时阻断相关主张。
- 全负向、重复apply、同事实换人改正向、冻结后修改、并发失败：保存负向、幂等/拒绝不丢原件。
- migrate半写、未支持复合源、较旧读者、另一个项目需求未准备：拒绝并可恢复，不修改已结项历史。

## 10. 对照、成本与开发批准范围

使用同一合成仓库、原事实、变化序列和产品主张，保留0.18.4严格基线不篡改；再在另一隔离副本跑候选。不拿不同任务墙钟直接算节省。先验证相同保护目标和能拒绝的反例，再比较物理执行次数、原事实重登记、审阅的实际变化/原件、读写量和总墙钟/维护操作。

新增维护成本包括：首次主张key/权威对齐；首批约十余个入口/读者的接管与长期一致性测试；独立差异审查本身；追加事件增长后的读取/存储；显式迁移和遗留只读适配。当前只有接口清单，不能据此承诺人日或模型费用。一次resolver操作应共享一次输入采集及解析，避免每行重复Git/文件扫描；操作内可复用，跨操作缓存与历史裁剪不在本批，不以持久缓存掩盖输入漂移。若事件增长成为瓶颈需实测再设计，不事先扩大为数据库工程。

分别记录变化捕获/独立审查/序列化/恢复等新增成本，不能只报告少跑的命令。人工时间仅有可靠记录才计，等待与工作分开，并行不相加；模型usage与可归属账单分开，拿不到就未知。按可观测事件验证少一次事实重签或重复登记，不预定节省百分比。保持一次性的成本采集沿现有stage-cost/日志，不新增业务必填成本表。

首批必须通过安全反例并在局部语义变化对照中减少至少一种已确认重复（原事实重登记或重复完整判断），且完整成本如实呈现；如只换字段/位置却原样重复审查，不算优化成立。代码/共享变化仍可能要求整组物理测试，设备回执与模块档案成本未解决不得掩盖。

本设计待批准的是上述一条验收纵切，不包括：检查级执行缓存/输入闭包引擎、设备多观察组合、档案拆分、全仓依赖自动发现、取消独立审查、自动启用项目合同或重验7466/8024/8025。发布、安装和真实项目启用在候选验证后分别核对范围。用户保留的下一UI优化在候选可用后正常试点，不另加一套试点验收；紧急业务可继续现版，不应被工具设计阻塞。

## 11. 未证明的内容

本轮仅做设计与源码核对，没有实现/执行本矩阵。新增协议是否更便宜、能够安全恢复哪些旧材料、真实UI中的净成本、确切开发工时/费用均未测。作者参与此前实现，不是独立认证；如需独立方案审查应明确授权与成本。实现前发现接口不可行或接管范围扩大，应修订设计并说明，不继续靠补例外完成既定结论。
