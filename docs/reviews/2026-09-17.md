# feature-delivery-skill 阶段审查

审查日期：2026-09-17。源码版本：0.4.5；提交：bd0cfc8。范围：维护目标、路线图、Skill 入口、PRD 读取与复核、扫描指纹、修复记录与校验，以及现有回归测试。未修改仓库源码、已安装 Skill 或业务项目。

## 结论

整体仍围绕“把 PRD 转成可追溯、可实现、可验证的需求交付”展开，没有发现近期功能明显背离目标。多来源 PRD、有限扫描备份、选择性 Git 共享和修复记录都有对应的实际诉求。把完整 PRD 版本管理、自动影响传播留到第二阶段是合理的。

主要风险是开发节奏：记录字段与结构校验持续增加，真实需求的完整交付验证仍未完成。当前能证明部分记录结构符合要求，不能据此认定理解准确、任务描述一致、历史修复受到持续保护。文档大部分已如实说明这些限制；下一阶段应补齐小范围契约缺口，并尽快验证实际使用成本。

## 本次证据

- 本次重新运行全套测试：69/69 通过，约 6.17 秒；全部是合成或隔离案例。
- 另以临时功能、临时代码及临时 Git 仓库复现以下边界，不接触真实业务资料。

## 1. 修复记录可引用无关需求的回归测试

性质：可确定的关联校验缺口，建议优先修正。

实现只检查测试 ID 是否在整个功能的任意需求中出现，没有检查是否与本条修复关联的需求、任务相符。隔离复现：修复关联 R-1，却使用仅属于 R-OTHER 的 UT-OTHER，validate_fixes 返回零错误。这不证明测试无效，但当前记录不能解释它为什么覆盖该修复。

建议：要求测试与受影响需求/任务有明确关系；共享端到端测试可以跨需求，但需显式关联或说明覆盖原因。不要仅检查字符串是否存在，也不要错误禁止合理的跨需求回归。

代码定位：skills/dev/core/scripts/fixes.py:110。

## 2. 问题报告缺少明确的非缺陷关闭方式

性质：使用流程缺口，建议优先修正。

当前只支持 reported、investigating、blocked、resolved、verified，功能级 check 要求所有记录 verified。误报、用户撤回、确认符合既有需求、人工发现的重复报告，缺少清楚的处置结果。尝试 dismissed 被判定 invalid status。现状可能促使 Agent 把无需修复的报告勉强写成“已修复并验证”，或者长期保留未关闭状态。

建议：保留原始报告，区分“实际修复并验证”和“有证据地关闭”；按结论要求关闭理由、证据或重复项关联。不能把“暂时无法复现”直接当作“不是缺陷”。无须一次引入复杂状态机。

代码定位：skills/dev/core/scripts/fixes.py:6、122；参考 core/references/fix-workflow.md 的关闭流程。

## 3. 历史修复留存与后续回归保护尚未连接

性质：已实现能力的边界，距用户防复发目标仍有差距；不是 JSON 校验器承诺执行测试而失效。

隔离复现：原代码输出大写，登记 verified 修复；随后将代码改成小写，保持规格与历史修复记录不变。两次结构 check 都返回 FEATURE_VALID。tested_revision 目前只检查非空；不会比较当前代码，也不会自动选择或执行历史修复的回归测试。实际运行相关测试仍可能发现问题，本次复现未声称完整 /dev check 会放过真实失败。

建议：保留“当时已验证”的历史事实，另记录“本次改动是否需要重验、实际覆盖了哪些历史修复”。近期可先让 Agent 在开发和检查前读取相关旧修复、选择回归；自动失效应基于相关范围，避免任意提交使全部修复重新打开。不能宣称 fixes.json 自身能防止复发。

代码定位：skills/dev/core/scripts/fixes.py:108、120；skills/dev/SKILL.md 的 Delivery/Completion。

## 4. PRD 复核保护尚未延伸到子任务内容变化

性质：已有复核范围的限制；与“避免生成子任务后漂移”的目标直接相关。

当前复核摘要覆盖来源、intake 和需求语义，不读取 tasks.json。隔离复现：需求仍要求大写，把子任务标题改成明确要求小写，develop 校验仍通过。校验器核对任务 ID、状态和关联，无法识别这种含义冲突；结构通过不代表子任务与需求一致。

建议：把任务内容变更和任务进度变更分开。任务描述或验收意义变更时，要求局部核对关联需求并记录结果；只更新进度不应重新复核整份 PRD。内容指纹可提示发生变化，仍不能替代语义判断。

代码定位：skills/dev/core/scripts/prd_intake.py:30；skills/dev/core/scripts/validate-feature.py:118。

## 5. 扫描“过期”提示同时存在粗粒度触发与覆盖盲区

性质：已知设计权衡，需要明确使用含义，是否优化取决于真实数据。

隔离复现：只提交未登记的 README 修改，项目指纹仍因 git_head 改变；反过来，修改未登记 Kotlin 源文件但不提交，指纹保持一致。前者可能增加复核次数，后者说明 BASELINE_VALID 不等于所有源码未变化。当前文档已经说明不是完整增量扫描，没有发现新增的完整覆盖承诺。

建议：保持保守检测的同时，未来区分 HEAD 变化、清单变化和登记证据变化，让 Agent 依据实际差异局部复核。不能直接删去 HEAD 来减少提示，否则会失去对部分已提交源码变化的提醒。先收集多次真实扫描的读取范围、耗时和备份数量。

代码定位：skills/dev/core/scripts/project.py:20、33、50、258。

## 6. 校验粒度和记录成本尚缺真实验证

性质：产品设计风险，尚不能认定已过度设计。

任一读取缺口、blocked 需求或未决决策，会阻止整个功能 develop；一条未关闭修复会阻止功能级 check。文档已公开这一限制，也允许独立执行项目检查收集证据。需求越大，越可能出现“小部分待定，整个功能无法继续编码”的摩擦。

PRD 来源、阅读单元、条目、aspects、需求、任务、决策和追溯共同构成记录链。它们有各自用途，但真实新增耗时、重复录入、错误修订成本尚未测量。69 项测试验证了脚本契约，没有证明这些记录的收益超过维护成本。

建议：用一个真实需求按当前规则完成交付；记录澄清次数、填写/复核耗时、修改同步成本、误阻塞次数、真正捕获的偏差。先根据反馈简化重复项，再决定任务级隔离及新增门禁。

## 优先顺序建议

1. 在现有 0.4.5 范围内补修复测试关联与非缺陷关闭规则，增加针对实际缺口的回归。
2. 将历史修复回看、任务内容变化核对作为轻量工作约定试行，不急于实现完整自动影响分析。
3. 以真实新需求跑完整交付并完成已有 PRD 表达差异评估；局部模块需求同时记录保留行为与受影响调用方。
4. 根据复盘结果推进完成条件、任务级隔离和结构化影响面约束；完整 PRD 权威版本及自动传播继续留在第二阶段。
