# 第二批：人工证据适用性与批量登记最小方案（2026-10-18）

状态：**用户已批准方案评审，未批准运行实现、数据合同启用、安装、发布或推送。** 本文是可审阅开发范围，不是当前工具规则。VERSION和Claude安装保持0.17.0；不操作8024/8025业务仓或设备，不改变任何既有结项。

后续接续：用户已批准本批开发及隔离验证；实现与实际结果另见[开发验证](../evaluations/2026-10-18-manual-scope.md)。下文保留评审时的候选及未执行状态，不将拟议矩阵改写成历史通过记录。

依据：[PRODUCT](../../PRODUCT.md)、[8025成本核对](2026-10-18-ogfr-8025-cost-review.md)、[既有失效范围评审](2026-10-17-verification-invalidation-scope-review.md)、A88/A91/A93/A94及ROADMAP的GAP-26/32/34。此前自动执行分离已完成0.17.0，不能重复建设；本批处理人工观察的当前适用性及其重复登记成本。

## 1. 评审结论与首期目标

建议实现一个闭环：**全局变化一次收集 → 批次逐行判断 → 仅登记支持子集的当前适用性 → 统一读者 → 完整终审。** 采用现有evidence_carry入口与verification.json，不新建Skill、常驻服务、第二状态机或人工必填台账。

目标是减少“旧观察仍成立却整轮重观察、每行起一次进程/全局扫描、重复重签历史”。本批不自动证明依赖完整，也不自动将未变化代码或同一包认定为行为无影响。出现新变化时先显示stale及“适用性待判断”，不能直接把这个状态等同必须新执行；经审查后受影响/未知继续缺证据，有据不受影响者引用原观察。

首期限制：同一feature内、当前活动的人工需求/影响行、最新有效观察及其可校验连续延续链。只读/已归档/未授权的feature不自动启用。失败、撤回、waived、不完整原观察、不受支持的旧链不走本路径；涉及退役行/改写验收预期时沿已有解释纠正adoption，不在本批做任意历史选取或多次观察拼装。自动检查、FIX设备回执、豁免重新登记和既有实际观察record命令保持各自职责。

## 2. 三层身份与共享范围判断

| 层 | 保存/核对内容 | 改变后的处理 |
|---|---|---|
| 原观察事实 | 原行/历史位置及摘要、原tested_revision、真实执行/观察时间、方法、材料定位；有连续链时回溯可信原观察 | 不更写、不复制原私有文字、不改成当前测试；原件变化/缺失、后续失败或撤回拒绝延续 |
| 当前行的完整主张 | 原/当前预期、完整父条款及共同约束、相关来源/决定、保留行为、直接/传递依赖、必要环境与最新实际结果 | 同一行文字不变并不充分；真实扩展或相关变化需要新证据，未知不能采用 |
| 当前差异与审查覆盖 | 完整业务树/实际输入、权威记录、证据清单前后变化一次收集；逐行相关性判断引用共享材料 | 任意未覆盖新变化阻止认证；已明确支持的子集可一次登记，其他行仍阻塞整体结项 |

完整父条款和所有全局变化仍供审查，不再用“父条款逐字不同”或“依赖文件有任何字节变化”在审查入口前一律拒绝。共享strings/Analytics/导航文件的无关成员、父条款另一AC的说明允许进入有据审查，但不得按扩展名、注释、assumptions或测试目录白名单免审。构建装配、初始化、资源编号、调用方、环境、mock配置及设备特异风险都可能传递影响。

首次capture收集全部当前活动人工行的清单和变更全集，推导可选择范围；已有权威关联提供候选，Agent只补实际调查依据。没有关联不能推定独立，未归属的决定/来源/全局限制须保持待调查。对有可信原观察的目标给supported/affected/unknown；空白或无合格原观察的行仍未验证。可共享一个变化评估供多行引用，但每行仍须说明完整主张、原证据和反例，不用“一行支持”覆盖整组。

每次新变化不能仅看已列依赖就自动放行：完整变化哨兵必须发现新增路径、未登记源、规则/环境变化。无未审变化且当前主张/引用材料/依赖/审查范围均匹配时才能认证；否则stale并给出具体差异。审查共同输入一次即可，不要求所有行重新执行。初期不自动用符号解析排除同文件增量，也不建立动态依赖发现系统。

## 3. 最小记录与流程设计

候选数据结构复用verification.json：新增一个共享`manual_scope_reviews`事件集合和活动行的`manual_scope_ref`，不另建观察库。字段名为本设计候选，开发时保持同一职责。

- 事件保存feature、冻结输入摘要、差异全集及来源、目标集合、原观察引用、完整主张前后依据、审查者/新上下文声明、逐行判断、支持子集和应用时间；共同材料只存一次。
- 行引用定位共享事件及该行finding，绑定当时最新结果摘要和可校验的原观察链。原history原样保存，不把续用写为新passed，不为每次确认追加一条看似新执行的历史。视图分别显示“原观察状态/时间/包”与“当前适用性及审查时间”；有效引用表现为retained，失败或未知不被覆盖。
- 每个引用都须对应该行最新结果/可信链，不可在出现新failed/unavailable/撤回后绕过新结果挑旧绿灯。新版真实record写入新结果时清除或使旧current引用无效；共享旧事件保留历史。
- 新格式候选为verification schema 5及feature级`manual_scope_contract: 1`。它可独立于execution_contract=2启用：自动检查仍可为legacy或新模式。schema4当前必须绑定执行模式2，故不能冒用4或在旧schema中偷偷追加旧reader忽略的新权威字段。
- 旧schema1～4不自动改写。显式feature准备只声明新合同、初始化空集合，不使任何行通过，不发设备/命令；首次逐批采用才形成当前适用性。新版读取旧历史，旧0.17.0必须明确拒绝5；不得删字段降级。schema5下既有correction/adoption/annotation/check映射都要保持可读及不降级。

候选入口在现有evidence_carry内提供batch capture/apply，继续由普通Verify按需调用，不再增加用户必须记住的阶段。既有carry/annotation/adoption/设备continuity按原格式保留，新引用不反过来伪装旧receipt。一般描述勘误和隐私注解优先沿已有路径；新格式若与某项历史链暂不兼容，应明确拒绝该操作，不转换状态绕过。

执行顺序：

1. 普通Verify核对当前需求权威、授权、最新失败/撤回、模块/范围、所需原观察与材料。静态核查不强制要求APK；设备/UI观察才核对它所需的包、运行方式和环境。原件或旧合同欠缺时按现有出处恢复规则处理，不补造身份。
2. 使用一次共享读取上下文，冻结当前plan、完整语义、代码/索引/实际工作区、来源/证据清单及目标。复用既有实际字节检查；业务输入不干净时capture拒绝，status只报告过期，不强迫执行检查或提交。保留测试版本/保存合同版本/当前审查版本的区别。
3. 一位或按实际范围拆分的新上下文审查者，在同一批材料中逐行判断；不为每行强制新Agent，也不再加普通Verify之外的人审。拆分组须同一快照，结果明确覆盖目标，无缺失/重复/矛盾。fresh字段是声明，不是密码学独立证明。
4. 持有既有feature非阻塞plan锁，检查完整review结构、目标覆盖及全部输入。partial/unknown是合法负面结果，保持缺口；只有明确选择且supported的子集可应用。输入/引用损坏、审查缺项、并发变化时整批零写入，不先写几行。
5. 共享事件及支持行引用一次原子保存verification.json，之后render一次视图。重复应用同一有效review幂等成功；重新capture同一原观察/相同当前依据不增加历史或重复事件。新fresh观察和其真实时间不通过这条批次命令伪造。
6. audit、status、Verify输入、报告草稿和最终claim review通过同一适用性读取器获取结果。任一最新失败、未审差异或全局未决仍阻塞。完整终审对当前全部活动行进行，不拼接历史终审结论；scope review不是第二份整体验收。

## 4. 如何避免再次被共享摘要拖回原处

冻结输入与持续有效性分开：capture→apply对审查所需语义、输入、plan和目标做前后复核；应用后的当前性由原观察链、每行完整主张及有效范围事件共同决定。不能直接把整个原始JSON序列化摘要同时当作所有行永久有效性的唯一判断。

- 已定义的feature生命周期状态/任务进度由既有全局门禁实时检查，不作为行为语义。即使这些进度变化不重签人工观察，也不能绕过归档/修订/未完成任务等控制。自由文本status_note、决策说明、source状态和不认识的新增字段不自动当进度忽略；有潜在语义的变化仍需范围核对。
- 任何新的未审业务/权威变化都要进入差异判断，旧行引用不能偷偷忽略。scope事件保留完整历史冻结输入用于追溯；后续适用事件可确认既有支持子集，无需重签或复制旧执行。初期仍可能需要一次批量范围审查，不承诺全自动只定位少数行。
- 不因另一条无关结果登记而重算全仓、重记所有旧行。读取上下文仅在一次调用内复用，保存前重新核对关键输入；不做跨命令长寿命cache，不能由缓存掩盖移动输入。
- 支持材料精确引用，新增证据清单变化先判断性质。已有archive/annotation可用时复用；相关原件变化需重审，未知附加材料不能自动排除。隐私原文只存原位置，事件存引用；不手改绑定摘要。

## 5. 预计触达范围与明确排除

| 范围 | 最小改动职责 |
|---|---|
| evidence_carry.py及一个内部共享scope解析模块（如确有必要） | 共享capture、逐行判断验证、显式支持子集、引用/原始链、幂等apply；不做新平台/新Skill |
| verification.py | schema5、feature准备、批次读写、有效状态及当前性、旧行/新真实record行为；全局资格不减 |
| evidence_annotations/adoption/result_corrections | schema5不降级、新引用可用边界；复用已有语义，不新做纠错系统 |
| claim_review、audit-delivery、validate-feature/revise、feature-status、stage_view、verify-inputs、archive-preflight及生成视图 | 同一解析器/全局未知/原执行身份和新适用性提示；不能只有写端理解新格式 |
| regression_continuity / quality check | 原路径不重建；只核对若读取schema5是否需兼容，新设备回执/自动执行合同不改 |
| references、usage、测试 | 入口、旧reader拒绝、操作/回退、反例和实际指标一起验证 |

排除：通用观察拼装、跨需求借证据、随意选较早历史、自动给未知依赖补完整声明、全局自动免测、任意字段白名单、增量终审缓存、批次重新制造设备执行、自动重试、自动推送/业务迁移和历史隐私大清理。新真实观察的通用record-batch另行需要时评审，本批先消除适用性重复登记，不扩成所有记录重写。

## 6. 拟议验收矩阵（未执行）

| 场景 | 必须成立的结果 |
|---|---|
| 新增测试，原被测包不变、运行/依赖经审查确无影响 | 一次批次审查可使原观察适用；原包/时间/history字节不改，无设备执行；仍不替新增测试免门禁 |
| 注释或父条款另一AC说明变化 | 允许进入完整审查；有据独立可支持，实际共同约束变化则affected/unknown，不按字段/扩展名自动免测 |
| 预填赋值/返回取消接线、共享初始化/资源覆盖改变 | 原观察不足时拒绝支持，要求具体新证据；仅本文件未改不能放行 |
| 取消测试对错误实现同样通过 | 留partial，不以测试名/退出0认证分辨力 |
| 真正的新决定/全局约束、遗漏依赖或新增未知输入 | 相关/未知行阻断；无明确范围不能将其他行自动判独立 |
| 新失败/撤回、原件缺失/变更、身份错误、未知三星设备机制 | 不挑旧绿灯；缺包只阻断需要该包的观察，不给静态检查加设备义务 |
| 后续进度/另一行结果更新 | 生命周期/未决照常检查；无行为变化不追加原观察history、不重复全仓读取或全部行重签 |
| 逐行supported/affected/unknown混合 | 结构完整时只保存显式支持子集，其他缺口及全局阻塞仍可见；保存一个event，不把整批视为通过 |
| 46行共享上下文、同一review重复/重新capture | 共用一次快照、一次保存/视图；幂等，无重复历史，不按行重复起进程扫描同一全仓 |
| 捕获后语义/源/代码/plan并发改变或两个apply竞争 | 零覆盖他人修改；移动/冲突拒绝，旧事实保留；无自动副作用重试 |
| schema1～4原历史，新5与legacy/模式2组合、旧0.17 reader | 旧历史不批量升级，启用后明确拒绝旧reader；现有adoption/correction/check/device路径不降级、不漏引用 |
| status、audit、生成视图、最终review输入 | 结果一致，区分观察与适用性；partial/未知/实际失败不能complete，终审仍覆盖当前全体主张 |

确定性测试用合成fixture及正反例，保留失败。运行脚本变更后完整回归、安装/升级/旧reader核对；再安排已授权新上下文语义正反例的宿主演练，不把手写review JSON当作实际独立审查。现阶段没有派Agent、运行该矩阵或测得省时。

## 7. 对照、成本与发布条件

同输入合成对照使用固定0.17.0发布树与新候选，固定原观察/包/完整合同、变化序列、目标集和审查返回。分别记录拒绝原因、实际设备/命令次数、snapshot/读取次数、保存及history增量、登记时间；“旧工具拒绝”只说明旧合同，不等同证明业务必须重测。另用同一冻结材料的原生正反例检验语义采用，不用复用作者结论代替宿主行为。

工程维护成本：schema5与两种自动模式组合、全读者、旧链/隐私注解兼容、全局变化覆盖、索引/原件完整性、并发/幂等及一次性读取上下文。成本应与减少的物理观察/逐行重登记分开报告。只用小样本本地运行秒数不能推算Android/人时；模型实际费用取不到就未测，不按2,792,616 tokens直接换钱，不给节省百分比。

原生演练须在获准开发后完成；真实试点另定，不将8025回溯重验作成新版成功样本。若候选允许依赖漏报或新失败被旧支持覆盖、必须新建平行账本、全读者/旧reader拒绝不齐备，停止交付该候选；可缩为只展示差异的设计结果，但不得以减少哈希校验补齐。若scope审查实际比定向重测贵，明确报告并允许选择定向重测，不强迫走延续。

新增数据合同若最终实现并验证，应按MAINTAINER中间位政策选择版本；本设计不预先发布0.18.0。启用按feature显式授权，新旧格式不静默互换；启用后不能仅降级安装继续认证，新数据保留而旧工具拒绝，逆向迁移不在本批。发布/安装与业务启用分别需要明确范围批准。

## 8. 建议批准的最小开发范围

建议将“批次scope事件+原观察引用、完整差异/逐行判断、schema及全读者、并发幂等、合成对照/宿主正反例/隔离安装”作为一次闭环批准，不能只开发写端或删manual全局摘要就安装。观察事实的执行/新失败、产品权威、完整终审、设备continuity及自动执行保持原边界。本轮只形成评审，8025统计/版本补充可以异步核对，不作为已确认机制设计的等待条件；8024仍独立等后端。
