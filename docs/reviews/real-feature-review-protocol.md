# 真实需求的一次性只读复核

维护准备：2026-10-14；本次观察版本固定为0.13.3（源码提交28baf10）。这是维护复盘口径，不是安装到业务会话的新规则、验收门禁或新表单。CC在开发期间继续原工作；不为本文件更新安装、重载上下文或追补记录。仅在当前工作项结项/明确停在阻塞后执行一次，只整理既有材料。

## 先确定本次观察对象

从当前需求记录取得ID、项目、分支、起点、交付代码与记录提交，注明实际取证时点。分清新建需求、旧需求修订、缺陷修复、纯外部配置，不能把同一需求的多次修订算作多笔独立需求。读取feature.workflow_version：新建v6才能验证v6完成前复核的自然采用；v5旧单不为评估迁移或强制新增记录。

实际加载版本用会话载入记录和安装清单的必要字段作证；不要把参考文档标题当安装版本，也不要把后来安装的版本倒推为全程使用。安装文件一致只是字节证据，不等于当前上下文确实重载。无法确认的轮次标未知。

## 一次收齐六部分

| 部分 | 读取及最小输出 | 判断边界 |
|---|---|---|
| 1. 身份与最终状态 | 当前需求/基线版本、代码/记录提交、报告路径、已有交付/check/audit结果及其截点 | 历史交付与当前HEAD分别说明；merge后不自动重开完整旧验收 |
| 2. 本轮代码与任务 | 实际改动模块/文件范围、任务与提交对应；配置任务明确零本地代码 | 不把记录提交称为实现，也不把所有历史提交算成本轮开发 |
| 3. Test→Verify证据 | 门禁、门禁外设备自动、Agent/用户观察、静态审阅、保留、未验证分别计数并给出处；变更条款与断言是否完整对应 | manual字段不等于人测试；编译/安装成功、截图、共享函数或近似前提不能替代完整行为覆盖 |
| 4. 负向与过期边界 | 对本轮受影响的异步负向断言核对触发、观察者、对象、窗口；旧证据记录原tested_revision和reviewed_revision及关联勘误 | 区分未触发/尚未出现/真正移除；跳过/零执行不计通过；查看stale不要求整轮重测 |
| 5. 自动接续与失败 | 按时间列实际暂停、必要选择、用户提醒下一步、失败/修复/复测、通过撤回；新v6给claim-review及真实新上下文派发出处 | Agent自述或independent_context字段不独立证明派发；16条carry审查不等于整项完成前复核；有据产品/权限/资料阻塞不是流程失败 |
| 6. 成本与残余范围 | 按下节记录可得时间、实际重复运行、记录维护、人工介入、usage来源及未知；结项限制/设备副作用 | 缺数据不阻断复盘或业务交付，不把最终绿灯消掉历史误结项，不算同需求双跑收益 |

先用现有简短报告、current结果和精确路径恢复；不把全部sources、旧历史、整份大回执复制到上下文。对变更/高风险或有矛盾的条款回读完整父条款、实际断言和必要原始产物；省略不证明无关。摘要输出保留上述六部分及具体失败/证据缺口，不必粘贴每条历史。缺来源只写缺什么；没有问题不制造额外检查或让人填表。

本次只读复盘不修改业务记录/状态、补登记、运行构建/测试、操作设备、提交/推送、联系团队。现有status等只读查询可按必要范围使用并标注为本次读取，不能称旧质量门刚刚执行。已有检查记录足以先核对时，不重复执行check/audit。发现越证据结论先指出对应行/来源/最小缺口；后续修正是独立授权动作，不能为了输出好看当场改成通过。资料分享只选必要片段并脱敏，不回显账号/设备原值或令牌。

## 成本读取口径

复用[现有stage-cost说明](../../skills/dev/core/references/stage-cost.md)，不新增登记系统。只读取已经存在的ignored `.agent-workflow/scratch/<ID>/stage-cost.json` 或本轮可信时间/usage出处；不在开发中途开始追补过去的计时，不改验收摘要。没有journal就如实未测量。

| 指标 | 可用来源与输出 | 不能据此声称 |
|---|---|---|
| 本轮总墙钟 | 初始工作请求至交付/阻塞的真实时间戳，注明含等待和时区 | Agent工作时间、CPU时间、Skill记录维护时间 |
| 已计量分类时间 | journal的已闭合intervals，类别test/verify/waiting/record_maintenance及wall_seconds，status的wall_seconds_by_category | 整个需求被完整计量；未记录时段为0 |
| 活跃/遗漏时段 | active非空、未覆盖的开始/结束、不可用clock信息 | 活跃计时已完成；最后状态时刻等于实际结束；错误重启后可反推可靠时长 |
| 重复运行 | 命令、测试/构建对象、代码/证据版本、时间和重跑原因 | 相同命令就是浪费；修复后必要重测与同版本无关重跑应分开 |
| 记录维护 | 独立闭合的record_maintenance区间或可核实操作轨迹 | 首末登记时间差就是纯维护耗时；重新登记等于重新测试 |
| 人工介入 | 实际用户事件/回复及目的，分产品/授权/登录等环境权威与可自行调查/重复问命令 | 多个选项等于多次介入；消息总数等于产品决策数 |
| Token/费用 | 相同明确区间的provider原始usage与来源；保持input/output/cache_read/cache_write、币种和计量范围 | 账号额度、context大小、缓存量或估价等于需求实耗；同一usage重复相加 |

**零与未知**：stage_cost status在没有已闭合区间时可输出interval_count=0和各分类0；这是“无已记录区间”，不是“没有成本”。只有明确覆盖的已完成区间中的真实0才可说零。active未结束、缺文件、缺usage或不完整轨迹都保留未知/未完成。

**合并与并行**：不重叠的同口径区间可以加总为已计量分类时间，但不自动等于总墙钟；并行父/子时长不能直接相加成墙钟。usage按实际请求/调用身份去重，区间须匹配；不把主Agent与子Agent累计上下文重复算计费Token。不确定是否重复时分别列来源并保持总量未测量，不追加假usage。

**三个读法示例**（说明口径，不是真实测量）：

- 无文件或interval_count=0：写“分类耗时未测量”，不能写测试0秒/复核0秒。
- 闭合test=30秒、verify=20秒，另有active waiting：只能写“已计量test30秒/verify20秒，等待未结束”，总墙钟和缺失时段仍未知。
- provider只有一个子Agent的区间费用：仅报该子Agent/区间费用，不能写整个需求成本；账号窗口已用28%不参与计算。

## 第二阶段判定

同一案例分别判断“交付事实成立”“没有错误完成声明”“无需非必要提醒而自然接续”“成本是否可评估”。新v6准确复核/自动接续缺迹或成本未知就保留未验证，不因compile/complete/402项维护回归通过提高成熟度。不同真实需求再次出现连续效果，且覆盖修订/修复及有据旧行为保护，才按[路线图标准](../../ROADMAP.md#delivery-mainline)评估收口；没有同输入对照不报收益百分比。
