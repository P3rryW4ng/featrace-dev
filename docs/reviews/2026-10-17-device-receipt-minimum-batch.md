# 设备回执延续：待批准的最小开发批次

日期：2026-10-17；维护源码基线f38f34b，安装仍0.15.1。用户本轮批准的是收敛设计，**尚未批准本批代码实现、演练、发布或安装**。依据[实际执行审计](../evaluations/2026-10-17-0151-preflight-audit.md)和[完整候选设计](2026-10-17-device-receipt-continuity-design.md)。本页收敛后续范围，不恢复当前Bug的任何结果，不参与后端契约裁决。

## 建议批准的唯一目标

对“当前FIX回归要求不变、原设备执行可靠、改动未影响原行为”的情况，允许基于原设备回执形成**针对当前代码的适用性结论**，避免只因全项目树不同而必然重跑。保留原执行身份，保留当前审查身份，不称新执行。关联GAP-26/33/32，不扩大B1/B2～B4或增加独立Skill。

一个批次内部依次完成：数据/有效性实现 → 全部验收读者接通 → 确定性与原生隔离正反例。三步完成后才能评审发布，不能只上线写入端。当前业务Bug继续按0.15.1规则收尾，不能为了新工具试验反复改变其记录。

## 决定一：允许延续的范围

每批只处理一个feature，显式列出FIX/TEST对，选择该TEST最新原始schema 1实际执行回执。原FIX预期、必需案例、实际断言和设备/环境前提不变；原包、原源码归因和归档材料有据。检查所有后续失败/撤回和矛盾证据，不能只挑一个旧绿灯。第一次不支持从其他延续结论继续延续、不跨feature或拼接多个不完整执行。

| 原/当前差异 | 本批处理 |
|---|---|
| 完整差异落在经调查不影响原断言的功能/测试中 | 进入一批新上下文审查；没有独立性依据不支持 |
| 共享文件增加无关成员/资源key，原断言路径本身未变 | 可进入审查，须逐个变化说明完整diff、原路径/资源/构建装配为何不受影响；不按扩展名或目录自动忽略 |
| 原行为、相关默认值/资源覆盖/初始化/测试装配改变 | affected，原执行不能顶替当前验证 |
| 环境变化、依赖不完整、原机型故障机制不明且无法排除影响 | unknown/partial，执行受影响回归或保持缺口 |
| 相关产品规则改变、缺原包出处、原断言未完整执行 | 拒绝延续，另走正常验证 |

这不是“相关文件一字不能改”规则的改名；可审查同文件中的确凿无关增量，否则无法覆盖当前真实摩擦。但也不实现符号级自动判定/通用依赖图：脚本保证差异完整和冻结当前性，新上下文审查判断行为独立性。FIX-002还经过确认页，FIX-001有三星特异性，**本方案不预先保证它们能免测**。

## 决定二：数据与兼容方式

- 原执行schema 1及其tested_revision/executed_at/command/原装机包身份/原始证据保持不变，不复制私密描述到新回执。
- 现有fixes.json增加一份批次审查事件，各目标历史追加明确类型的延续条目，包含原条目定位和摘要、当前目标及事件引用。使用与原执行不同的receipt版本（拟schema 2），不是把旧execution的tested_revision改成HEAD。字段细节在实现时验证，不能手工摘要迁移。
- 新条目明确区分原execution与review_target；reviewed_at不是executed_at。不装新包也可以形成代码目标的适用性结论，不能表述为“当前设备新包已跑过”。
- 0.15.1/0.15.0的validate_receipt只认schema 1，fixes校验逐条调用它：拟利用未知receipt版本使旧验收/交付认证明确拒绝。必须实测旧命令拒绝，不能仅凭源码推断；不声称任意古老工具或普通JSON读取器都会理解新语义。
- 新读取器兼容旧执行并保留其现行有效性规则，不自动延续、迁移或生成支持结论。新引用错、事件缺失、跨FIX/TEST、篡改或来源撤回均失败。新增存储不能绕过旧设备执行的失败/跳过/身份要求。
- 冻结完整当前证据/需求/决定供审查，绑定相关FIX契约和完整代码目标。无关合同变化须明确调查，不能靠空依赖或不列来源避开。应用前复核完整冻结输入，并原子保存一批显式支持的目标；partial不能被同批支持项带过。

若实现无法让所有认证入口明确拒绝不支持的版本，或存在未读到事件却沿旧绿灯通过的路径，本批不得发布。新共享读写合同预计对应中间位版本；当前不预选版本、不改VERSION。

## 决定三：何时复用比重测合理

不设置固定“先复用再说”的流程。已有完整原件、范围明确且一次批次调查能复用时，才值得尝试。若需要多轮追索包身份/恢复缺失证据/争论故障机制，优先报告定向重测选项，不反复派审查直到得到支持。审查一轮结论不足时，补明确缺失的材料或选择重测；不自动多轮全量复审。

本次CC说设备会话约10～15分钟，是其估计，不作为统一阈值。一轮新上下文审查也可能超过它；功能目标是减少无依据的强制重跑，不保证每次少花时间。新复用不触发额外45行审查；正常最终独立复核仍按既有流程执行，不能取消或宣称局部审查代替终审。

沿现有日志/结果记录批次墙钟、调查/审查轮次、实际设备执行次数、误放行/误阻塞及回退原因，不新增人工计时表。实际模型费用无账单保持未知，子Agent累计上下文不换算计费。首次采用仅报观测，不能从与复杂度不同的8024耗时相比推断节省比例。

## 验收清单：获准实现后执行，目前均未执行

1. **正例A**：无关功能增量、原依赖和原案例完整，人工真实审查支持后，旧设备执行版本/时间/包哈希逐字不变；audit接受该目标，视图说明未重跑。
2. **正例B**：同一资源文件新增无关key，机器不自动放行，审查给完整差异/相关资源依据后可支持。不能仅以“strings新增”固定白名单通过。
3. **反例A**：同文件改了原key或资源覆盖/全局初始化，审查必须affected/unknown；相关代码改变后，即使旧案例曾绿也不能沿用。
4. **反例B**：最新失败/撤回、缺包来源、前缀哈希不足、案例缺漏、只编译/跳过、原测试装配变动，均拒绝或保持明确缺口。
5. **身份与事务**：脏业务树/读失败、证据篡改、冻结后或应用中漂移、错feature/FIX/TEST、循环/悬空引用、重复应用均有明确拒绝及无半写状态；支持子集必须显式选择并重新核对冻结内容。
6. **合同**：无关决策变化可调查而非自动受影响；当前FIX预期/必须案例改变则不能用老观察补齐新要求。不能手改历史或通过删除依赖制造资格。
7. **兼容与所有读者**：旧执行仍正常；旧0.15.1/0.15.0验收和交付认证拒绝新条目；新审计、fix校验、render/status、阶段视图和终审对有效/过期/缺失事件一致。原执行、共享事件和当前目标任一变化须能检测。
8. **原生演练**：在隔离合成项目，给新上下文审查真实的同文件无关增量和隐藏全局影响两例，不预设结论；再以实际产物验证应用及审计。只写fixture supported字符串不能证明这一项。
9. **回归与安装**：脚本变化后跑完整回归，关联差异与运行输入，隔离安装/旧包备份及新旧reader验证；不在正在等待的业务仓测试新格式。
10. **发布边界**：按实际数据合同选择版本，选择不含未批准运行改动的发布包。安装到CC及真实采用另行明确范围，不能因本批代码完成直接升级或恢复业务状态。

## 成本与退出条件

新增成本：一个新回执类型、一个共享批次事件、原件引用/冻结的验证、所有认证读者兼容与长期回归；同文件语义审查仍是Agent成本，不能靠哈希消除。当前不能可信估人天或费用，不用“最小”暗示几行代码。

只有确定性拒绝、读者兼容、原生正反例及完整回归全部通过，才形成可发布候选；功能实现不等于本批真实省时，更不等于第二阶段完成。若该复杂度无法换来可证明的适用性路径，可停止在候选、不发布，继续采用已授权的定向重测；不得靠放松未知/相关项的判定来达成复用率。
