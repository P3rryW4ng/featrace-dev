# 合同10最小调整方案：检查结果适用性与未决评审发现

状态：2026-11-09方案获用户明确批准；2026-11-10实施与候选验证完成。正式版本仍0.33.3／合同9。用户已要求设计并完成调整；用户已批准本方案开发与验证，批准范围不包括发布。不推送、发布、安装或修改业务任务。

依据：[定向机制评审](../reviews/2026-11-09-execution-assessment-review.md)。保护目标不变：真实运行、原失败、产品权威、适用授权和证据来源不因提效失真。保留当前任务架构、有界存储、宿主压缩及项目现有工具，不增加常驻Agent、永久事件库或新的业务文档体系。

## 1. 选定边界

实施两个局部替换，放在同一个新合同内。先实现未决发现与处置，再实现检查适用性，最后统一核对读者与清理。已有“所有检查必须有当前运行”分支替换为按预先声明的证据要求判断；已有“partial被supported无条件覆盖”分支替换为当前判断加有限未决发现。运行字节身份不变。

不采用三种捷径：全局剥离注释后计算摘要；删除真实构建依赖；仅在文本里提醒保留partial。注释可能参与生成/门禁，前两种会漏验；第三种不能约束判定覆盖。也不把所有评审轮次永久保存，仅保留负面发现及必要处置依据。

## 2. 未决评审发现与显式处置

继续使用assess登记当前判定。partial/unknown在同一事务中生成不可变finding ID，保存criterion、原判定、原事实ID、当时criterion摘要、理由、时间与真实评审凭据；真实独审仍由宿主提供，不新增“让开发者自己冒充复核”的路径。原运行失败继续归runtime_failures，不能改登记为普通评审发现来弱化。

发现按criterion阻塞后续supported和close。partial之后再写supported、改标准、删标准、改review标签、延期或换ID，都不能默默消除未决发现。相同登记意图重试返回原ID，避免生成重复发现；有不同内容才新增。

新增一个处置入口，要求明确finding ID、类型、理由与证据引用：

- addressed：用当前适用事实/检查及必要复核说明原缺口已处理。若原发现来自独审，处置需要真实独审依据；原发现和原件不改。
- judgment_error：保留原判断，提供可核对的纠正依据。独审原判断的纠正须能追溯同一真实评审上下文及原事实/权威，不能通过换人或给原事实改时间来洗掉。
- deferred：只通过现有整条承诺defer及真实产品授权/存活交接处理；不增加第二套延期命令。撤销延期后，仍未addressed的发现恢复阻塞。

新发现、执行失败、产品未知各自保留原保护，不互相抵消。处置后再出现的新变化照现有摘要失效规则重新判断；撤回处置支持事实或来源变化时，处置不再适用，发现重新阻塞。支持结论不能代替处置。

数量使用现有任务预算约束，新增明确上限64个发现、每个最多8条处置；未决/已引用原件不可prune。上限不足时拒绝，不静默淘汰。保留期与现有任务相同，不永久保存。查询分页，不向主上下文倾倒全部历史。

## 3. 显式检查适用性，不冒充重新执行

现有run保持按原字节、命令、工具、环境、权限执行或精确复用。输入变化后run仍不会返回旧执行为“当前已跑”。

计划给检查增加证据要求，缺省为current_run；只有确实允许以旧运行加当前适用性分析证明的检查，才显式选applicable_result并说明依据。项目/用户要求当前运行、真实当前环境检查仍只能current_run。工具不能自动理解自然语言规则，Agent须调查具体来源，来源变化使采用失效。

新增check-adopt，接受同任务原成功执行ID、当前静态分析事实、理由及被覆盖的标准。生成独立application，不改executions指针、旧执行输入摘要、原时间或日志。采用只对选定检查及其完整covers集合成立，不把单场景分析推广至整个组合检查。

资格条件：

1. 原执行成功且日志/关联结果产物仍完整，原命令/真实输入身份可恢复；实际测试结果沿用仍需要原producer及原产物，不把命令退出码当作测试断言。
2. 仅已声明文件内容变化可进入适用性判断；命令、工具/协议、环境、依赖成员集合、相关约束或来源改变，拒绝此最小路径。输入清单缩小不能使失效结果可用。
3. 当前分析明确列出完整差异、受影响调用/生成/文本检查、原断言为何仍覆盖；由Agent作语义判断，工具只验证绑定与完整性，不自动认证“注释无影响”。
4. 该检查没有更新的failed/unavailable尝试，相关标准没有未解决运行失败、评审发现或未知。current/live时效声明及过期产物不允许采用。
5. 当前计划、代码身份、分析事实、来源或原产物再次变化，application失效；不能application链式采用、跨任务采用或恢复旧许可。

计划中的proof显式使用applicable_command表示历史命令加分析足以支撑；command继续只表示当前精确适用命令。使用者不能为了结项临时把强制当前检查换为较弱证明。必要独审仍审最终证据组合。

status/close在applicable_result检查下允许完整有效application满足该检查；回执与诊断明确分别报告executed、exact_reuse和adopted，不改变事实类别或声称新执行。run无论application存在与否仍遵守真实执行规则，采用本身不授予运行许可。

该路径增加分析成本，只在明显低于针对性重跑且证据充分时使用；便宜的定向重跑仍是正常选择。不能承诺F14原9次执行全部可以省掉，需先核对各检查的实际保护目标。

## 4. 参与入口与退出分支

| 范围 | 必须同步的实现 |
|---|---|
| 计划/加载 | 新字段及上限、结构与引用校验；缺省保守，未知格式拒绝；新合同号 |
| 执行与适用性 | run/执行身份保持；check-adopt、fact_available、selected_support、check诊断新增显式采用路径 |
| 评审 | assess原子登记发现；处置入口；真实provenance及原件保全；review-input展示未决发现 |
| 交付 | view/close对发现和采用的统一判定；原“任何旧成功可替代”路径不引入 |
| 生命周期 | correct保留原判断/发现/处置；defer与retire交接包含未决发现；prune/cleanup共用引用闭包 |
| 查询/预算 | detail/storage分页及所有采用/发现引用的可见性；超限不删原件 |
| 指引与图解 | SKILL、task-workflow、Android PROFILE、usage、模块图和维护说明按实际行为同步 |

删除/替换的是assess覆盖负面却不留处置、view无区分要求所有检查精确当前这两条分支。task_storage布局、运行失败规则、权限机制和隐私模块无需重构。尽量在已有adoption/failures职责内组织，若拆小文件只为避免循环依赖，不建立另一个流程内核。

## 5. 设计时的验证与反例要求（实际结果见文末）

未决发现：partial/unknown→supported无处置拒绝；重复登记幂等；错误/损坏/伪造provenance拒绝；新支持不能冲掉旧发现；改名删标准/换标签不能绕过；处置证据漂移恢复阻塞；独审身份更正只改身份；延期需真授权且交接保留；retire不算交付；prune/清理保护所有原件和间接引用。

检查采用：合成无行为变化可采用且真实执行计数不增加；原运行ID/时间/摘要不变；后续变化使采用失效；运行失败/不可用/当前门禁/环境过期/产物损坏/成员变化/工具变化/未知/缺原producer均拒绝；不能command-adopt偷换新运行；强制检查仍挡结项。代码语义变化不能由“注释”标记自动放行。

端到端：从begin到close完成有限采用与发现处置；读者显示一致；更正与清理在相同引用图上验证；失败、中断、预算不足不产生半写状态。脚本改动后跑完整当前套件，再按失败/具体新改动决定必要补验，不重复刷次数。

## 实施细化

采用资格保留原执行的check/criteria依据摘要，并增加输入成员/类型/执行位和外部内容摘要，不保存全仓清单。只有预先选applicable_result的原执行可采用，后改模式不能倒签资格。精确复用仍由run的reused输出标明；回执使用exact_result与adopted，不伪造未持久记录的复用次数。原测试结果需要单独运行观察与producer，检查采用不代替它。

发现处置的依据限定为当前直接事实，避免“尚未处置发现→采用→借采用处置发现”的循环。收窄为明确的最小路径，必要时定向执行；不承诺每种历史结果均可沿用。
