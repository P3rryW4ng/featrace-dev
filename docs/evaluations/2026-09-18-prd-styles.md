# PRD 表达差异样例评估（2026-09-18）

执行方使用 Claude Fable 5 和当时安装的 `/dev` 0.4.8，8 份合成 Markdown 样例分别在独立临时工作区和新上下文中处理；执行样例的 Agent 未取得 `expectations.json`。维护者对照原始样例、预期与生成需求/intake 判读，报告 **8/8 语义通过**，四类 forbidden 错误未命中。此结果仅代表这一模型、这一次、这套样例；未给出通用准确率，也未验证 Word/PDF/OCR 或业务真机。

| 范围 | 结果与边界 |
|---|---|
| formal / colloquial / reordered-table | 每日三次、会员例外、冻结优先、时区未指定四项业务不变量保留，表述/编号可不同。 |
| per-request | 单次三条没有与每日次数合并；未规定每日次数保持待定。 |
| only-admin / also-admin | “仅”与“也可”的排他性区分正确；未提及角色未被臆造。 |
| example-not-rule | “苹果”保留为例子，超时/重试保持未知。 |
| unreadable-diagram | 缺失图片登记读取缺口，没有发明冻结流程。 |

**可复核证据**：8 份生成工件在执行时存在于隔离临时目录；原始总结报告已另存给项目所有者。本仓库不保存个人安装路径和临时目录绝对路径。5 份工件有完整 review digest；per-request、only-admin、unreadable-diagram 这 3 份如实保留待决条目或不可读单元，未登记完整 review。执行方报告这些样例仍通过 draft 结构检查；语义通过不表示可进入 develop/check。评估总结将“撞上门禁”和“完整登记”并列叙述，容易混淆；此处按工件状态分别记录。

**确认的流程摩擦**：`review-prd.py` 在 0.4.8 固定用 develop 严格度登记评审；待决条目和缺图会使局部已读内容无法留一份明确标为 draft 的评审。Agent 出现两类做法：把歧义记录进待决决策并映射已知部分，或留下待决条目使登记失败。0.4.9 增加显式 `--stage draft`，如实保留待决与读取缺口并记录已读部分，仍拒绝未完成事项通过 develop/check。修正仅经合成回归验证，尚未重新跑独立 Agent 评估，不能把 0.4.8 的行为结果冒称为 0.4.9 的新结果。

第一阶段仍需要真实业务案例的最终版本真机验收、修复证据和报告对齐；此评估只满足表达差异样例这一项。
