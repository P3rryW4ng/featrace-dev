# GAP-06：交付流程成本的轻量测量口径

状态：2026-09-30 建立测量方法并登记现有合成样本；**真实需求的记录成本、净收益仍未测量**。本文件是维护者的评估方法，不是安装版 Skill 的新表单或交付门禁。需求按原有 `/dev` 流程推进，不要求为了对照重复开发。

## 测量单位与来源

以一次需求的连续交付为主单位；发生获批 PRD 修订或修复时，另记该段的起止和触发原因，再合并计算端到端成本。每段只保存能够核对的版本、开始/结束时间、工具用量来源、结果和额外人工介入。等待用户、设备、外部系统的时间与 Agent 实际运行时间分列；时段重叠时不相加。

| 要回答的问题 | 最小证据 | 不能推断的内容 |
|---|---|---|
| 交付花了多久 | 会话或阶段起止时间、运行器报告的耗时；注明墙钟/运行时间的口径 | 没有分段时间戳时，不倒推出记录填写耗时 |
| Agent 花了多少计算资源 | 宿主提供的 Token、缓存读写、工具调用和费用估计；记录来源与计价口径 | Token 数不等于实际付费，费用估计不等于账单 |
| 流程维护增加了什么 | 仅在可辨认时记录资料重复读取、同一事实重复填写、记录修订、误阻塞及对应起止/调用证据 | 不能由写入次数直接换算为耗时或判定为无用工作 |
| 人做了什么 | 只记介入原因、是否必须由人裁决、人工实际投入时间（若有计时） | 未计时写“未测量”，不按消息条数估算工时 |
| 流程避免或漏出了什么 | 被提前发现的具体偏差及其证据、最终验收漏出、返工与复测结果 | 合成注入故障不计作自然需求的发现率或节省工时 |

来源等级统一标明为**实测**（原始时间/用量/运行记录）、**由实测计算**（注明公式）、**人工估计**（注明依据）、**未测量**。不把这四类混写成一个精确数字。原始提示、用量和操作记录可能含项目或账户信息；共享前脱敏，只保留复核所需的摘要与引用。

## 下一次真实需求怎么记录

1. 开始时只记需求 ID、使用的 Skill 安装版本、代码基线和起点时间；结束时记交付点、终点时间、实际质量与人工验收结果。已有日志可提供的值直接引用，不让开发者重复填表。
2. 每次**必须停下来找人**时，记一句原因及结果：产品权威、资料/权限缺口、人工验收，或本可由 Agent 自行调查的非必要介入。等待与实际处理时间分开；未计时留空。
3. 结束后从操作轨迹回看记录维护：哪些是必需的来源、决策和证据核对，哪些属于相同事实重复录入、过期后重做或误阻塞。只有轨迹有分段时间时才汇总分钟数；否则报告次数、位置和“时间未测量”。
4. 同时核对被 Skill 提前发现的错误、最终漏出的错误和修复返工。对一个候选简化，先写明要删掉哪项重复操作、哪些证据必须继续保留，再在下一次适用案例核对成本与遗漏。独立 Verify、拆分 Skill 或更多并行 Worker 的收益须另有可比证据，不能由一次流程计数推出。

可直接放进**维护者评估报告**的最小记录为：`需求/场景与真实或合成`、`Skill 版本和代码版本`、`起止及等待口径`、`宿主用量来源`、`必要/非必要人工介入`、`重复工作或误阻塞的轨迹位置`、`提前发现/漏出/返工`、`未测量项`、`拟简化的单一步骤及不能丢的证据`。这不是新的 `.agent-workflow` 权威文件，也不要求用户在使用 Skill 时填写。

调用轨迹能定位来源、记录、代码和验证动作，但导出的 `calls.json` 没有可靠的逐调用持续时间；**记录填写/复核分钟数未测量**。维护者设计夹具、注入故障、运行隐藏契约、审计与证据整理的时间也未完整计时，不能并入上表。0.5.35 的 GAP-23 后续复核是单独的合成运行，不加到原三轮。该样本证明可以取得总成本和操作轨迹，也暴露缺失的分段与人工成本；它不能证明真实需求提效或流程过重。

| 观察 | 证据与归类 | 当前判断 |
|---|---|---|
| 第二轮在事件 251、258 两次调用 `verification.py run`；事件 298 又直接调用 `project.py check` | `verification.py run` 的[实现](../../skills/dev/core/scripts/verification.py)内部会调用 `project.py check` 并写质量报告。因此轨迹中有三次项目质量门执行入口；251→258 之间修正了 R-ATOMIC:5 的覆盖说明 | 258 的重跑与记录修正相关，不能直接删。298 是**可进一步调查的重复执行候选**：258 后到 298 前没有新的业务代码编辑，只有证据/任务记录处理；仍需核对当时报告是否继续有效，不能仅凭轨迹断言第二次检查多余 |
| 第三轮在事件 266 把 FIX-001 证据写入 T-2 的任务字段；事件 334 尝试移除，346 逐字恢复任务文件 | [第三轮复盘](evidence/2026-09-30-storeflow/round3/assessment.md)记载这使任务语义复核过期；334 留下空字段，346 才恢复原摘要 | 一次**有证据的记录返工**。属于 Agent 选择了错误的记录位置，不等于任务语义门禁本身是误阻塞；次数与轨迹可核，额外分钟数未测量 |
| 第二轮事件 144、152、162 围绕 mutation helper 重试 | [第二轮复盘](evidence/2026-09-30-storeflow/round2/assessment.md)记载自写 helper 曾错误报告变体存活，随后用核对过的替换方式重测 | 这是临时测试方法的返工，不归为 Skill 必需记录成本；不能拿它证明删减权威记录有收益 |
| 三轮开始时重新读取阶段规则、状态与来源 | 各轮是新会话，且第二轮有获批 PRD 修订、第三轮有新故障 | 属于恢复上下文和重新确认权威的必要调查；调用次数不能直接标为冗余 |

目前最清楚的后续测量点是：**一次 `verification.py run` 产生当前质量报告后，是否仍因真实输入变化需要再执行 `project.py check`**。在下一适用真实需求中保存两次检查之间的代码/需求版本、质量报告状态、触发理由和实际用时。若证明报告持续有效且重复执行确无新增证据，再考虑去掉 Agent 的多余调用；保留自动检查、新鲜度核对和失败留史。当前不修改运行规则，也不以一次合成案例估算节省比例。

## 决策边界

首个真实案例先建立成本与收益账，不因为某一轮调用多就删字段。若轨迹指向一个具体且可重复的冗余操作，可做一次**可逆的最小简化**，并用下一适用案例检查是否减少操作且没有放过此前能发现的偏差。真实样本不足时继续标“未测量”；扩大 Skill 拆分、并发和通用自动化仍按 [路线图](../../ROADMAP.md) 的独立完成条件判断。
