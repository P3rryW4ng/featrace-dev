# StoreFlow 跨会话综合隔离演练（2026-09-30）

## 结论

个人安装的 `dev` 0.5.34 在三个**独立原生 Claude Code 会话**中，完成了受控部分开发、获批 PRD 修订后的接续交付，以及一次明确标记的人为回归修复。安装版未被改写；所有代码、记录和临时写入均留在合成项目中。最终项目 32/32 测试、维护者隐藏的 18/18 业务契约、`validate --stage check` 和 `audit-delivery` 均通过。原始 PRD、旧测试断言及既有共享接口保持不变。

这证明链路在本例能够前进，也暴露了两个不能被“绿灯”掩盖的问题：修复后的报告结论仍写着三个“待完成”步骤，虽然它们随后均已完成；Agent 在折扣 mutation 检查中删除了临时副本，失败过程只能靠命令轨迹和描述复核，不能复原副本。前者登记为 GAP-23；后者作为证据留存限制继续观察。本例不证明自然需求的准确率、节省时间、跨机器恢复或双 Worker 分支。

## 证据边界与真实摩擦

- 第一轮没有项目质量报告，旧 v1 运行证据并未先建立；因此本例**没有**验证“已有 quality report 在 v2 apply 后自动失效”。第二轮是新建基线并实跑质量门。不能沿用上一例的失效结论给本例加分。
- 修订语义只改 R-PREVIEW 的 statement 与折扣 AC；原来源和历史保留。第一次提案把单个 AC 写成不被 schema 接受的字段，Agent自行改成完整列表字段。修复轮先被过期模块档案拦住，再因回归候选和误改任务证据字段被拦住；它分别重审、重新同步和逐字恢复任务记录，没有靠手工改摘要放行。
- 第二轮 Deliver 的关键顺序为报告 Write 事件306 → 单独 Read 事件309 → 修订交付登记316 → 完成状态323。第三轮为报告 Write401 → 修订登记404 → 单独 Read407 → 完成状态432。前两者顺序略有不同，但两轮均在完成状态前全文回读，没有同批写读。
- 第三轮报告最终结论仍说“全文回读、修订登记、状态更新”是待办；后续记录证明三步执行了，报告文字却未随之修正。确定性 check/audit 未识别该文义冲突，不能把 `DELIVERY_EVIDENCE_CURRENT` 解读为报告全文无矛盾。后续应找最小收口方式，不应只靠堆叠更多门禁。
- 36 条验证行中 32 条由自动测试支撑，4 条是 Agent 技术检查，**不是**用户验收。会员输入没有运行时类型校验、`Inventory.reserve` 单独调用不具原子性、内存收据没有并发/持久化保护；这些是夹具约定和实现边界，不在本轮冒充已覆盖。
- mutation 过程中两个临时副本被删；且自写 helper 曾错误报告两个折扣变体“存活”，Agent随后用已核对的替换命令重跑并记录失败。临时副本的完整失败现场不可复算，独立黑盒契约和最终代码是更强的结果依据。
- 三轮原生执行墙钟分别为 **431.869、507.479、366.302 秒**，合计 **1305.650 秒（约21分46秒）**；CLI 报告的估计费用分别 **$1.8792、$3.2804、$2.1105**，合计约 **$7.2702**；工具调用分别 36、57、44 次。另有维护者设计夹具、运行隐藏契约、注入故障、审计和整理证据的成本，未完整计时。没有可比的自然项目对照，不能由这些数值推断提效。
