OGFR-7840 曾静默沿用 OGFR-7659 的项目级质量门，先跑了无关检查，直到历史回归测试 ID 未选中才被审计发现。另一次仅重选门禁时，全局 verification digest 让同一代码版本的人工观察整批 stale。项目级配置仍保留单文件，但非空门禁必须显式绑定 `selection_feature_id`；执行器在运行前拒绝错绑，质量报告保存选择摘要，audit 核对它与当前需求及配置的命令合同。`selection_reason` 等解释文字不进入执行摘要，测试命令与 `test_ids` 进入。代理仍要判断哪些检查适用，脚本无法从模块路径自动选对门禁。

新人工结果另存逐项 `evidence_digest`，以需求、决策、影响快照与该行语义为依据，不把质量门的散文或其它行加入。自动门禁仍按当前选择和实跑结果判断；旧人工结果没有新字段时遵守原有全局摘要规则，不批量改签历史。既有非空配置需补需求编号并重选、实跑检查；旧质量报告不视作新版绑定。真机证据另外需要证明装机包对应当前修复，摘要机制不能验证叙述真实性。中间版本号反映这一数据合同变化；源码测试和安装版复检分开记录。

## A70 独立旧功能变更复用现有 Feature 记录（0.8.0 源码，2026-10-10）

用户提出的修改可能落在已存在的代码和业务模块中，却不属于任何已记录的旧需求；突发故障也可能没有可挂载的旧 Feature。要求用户先写完整 PRD 或把它强挂在当前选中需求，会增加无意义准备或污染历史权威。新增 `change` 轻量入口，仍要求产品系统给出的工作项 ID 和用户原始描述，保存在普通 Feature 的来源中；`entry_kind` 只标记创建来源，不新增状态机。原始描述能支持的新增行为才进入已确认要求；故障只证明观察，`FIX` 先为 reported/unclassified，预期与根因需继续调查。与旧需求相关的行为通过历史档案、影响和回归候选关联，不改写无关旧需求；同一 ID 已存在则拒绝初始化。

实现复用 `init-feature.py`、`record-fix.py`、现有 intake、Scope 与验收门禁，不放宽 develop/check，也不让用户指定内部模块。短来源由 Agent 在受授权的项目 scratch 逐字保存，再由 helper 复制为不可变源；辅助命名 `prd-original.*` 是现有格式，不表示整份 PRD 或审批。此入口是新的用户能力，源码 0.8.0 选择中间位；脚本测试不能证明安装版 Agent 自然路由、真实缺陷分类正确或端到端提效，后续按路线图取证。

## A69 外部配置任务按实施方分流（0.7.3，2026-10-10）

OGFR-7659 的 eSIM 目标页修改由后端下发配置实现，客户端无代码改动；但混合 Feature 的既有路由使记录提交和重复客户端质量门看起来像本轮开发。Scope 改为逐任务判定实施方和实际产物：本项目代码任务正常 Build；有据确认的外部配置任务在进入 Build 前醒目告知零代码，输出精确交接，待配置实收并经最小端到端观察后纳入 Verify。质量门按实际变化选择，旧检查仅在快照仍有效时复用；合并或客户端依赖变化另行判断。为避免凭 Agent 自述伪造豁免，本轮不新增 JSON 状态、不放宽空质量门或 audit；独立纯配置 Feature 若没有适用可执行检查，仍如实停 provisional。先用下一真实混合需求验证路由、漏检与成本，再决定是否为纯配置建立受约束的完成契约。

## A68 已结项需求的合并后范围复核（0.7.2，2026-10-10）

真实交付后合并其它代码会让全局质量报告按设计过期，但 `check` 的红灯不等于原需求发生回归。将“原交付版本已完成”与“合并版本重新获交付认证”分开：前者只读盘点原交付 SHA 到当前 HEAD 的路径和工作树改动，Agent 逐项调查真实差异、调用方及共享依赖；有据无关时保留旧 `complete` 和旧被测版本，不重复完整真机验收，也不刷新旧质量报告。相关或未知改动定向复验；若要认证合并版，继续要求该版本适用的质量门及 check/audit。脚本只证明 Git 路径事实，不能自动证明依赖完整或行为无影响。未给任意非工作流提交添加质量报告豁免，避免把旧自动检查冒充新构建结果。当前版本不新增用户命令、第二套完成状态或自动质量门保留字段。

## A67 推断需求与完成状态的权威边界（0.7.1，2026-10-10）

真实需求复核发现一条 `inferred` 需求混合了用户决策已确认的视觉规则与从现有实现推断的旧行为保护，整项需求已完成且逐项有证据。旧规则中“active requirements confirmed against evidence”容易被读成“所有需求状态必须改为 confirmed”，而现有校验器允许 `inferred`；为了改标签而重写需求会使当前验证指纹失效，并产生不必要的构建和人工复验。明确：`inferred` 保留产品归属的不确定性，不能因测试通过而当作用户批准；结项时必须逐项说明来源、现有行为依据、实际验证和未决产品选择。纯旧行为保护有据且不改变产品合同，可以保持 `inferred`；任何未获权威确认的产品可见新规则或变化，仍须澄清并保持 provisional。优先在新需求中把纯保护行为记入 impact，但不为整理旧记录强制迁移。语义辨别仍是 Agent 的职责，校验器不声称自动识别产品意图；本次不增加字段或门禁，不追改历史。

## A66 最后一项任务后自动接续验收与结项（0.7.0，2026-10-10）

产品所有者不希望开发结束后再记住并输入一次 `check` 或“结项”。总路由在已授权的实现链完成最后一项任务后，自动进入普通 Verify；当前需求、来源、质量门、历史回归与人工证据均支持时，按既有 Deliver 顺序保存报告、单独全文回读、登记适用基线、更新状态并复核。任务 `done` 和本地提交只触发准备核对，不能代替验收。证据缺口保持 `provisional`，给出最小明确待补项；用户回报后原链路自动接续。Repair 完成也回到 Verify。状态/帮助/会话激活、明确只读、规划或仅检查请求不触发结项；归档、推送与 PR 仍独立。复用现有权威记录和门禁，不新建命令、字段或第二套完成状态。规则层验证不证明 Agent 在真实需求中总能按此接续，也不宣称 L2 完成。

## A65 专业 Agent 的短消息与完整证据分层（0.6.1，2026-10-10）

Build Worker 和独立 Verify 已有受检查的结构化返回，但面向总路由的自然语言消息没有统一长度与顺序，容易重复日志并掩盖真正的阻塞。两类专家各用五项简短交接（状态、结果、检查或证据、风险或缺口、下一步）；总路由必须读取完整结构化返回和引用，再向用户合并成一份结论。不得缩短 JSON 中的完整发现、补丁或检查记录，不因文字摘要省略失败、过期、未知与重要风险。此改动只约束表达，不新增第二套权威记录、命令或门禁，也不改变 Worker/Verify 的职责。宿主直接展示的工具轨迹无法仅靠 Skill 文案隐藏；真实可读性仍待使用时观察。

## A64 任务提交由总路由在 Build 后逐项完成（0.6.0，2026-10-10）

用户反馈把整项需求的检查和 Git 提交集中在最后，造成长时间等待及难以阅读的合并提交。将本地提交明确为总路由的 Build 任务收尾，而不是 Deliver 完成条件或独立用户命令：每个已完成且能安全隔离的任务，先核对实际补丁、运行其必要检查并更新任务/追溯记录，再以需求/任务 ID 和可观察结果写一笔本地提交；之后继续下一任务。完整质量门、历史回归、人工验收和交付结论仍由 Verify/Deliver 对最终实际版本核对，不为每笔任务提交重复全套检查。若任务之间无法单独暂存、已有他人改动或项目规则禁止自动提交，保留现场并说明具体阻塞；不得把不相关改动裹入提交。

并行 Worker 与外部候选不提交，只有经主项目采用、共享记录串行更新后由总路由逐任务提交。提交不自动推送、建 PR、标 complete 或宣称最终验收。采用本地任务提交作为默认行为会改变用户工作流，故在实际隔离验证后按版本规则提升中间位；不以此宣称真实连续交付里程碑或 L2 已完成。具体顺序见 `skills/dev/core/references/task-commit.md`。

## A63 版本号按交付能力和契约选择，不按发布次数机械递增（2026-10-09）

`0.5.x` 历史把大型内部重组、新专家试点与小修正都放在末位，无法从数字判断变更幅度；不追改已有版本。自 0.5.44 后，既有能力的小修和提示优化升末位，已实现且相应验证的显著用户能力或重要工作流/数据契约升中间位，稳定对外契约成熟后再评审首位。版本选择在发布前给出依据，不能把方向改变、设计提案或合成通过当成成熟能力；中间位也不等于产品 L2 完成。下一次真实连续交付里程碑优先作为 `0.6.0` 候选，但只有到时核对实现、证据、兼容与迁移后才决定。具体发布操作见[维护总览](../../MAINTAINER.md#version-policy)。

## A62 新需求入口分阶段确认必需信息（0.5.44，2026-10-09）

用户明确开始新需求时，统一入口先展示产品编号、可读取 PRD 和模块调查状态。编号是产品给定的工作项身份，不由 Agent 自造；PRD 文档或 HTML 至少有一个可读取来源。缺项只问缺项，未齐前不创建需求或切换当前选择。已有资料齐全时直接走原有 `prd --feature`，不让用户重复输入命令。模块不是前置表单：draft 后先用项目地图、相关代码与调用方提出有证据的 owner/host/provider/consumer/shared 职责，只把真正不清楚的产品归属交给用户确认。复用既有 Scope pending 门禁，不新增平行状态或第二份权威记录；提示本身不证明模块判定正确，也不宣称能自动理解全部 PRD。

## A61 项目地图按证据逐步扩展，并显式呈现未知区域（2026-10-09）

用户确认项目理解应随开发累积成可共享地图，用于跨模块定位、发现地图外问题和同事交接。现有 Gradle 候选、正式模块目录和档案分别覆盖待审结构与已复核知识，但缺少从陌生路径进入地图的直接入口。0.5.41 增加只读路径/字面查询：先区分已登记、待审候选、地图外、目录缺失、路径缺失和候选证据过期，再由 Agent 阅读实际实现、调用方与旧行为。只有来源明确的边界和行为才能更新正式目录/档案；未证实的关系继续留在候选或缺口。模块档案随受影响的交付更新、经审阅由 Git 分享；并行同文件编辑需合并和重新复核。此处不创建自动语义所有权、全量调用图或第二套数据中心。只读定位与状态区分已有合成测试；多人真实采用、漏报/误报、地图维护成本仍待观察。

## A60 Figma 采用局部页面/状态索引与精确身份匹配（2026-10-09）

设计稿可能有多个页面，且同一逻辑页面包含多个状态。只存一个链接会在开发与改稿时丢状态；预先把整个 Figma 文件转写成 JSON 则成本高，未读内容也容易被误写成事实。0.5.41 因此在注册新设计来源后要求按本需求范围登记逻辑页面与状态，关联已读 intake 单元及需求。文件 key + 节点 ID 用于定位已有状态；描述、截图或复制后的新节点只返回候选，由 Agent 比对相关内容，必要时由用户确认。来源摘要绑定的是登记证据文件，不能证明节点内容未变；匹配成功仍需检查新稿、需求含义及受影响实现。未启用索引的旧需求保持兼容。当前无远端自动监听、视觉相似匹配或完整 Figma 枚举能力；真实准确率与成本待下一组合来源需求验证。

## A59 保留行为的按项验收范围（2026-10-08）

CASE-03 说明完整重验可能把纯文案改动扩大为旧导航链路的人工验收。0.5.39 不引入通用静态依赖图或自动语义免测：沿用唯一 verification.json，给需要保护的 `impact` 保留行为登记人工调查过的精确依赖文件与依据。每次真实 diff 先使原证据过期；只有历史实际 `passed`、需求/决策/影响合同未变、变更路径完整复核且与登记依赖不相交时，`retain` 才记录本次范围裁决。旧 `tested_revision` 保留，另记 `reviewed_revision`，状态为 `retained` 而非新的测试通过。自动质量门、失败/豁免、需求变化、依赖变更及关系不明项仍走重测或进一步调查。历史 FIX 候选继续走独立的逐项 disposition，不因本机制自动免测。文件清单的正确性和间接调用影响仍靠 Agent/人工审阅，不能把合成验证冒充真实漏测率或效率收益。

2026-10-09 补充：0.5.39 的[安装版反例](../evaluations/2026-10-09-gap26-installed.md)显示 Agent 找到传递依赖漏登后仍自行例外保留。0.5.40 维持 A59 的数据结构与有据缩小范围目标，但把“发现漏登即未知、补齐依赖并重新观察”明确为不可例外的执行条件；[安装版正反例复检](../evaluations/2026-10-09-gap26-0540.md)通过。脚本仍不能自动证明依赖清单完整，因此真实收益与漏测率继续待测。

## A58 完成审计与历史回归逐项结果的最小门禁（2026-10-08）

[CASE-03](../reviews/2026-10-08-case-03.md)最终交付正确，但曾在过期质量报告上提前标 `complete`，且多条计划回归只做一部分就整体写 `passed`。0.5.38 不增加用户命令或专业 Skill：新建需求的 `workflow_version=4`；Agent 保存并全文回读报告、另一步更新完成状态后，再运行 `validate-feature --stage check`。v4 的完成状态要求非空项目报告，且复用现有 `audit-delivery.py` 确认当前质量证据。失败则撤回完成声明、保留现场与原因。旧工作流不批量重写或追溯套用新门禁。

新建历史回归记录采用 schema v3；每项 `planned_checks` 需一条对应的结果、方法和证据，豁免还要残余风险与批准依据；整体结果须与逐项结果一致。旧 v1/v2 记录仍可读取且同步时不强制升级至 v3。这只验证记录结构和当前摘要，不能证明某项真机观察或测试命令真的发生、断言有效，也不能阻止 Agent 跳过最后一次命令。真实收益与稳定性等待安装版及下一真实需求验证。

## A57 Worker 全文差异检查绑定当前补丁（2026-09-30）

[0.5.36 安装版同输入对照](../evaluations/2026-09-30-build-installed-ab.md)里，两个 Worker 均按顺序派发和返回，但在 `finish` 前只看了 `git diff --stat`；旧文字“read the actual diff”不足以保证全文查看。0.5.37 在现有外部尝试目录新增 `inspect-diff`：使用与 `finish` 相同的私有索引导出完整补丁，输出 `full_diff`，并保存绑定当前补丁、工作区状态和尝试摘要的检查记录。`finish ready` 缺记录或代码随后变化就失败，集成继续验证该记录。`blocked`/`failed` 返回不要求检查记录，避免阻塞诚实失败。

这是对实际轨迹的窄修正，不给 Worker 新增共享记录写权限，也不改变两 Worker 上限。记录证明完整补丁曾被 helper 输出，不证明 Agent 全文看完、理解了语义或候选行为正确；输出截断需补读或阻断。仍需任务检查、集成检查和后续 Verify。新增命令仅是内部 Worker 步骤，用户入口保持 `/dev`。

## A45 显式两任务隔离 Build 最小原型（2026-09-28）

本期不实现通用任务调度、工作区池、自动重试或清理，也不扩大其他专业阶段。原型只提供明确两任务路径；同一时间的 Verify 不与写代码的 worker 并行。合成机制测试与独立 Agent 采用分别记证据，个人 Claude 安装和真实收益另行核对。验证及后续顺序见路线图。

| 总路由 | 读取当前状态，安排阶段与任务依赖，分派执行者，核对返回证据，再决定合并、重验或下一步；不替用户改变产品决策 |
| 专业 Skill | 提供 Requirement、Scope、Build、Verify、Repair、Deliver 的规则；按责任和产物拆分，不按每个命令拆分 |
| 执行 Agent | 在独立上下文中加载所需 Skill，完成明确范围的任务；多个任务可以复用同一个 Build Skill |
| 共享事实与证据层 | 复用现有需求、任务、决策、修订、Fix 和验证记录；后续补版本核对与写入协调，不另造一套需求权威 |
| 独立工作区 | 并行编码时隔离代码修改；合并后仍须集成验证 |

Skill 是工作规则，不是独立进程。拆多个 Skill 可以减少按需读取量；独立上下文需要执行环境提供 Agent 隔离，实际并行能力还依赖主机支持。读取更少不保证细节完整：执行者仍须获得对应需求、接口、调用方、旧行为和测试依据；缺少关键资料时请求补充，不能凭局部上下文猜测。

拟议链路：总路由 → 需求确认 → 影响调查 → 任务依赖分析 → 可独立任务分别交给 Agent + 专业 Skill → 汇总与合并 → 独立 Verify → 交付。存在前置依赖或未定接口的任务按序推进，不能仅因修改文件不同就判定互不影响。

### 冲突与最小协调方案

共享文件夹不自动具备并发安全。需要处理文件冲突、跨文件语义冲突、共享记录覆盖三类问题。不同文件也可能对接口、共享状态或导航作出相反假设；各任务单独通过不证明整体正确。

1. **版本绑定**：分派时明确需求基线、代码起点、允许范围、前置依赖、接口约定和验收目标。需求或接口变化后，总路由重审受影响任务；过期结果不能直接继承通过结论。
2. **有限并行**：检查共享文件、状态及接口依赖后再决定并行资格。出现超范围修改或新依赖时交回总路由重新安排；子 Agent 不自行扩大产品边界。
3. **共享记录单点写入**：子 Agent 返回改动、证据、未解决问题和基线引用；总路由核对当前版本后串行更新权威记录。子 Agent 不同时改主工作区的需求/任务 JSON。历史结果保留，但不冒充当前证据。
4. **代码隔离与集成**：并行 Build 使用独立 Git 工作区或等效隔离；总路由检查差异并合并，针对合并后的代码版本执行适用检查。文件冲突与语义冲突分别调查。
5. **失败与接管**：失败、超时、取消或返回资料不足时保留改动与证据，不自动标为完成；重试前核对已有结果，避免重复合并或覆盖。无法安全推进时保留人工接管入口。

“数据中心”首先指共享事实与写入协调能力，不预设必须引入数据库、服务或分布式平台。具体交接格式与实现工具留待最小演练确定，并兼容已有交付门禁。

### 演进边界

先验证串行专业 Agent 交接，优先独立 Verify；再用两个范围清楚的任务验证并行 Build。比较漏报、误判、交接损失、人工介入、端到端时间和 Token 成本（可取得时），再决定是否扩大范围。验证包括失败路径、基线中途变化、共享逻辑冲突和合并后测试失败。

0.5.22 当前只有单入口、同一 Agent 的六阶段按需加载及已有事实记录。独立 Agent 调度、并发任务分派、工作区生命周期和共享记录写入协调均未实现；此方案不证明完整自主交付可用。执行顺序与启动条件由 ROADMAP.md 维护。

## A41 单入口路由专业能力，按证据分阶段隔离上下文（2026-09-23）

产品保留一个用户可见入口，内部采用小型路由器、Requirement、Scope、Build、Verify、Repair、Deliver 六类专业能力及共享事实与证据内核。拆分边界以独立产物、责任和状态转换为准，不按现有命令逐一拆分。路由器负责读取当前状态、选择阶段、验证结构化结果和推进状态，不重新吸收完整 PRD、代码与所有测试；专业能力通过输入摘要、事实、待决项、产物、证据及允许的下一步交接，聊天摘要不作为权威。

上下文治理分级实施。第一步缩小主 Skill，在同一 Agent 中按需加载专业说明；第二步用对比测量决定是否启用独立上下文，优先隔离 Verify 以降低实现者自证偏差；随后才评估 Requirement、Scope 与任务级 Build。拆成多个 Skill 只提供渐进加载，独立 Agent 才提供上下文隔离，但会增加重复阅读、交接损失、冲突、时延和 Token 成本。未经数据证明，不把每个命令变成一个 Agent，也不宣称多 Agent 自动消除幻觉。

产品所有者已在 2026-09-23 确认该方向并授权开始渐进开发。0.5.17 只实施第一层：一个可见入口、同一 Agent 内的阶段路由、按需规则加载和结构化交接约束；不创建六个用户命令，不启用多 Agent，也不新增第二套状态。后续是否隔离 Verify，需用相同真实或隔离案例比较遗漏、错误推断、人工介入、交接错误、误阻塞、时间和上下文成本后决定。

## A39 Gradle 依赖只能先成为候选（0.5.16）

Android 初次扫描可以从常见静态 Gradle `include`、`projectDir` 和 `project(...)` 依赖中提取模块与关系，减少人工抄录和全项目盲查。解析结果单独存为 `candidate_only`，保存文件哈希、行号证据和未理解表达式；它不直接修改人工审阅的 `modules/index.json`，也不能满足 scope、dossier 或开发门禁。

正式关系图用虚线展示这些候选，用实线保留人工声明依赖与已确认业务职责。动态 Gradle、convention plugin、运行时导航、反射与外部服务继续登记为边界。这样利用确定性线索缩小阅读范围，同时避免把构建语法匹配误写成业务归属或完整调用关系。

0.5.21 修复候选图的契约缺口：依赖目标即使不在静态 include 候选中，只要保留了对应来源缺口，也应以独立的待审节点与虚线边展示，不能因此拒绝整份候选；过期或损坏的记录仍拒绝。该节点不等于正式模块，不推断业务归属。

同版还给可识别的变体专属 `add` 依赖保留条件候选。正式 `depends_on` 只表示无条件关系；若唯一匹配的两个模块只有条件声明、没有同对普通静态声明，生成关系图和发布扫描基线时拒绝把它压平。该保护不推导各 flavor 的实际组合，也不覆盖所有动态 Gradle 语法。

## A38 业务能力与代码模块采用正交分类（0.5.15）

产品需求编号必须来自用户或产品系统，Skill 不根据标题或日期生成。工作流内部的需求、任务、决策和修复编号继续独立存在，避免把内部拆解 ID 冒充产品权威。

业务能力与代码模块不采用单一归属层级。一个能力可跨多个真实工程模块，每个模块登记 owner、host、provider、consumer 或 shared 角色、具体职责和依据；例如红包能力可以由 wallet 拥有规则，同时由 chat 承载展示。新工作流在 develop/check 前必须确认该范围，或用具体理由说明没有运行时模块。脚本验证结构、目录身份与档案新鲜度，不代替用户裁决产品归属。

项目关系图由已声明模块依赖和已确认 feature scope 生成 JSON 与 Mermaid 视图。路径匹配仅用于推荐候选；反射、动态导航、远程开关和未登记调用保持显式缺口。关系图用于定位和影响调查，不宣称是自动生成的完整调用图，也不要求每个业务能力创建新的构建模块。

## A37 扫描失效原因可见，HEAD 保护继续保留（0.5.14）

全局基线继续覆盖 Git HEAD，避免已提交但未登记的源码变化完全绕过提醒；同时 verify 分别报告 HEAD、构建清单、登记证据和工作树路径，让 Agent 根据实际差异选择模块复核或全量刷新。`.agent-workflow/**` 自身不使实现基线失效。工作树路径检测覆盖 staged、unstaged 和未跟踪的非忽略文件，但只提示路径，不判断语义影响，也不扫描被 Git 忽略的未知内容。

scan 发布时，若 Agent 已审阅变化且基线正文、清单和登记证据均未变化，只有指纹中的 HEAD 更新，则原地刷新指纹，不保存一份正文完全相同的备份。清单、登记证据、inventory 或人工说明发生变化时仍保存完整旧基线。该方案减少确定性冗余，没有宣称消除真实 Agent 阅读成本。

## A36 任务语义与进度分开复核（0.5.13）

任务标题、描述、范围、依赖、关联需求及未来新增的非进度字段共同构成任务语义摘要；状态、负责人、时间、实现版本、测试及验证证据只表示执行进度。前者变化使 task-review 过期，后者不触发 PRD 重读。这样可捕获“需求仍要求大写、任务却被改成小写”的漂移，同时避免每次完成任务或补测试记录都重新分析文档。

复核范围由变化任务及其新旧 requirement_ids 决定。Agent 必须对照对应需求、验收条件及相关来源/决策/修订/修复依据，并登记精确任务、需求和证据；脚本只验证变化集合、摘要和记录完整性，不能判断自然语言是否一致。新工作区默认采用，旧工作区在第一次语义任务修改前建立基线；旧复核进入防篡改历史。

## A35 回归同步与处置分权，失效证据留史（0.5.12）

历史候选同步只计算当前范围与候选，不代表用户授权 Agent 选择 `retest` 或 `not_applicable`。用户明确限制为只同步、列出、检查或停止时，新候选保持 pending；只有当前指令授权判断，或项目已有政策给出唯一结论时才写处置。该边界放在运行规范中，因为脚本无法可靠读取会话意图，仍需短 Agent 复检验证实际遵循。

候选内容改变或候选消失时，当前处置必须失效，但原结论不是无价值数据。schema v2 将旧候选快照、处置、结果及前后摘要移入幂等的只读 history。history 只支持审计和回看，不参与当前门禁；新的候选仍需重新判断与重测，避免通过保存历史而继承过期绿灯。

## A34 历史修复采用候选复核而非自动重开（0.5.11）

当前需求的模块标签、追溯代码路径和影响清单，与当前及其他需求中 `verified` FIX 的模块及代码路径做窄范围匹配。匹配项写入当前需求的 `regression-review.json`，Agent 必须逐项选择本次重测，或说明为什么与本次修改无关。check 阶段的重测结果绑定当前候选摘要、方法、证据和代码版本；候选、范围或历史 FIX 内容变化后必须重新复核。

历史 FIX 记录的是当时已经验证的事实，不能因为新需求修改相关代码就自动改回 investigating。候选匹配也不冒充完整调用图：模块或路径缺失可能漏项，共享模块可能产生宽泛候选，因此保留显式 `not_applicable` 处置。该设计在不新增用户命令的前提下把提醒接入 develop/fix/revise/check，同时避免任意提交导致所有历史修复重验。

## A33 归档预检生成待审报告而非自动结论（0.5.10）

真实归档发现 complete 需求可能没有 delivery-report，导致最后一步才被拒绝。`/dev archive` 因此先运行预检：汇集现有需求、任务、决策、追溯测试、修复和质量结果，并报告模块候选、代码路径根、impact 是否存在及 sources 的 Git 状态。已有非空报告绝不覆盖。

缺报告时生成带固定 review-required 标记的草稿。草稿只搬运已有字段，明确提醒无关 gate 不能充当行为证据，也不自动认定真机、版本或风险结论。Agent 审阅并移除标记前，正式归档必须拒绝。模块只给候选、不自动写标签；ignored/untracked sources 只报告、不暂存或上传。这样减少手工汇总，又保持验收权威由证据审阅决定。

## A32 质量证据忽略纯工作流记录提交（0.5.9）

质量报告继续保存检查时 Git HEAD、清单和登记证据。audit 遇到后来 HEAD 时比较两个提交的实际路径差异：若全部位于 `.agent-workflow/**`，保留质量结果；只要同一差异含业务代码、构建配置或仓库其他文件，仍判为过期。这样记录收口提交不会让自身证据失效，同时不把混合提交误认成纯文档变化。原测试提交身份保持不变。

进度、剩余问题和是否完成属于只读查询，只读取 status 与已有证据。除非用户明确要求重新验证，不因此运行 check、构建、validate 或 audit，避免统一入口把问答升级成耗时操作。

## A31 开发模式采用会话软状态（0.5.8）

无参数 `/dev` 激活当前会话、当前项目的开发模式；后续普通交付描述默认进入 next，裸命令词映射到已有精确流程。状态只存在于对话上下文，不新增共享指针、后台进程或项目配置，切换项目、新会话或明确退出后失效。这样减少重复前缀，同时避免跨需求和跨项目静默继承。

Claude Code 的 `/status` 为内置命令，不覆盖；功能状态使用普通文字 `status` 或 `/dev status`。跨会话强制常驻需要修改项目 CLAUDE.md 或 rules，当前便携 Skill 不自动注入，以免给每个业务仓库增加隐式全局行为。会话模式依赖模型保留上下文，因此必须作为便利入口而非确定性门禁；底层 ID 校验、恢复、证据和验收规则保持权威。

2026-10-10 补充：0.5.43 曾在每次回复的 ON 提示中重复显示选中需求；用户希望降低重复信息。0.5.45 只保留 ON/项目作为常驻提示，空 `/dev` 也不自动列出需求；现有 `status`/`list` 按需展示。选择只从展示层移除，不从会话路由或具体操作前的身份校验中移除；无新命令、状态文件或门禁。

## A30 统一入口只负责编排既有流程（0.5.7）

日常操作增加 `/dev next [自然语言描述]`。它先读取当前需求状态，根据描述进入已有的资料补充、澄清、修订、修复、开发或验收流程，并在执行前说明选择结果。它不创建第二套状态、记录或宽松门禁；最终产物继续写入原有 JSON 与 Markdown，原精确命令全部保留。

图片按用途判断：期望效果、替换素材和设计稿进入 figma 流程，异常现场截图进入 fix 流程。无描述时只执行唯一、已获授权且不涉及产品取舍的下一步；需求身份缺失或产品权威不明确时聚焦追问。新需求仍由 `prd --feature` 创建，归档需求必须先恢复，避免自动猜测造成串需求或静默改写。

## A29 新工作区默认采用局部影响约束（0.5.6）

CASE-02 表明，仅在 Agent 主动设置标记后才生效的门禁会被真实开发绕过。新建工作区因此登记 `workflow_version: 2` 并默认要求 impact checklist；项目已有模块目录时，还要求选择模块或给出明确不适用理由。旧工作区不批量改写，继续开发时再按现有规则采用。

API/Figma 等后补证据通过一个登记操作复制不可变文件并同步两个来源索引，减少手工双写漂移。登记不等于已阅读或已对齐；新来源仍必须有读取单元、映射和新复核。语义变化后重跑 develop 校验是 Agent 执行顺序，当前不宣称可以在 Skill 以外拦截任意代码写入。

## A28 归档与 Git 保存分离（0.5.5）

归档后报告共享记录是否未跟踪、未提交或被忽略，避免将本地生命周期标记误作版本保存。记录与代码在同一业务分支中审阅提交；推送是另一项授权动作。提示不阻断归档，因为归档修改本身需要后续提交；不自动暂存、切分支、修改忽略规则或联网核验。远端差异只依据本地 tracking refs，必须如实标注。

## A27 模块现状与需求历史分开（0.5.4）

用户确认采用全局概览、模块档案和需求历史三层结构。全局目录登记模块边界、公共技术和依赖；档案记录 Agent 审阅的当前代码与细节，按范围内容检测过期；需求归档保留原证据。局部核对覆盖登记的直接调用方和依赖，不只看一个文件夹。来源解释、图完整性和产品权威仍需核对，不自动合并历史 PRD。未替换全局质量快照，不以缩小阅读范围承诺无遗漏。历史交付与当前工作树归档门禁解耦仍是已知限制。

## A26 自动验证与人工验收分层（0.5.3）

从验收条件、影响行为和选定命令生成验证列表。业务条目默认人工，只有审阅实际断言后才映射自动检查；编译成功不能推导 UI 或产品验收成功。复用现有执行器，保留失败/退役条目和被测身份；影响清单复用同一结果，避免双份回填。旧需求按继续验收时采用；摘要保守覆盖整份列表，暂不实现精准依赖图、设备驱动或历史清理。结构完成不自动改变需求和修复的业务状态。

## A25 帮助优先于命令合并（0.5.2）

用户选择保留现有命令，增加分组总览和单命令帮助，先降低记忆和选择成本。help 在初始化、选择需求和运行工作流之前处理，只展示说明，不执行示例；无需项目目录。暂不增加模糊输入自动路由，避免改变已经验证的命令边界。

## A01 证据与工作规格分离

原始来源保留，JSON 工作规格可修订，Markdown 由 JSON 生成。这样保留原始意图和后补证据，避免以 Agent 推断覆盖事实。

## A02 核心与平台分离

PRD、需求状态、决策和追溯属于通用核心；平台命令/约定属于 profile。当前只有 Android 和 Generic；其他平台专属适配须真实项目验证后添加。

## A03 来源按适用性约束

不需要 API/Figma 的功能可以完整交付；需要但尚未提供时为 provisional。not_applicable 必须有理由。

## A04 仓库与运行名

仓库 featrace-dev（原 feature-delivery-skill）表示产品与维护范围；skills/dev 是可自包含分发的 Skill。核心和 profiles 都在里面，避免只安装 Skill 时丢失仓库外依赖。dev 为实际 Skill 名，从而在 Claude 提供 /dev，在 Codex 提供 $dev。

## A05 安装选择

用 Python 标准库复制到官方个人 Skill 目录。无全局 CLAUDE.md 注入，无符号链接依赖。安装标记包含内容哈希；仅更新未修改的自有安装，并保留备份。代价是 git pull 后还须执行一次 --update。

## A06 质量声明

脚本通过不等于功能正确。说明真实实现限制，优先补全契约校验；此前对“完整迁移/强门禁”的宽泛描述不作为事实延续。

## A07 PRD 表达先归一化，保留原始语义

不同 PRD 不要求产品统一写作模板。先建立读取单元、上下文与来源条目，再映射原子需求及条件/例外，回读原文复核。JSON 是工作规格，不取代原始来源；机器校验不能证明没有遗漏或误读。实现为 intake v1 与复核 digest，完整来源版本管理留待第二阶段。

## A08 扫描事实、规则与执行命令分开

模块事实以实际构建配置和源码交叉验证；规范保留适用范围与例外。coverage 只代表声明的审阅范围。候选命令可以带条件与模板，执行清单只能放本次已选择的具体参数数组。scan 校验配置，不自动执行项目构建。v2 指纹覆盖清单、根规则与登记证据，不是完整增量分析。

## A09 一份当前基线与有限备份

采用草稿复核后发布，避免分析过程中把正式基线更新一半。变化时保存完整旧版，默认 3 份未固定的托管快照；固定版本另保留。选择按内容而非按扫描次数创建备份，控制冗余并支持回退。只清理本机制拥有的扫描历史，其他业务和安装记录由各自生命周期管理。失败与恢复边界以扫描契约为准，不宣称全局原子性。

## A10 先真实验证，再扩展第二阶段

最初以实际新需求和多表达 PRD 验证作为进入第二阶段方案讨论的依据；该前置验证已完成，当前阶段口径见 A23。已确认问题继续按影响处理。PRD 权威修订及任务/代码影响追踪先保留为方向，不因扫描备份或 digest 已存在而认定已完成，也不未经当前任务授权提前实现。


## A11 Git 保存共享状态，本地保存运行状态

Skill 仓库与业务仓库使用不同提交边界。业务仓库共享经审阅的当前基线和开发记录，本机指纹、当次检查选择、原始运行报告及扫描恢复文件默认忽略，避免 HEAD 指纹提交循环和备份冗余。原始来源默认忽略，允许逐项授权共享；必要来源缺失会影响换机复核，不假定 Git 已携带全部证据。安装忽略规则不自动改变索引或上传内容，源码/规格中的敏感内容仍需审阅。


## A12 需求包允许不对称来源

文档和 HTML 交互稿都可单独构成 PRD，也可共同提供证据。每份资料登记为来源，要求阅读单元，已观察交互记录动作与前后状态。缺少另一种类型不是缺口；已提供但无法读取或依赖缺失才是缺口。内容矛盾保留待决，不设静默类型优先级。结构检查不证明动态页面已穷举或语义准确，真实样例验证仍是下一步。

## A13 效果偏差先登记，再决定是否改变需求

一个已交付功能的效果偏差记录在同一功能的 fixes.json，并由脚本生成 fixes.md。代码实现缺陷不改变 PRD；旧资料理解错误需重审原文；真正的产品变更或一手来源冲突需新证据与已确认决策。报告问题不会自动授予修改产品意图的权威。若用户已确认某行为而子任务漏写、代码也实现错误，一条修复记录可标记主因与附加成因，并保存任务描述改动前后；回归测试引用用于降低复发，记录本身不保证缺陷不会重现。未验证的问题影响功能级 check，但修复过程可继续；该记录不替代第二阶段的完整来源版本与自动代码影响分析。


## A14 局部需求默认保护未授权的旧行为（0.5.1 最小实现）

当 PRD 只要求局部修改时，以已确认行为和新需求确定边界。0.5.1 复用现有命令增加一份影响清单，区分改变、保留和未决行为；Agent 调查六类机制，脚本检查记录义务、Git 实际范围及回归结果摘要。现有代码不自动代表产品权威；未决选择仍走澄清。未采用的旧记录保持兼容，后续代码修改必须由 Agent 采用。共享摘要优先保证保守失效，不承诺精准依赖发现；不扫描理解全项目，不生成模块当前行为索引。真实效果与成本尚待案例验证。


## A15 先补证据关联与正常关闭，再扩展自动化（2026-09-17）

阶段审查表明，结构校验通过不代表测试覆盖本条修复，也不代表历史修复仍适用于当前代码。当前维护计划先补修复测试关联和非缺陷关闭，再结合真实需求试行旧修复回看、任务内容核对。历史验证事实与本次回归覆盖应分开；任务进度变化与任务内容变化应分开。具体字段、状态和自动失效机制尚待实现与验证，不能当作 0.4.5 已有能力。

## A16 真实反馈分层归档，历史结论不冒充当前验证（2026-09-18）

真实案例反馈区分维护者独立核实、执行方提供结果和待验证判断；复现证据脱敏后进入仓库，原业务资料留在项目所有者处。当前安装哈希只证明检查时点，不证明历史每次调用的加载版本。字段同步不能代替语义复核，历史测试通过不能代替当前改动的回归选择与执行。CASE-01 支持契约说明和验收同步补强；具体进度以路线图 GAP-07/08 为准。本次仅归档，不变更运行规则。


## A17 修复验证与非缺陷处置分开（0.4.6）

verified 保留修复验证含义；closed 表示有证据的非缺陷、确认撤回或重复处置，不虚构修复结果。重复项直接关联原报告且不豁免原问题，撤回使用已批准决策而不重复询问。回归测试默认关联受影响需求/任务；共享测试允许逐项解释覆盖，未知引用仍拒绝。结构校验不判断证据真伪，真实回归与手工验收仍需进行。


## A18 交付核对只读取已执行证据（0.4.7）

选定质量检查可注明实际覆盖的需求测试 ID，运行报告保存当次选择。只读 audit-delivery 比对报告结果、当前项目快照与已验证修复的测试 ID；没有被已通过检查覆盖的修复不能由旧报告背书。映射由 Agent 对照实际命令填写；工具不自动信任名称即覆盖。检查运行期间若这些已覆盖事实变化，会拒绝把运行结果算作当前版本通过。当前快照仅含清单、Git HEAD 与登记证据，未登记的未提交源码、任务含义、测试断言和人工报告仍须核对，不把校验结果当作 complete。


## A19 澄清与修复共享决策，确认不等于落实（0.4.8）

clarify 处理疑问、细节补充及变更分析，fix 处理观察到的偏差；两者共享 decisions.json 中的决策，不新建重复问题文件。新增 clarification 扩展字段，区分待决、确认和应用结果；旧决策保留兼容。来源已说明的解释无需反复批准，产品取舍依据真实确认；普通讨论的记录规则只在 Skill 已加载时适用，并尊重仅讨论要求。登记不授权修改代码，应用证据不证明最终业务验收；确定性校验与 Agent 的影响分析分开，不提前实现第二阶段。


## A20 待决内容可局部复核，不等于开发前完整复核（0.4.9）

PRD 读取时保留未决、不可读和补证据项。draft 模式可登记已实际复核的部分及剩余缺口；缺口未解决前仍不得进入完整开发/检查。即使 draft 条目后来补齐，也要重新完成整体验证，不能将局部复核误作最终确认。旧工作区完整 review 记录保持兼容。


## A21 当前需求属于会话与项目（0.4.10）

通过 list/use 减少重复输入 ID；选择仅保存在 Agent 会话上下文，不写仓库全局指针，避免多个会话互相改变默认目标。显式 ID 仅覆盖本次命令；成功新建 PRD 后选择，失败或已有 ID 不切换。只读 helper 校验目标，每次工作显示项目/ID/名称。上下文恢复不可靠时重新选择，不猜最近需求。底层工具仍传明确 ID，暂不实现主机会话持久化或 Git 分支联动。


## A22 归档与业务完成状态分离（0.4.11）

第一阶段采用原地元数据归档，目录和证据不搬移，避免破坏引用；默认列表只显示未归档记录。模块为可多选标签，查找不等于当前行为权威。归档需要完成记录、结构检查与实际验收依据，脚本不能证明证据真实；恢复保留旧状态/结论，后续修复沿用 provisional 规则。归档事件记录验收版本与报告哈希，不要求历史验收版本等于当前 HEAD。归档不替代备份清理，不压缩删除原证据；模块现状索引、规则替代和自动传播继续留在第二阶段。
