# Repository maintenance

Read PRODUCT.md, MAINTAINER.md and ROADMAP.md before modifying the Skill. PRODUCT.md owns the confirmed product mission, staged target, boundaries and success measures. Preserve the distinction between the current developer-assistance stage, the strategic north star and the final bounded-autonomy vision. Keep runtime resources self-contained under skills/dev. Use synthetic inputs in tests; never commit project .agent-workflow, transient .featrace data or personal configuration. Run python3 -m unittest discover -s tests -v after script changes. Update VERSION and CHANGELOG for releases. Do not claim planned capabilities are implemented.

Before a release, apply the version-selection policy in MAINTAINER.md: choose the changed number from the implemented capability and contract, document the rationale, and do not increment the last number merely because another commit or publication occurred. Keep historical numbers unchanged. Documentation-only maintenance does not create a new runtime release.

When changing runtime commands, states, source applicability, conflict handling, or quality gates, review and update the daily workflow diagram and notes in docs/usage.md in the same change. Keep its verification date current and distinguish implemented behavior from ROADMAP plans.

Before continuing development, inspect VERSION, git status and recent commits; distinguish source version, tested behavior, installed copy and remote release. Read docs/decisions/architecture.md for accepted decisions and docs/validation.md for evidence. Chat history and an installed skill are not the source of truth. If documentation conflicts with code, record the discrepancy; do not silently treat a planned capability as implemented.

MAINTAINER.md owns current handoff state and limitations; ROADMAP.md owns priority and start conditions; docs/decisions/architecture.md owns accepted rationale; docs/validation.md owns dated verification evidence; docs/usage.md owns the user workflow. Keep these aligned when behavior changes. Documentation-only corrections need not bump VERSION or rerun unchanged runtime tests; do check links, version references and consistency. Do not describe a past test run as newly executed.

The maintenance-document map and long-term goal live in MAINTAINER.md. ROADMAP.md also owns phase status and stable GAP issue IDs; dated docs/reviews reports preserve historical findings, not current issue status. Read the latest review before closing a tracked gap; record the implementation and verification evidence. Never mark an issue fixed merely because documentation was added. Repository maintenance docs are not installed runtime instructions.

Follow ROADMAP.md for maintenance priorities and current GAP status; do not duplicate a changing issue queue here. The user has authorized the whole A109 code-grounded current-task replacement, including retirement of incompatible legacy functionality/tests. New runtime does not maintain old .agent-workflow ledgers, acceptance schemas, carry/history replay, module dossiers or parallel worker contracts; do not recreate them from historical notes. Preserve current failure, source/permission, privacy, ownership and freshness protections in the replacement. Do not migrate/delete user business data or rewrite Git history. Source completion, formal release/install and real-project phase-two outcomes remain separate claims.

Before implementing a Skill feature, deficiency fix or workflow change, review the underlying protection goal, current invariant and causal evidence. Consider keeping, correcting, replacing or deleting the existing mechanism before adding a layer. Report unsupported architectural assumptions, systemic coupling and contradictions promptly; sunk implementation cost is not a reason to preserve a flawed design. Scale review to the change: a routine local fix does not require a full-repository architecture audit or a new approval form. Use existing maintenance notes for the chosen tradeoff, contrary evidence, unknowns, validation counterexamples and added maintenance cost. Replacements must identify obsolete writers/branches to retire, participating readers, history preservation, migration and safe rollback/refusal. Architectural or contract replacement is proposed for approval before implementation; do not silently broaden a local fix. Compare equal quality/coverage, preserve negative results, and do not promise absolute correctness or efficiency without evidence. See MAINTAINER.md for the current review protocol and ROADMAP.md for authorized work.
