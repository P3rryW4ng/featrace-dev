# Applicable project constraints

Before substantive operations in a project, inspect actual rule entrypoints/imports, scoped rules and relevant hooks. Do not recursively read every installed workflow, past feature, private configuration or nested worktree. Names first, details only when selected or governing the actual action. Read-only help/status does not prepare or modify a project.

Distinguish coding/product standards, workflow ownership, mandatory checks and execution permissions. Installed does not mean active. An explicit request to use FeatraceDev selects the intended workflow but does not cancel enforced hooks or higher-priority instructions. A collaborator's task is not permission to modify it.

Use existing authorization for the same action/scope/environment. Ordinary authorized test preparation and reversible test operations should proceed automatically. Ask only for a specific unresolved rule/authority choice, missing credential or genuine host limitation; explain its exact source. Do not infer that test means any account, payment, external message or production action is permitted. Conversely do not invent a host prohibition merely because a setting or test device is involved: inspect actual instructions and available tools. No repeated approval is needed solely because an internal stage changed.

Consolidate reviewed applicable decisions into `.featrace-policy.json` through the task kernel's policy command, not a second baseline/dossier/contract preparation. Show an actual conflict and how the chosen disposition changes testing/commits/ownership before requesting a focused decision. Preserve source/authority references and applicable scope. Source changes require reconsidering affected rules. No-conflict tasks need no workflow-choice questionnaire.

The policy supports scoped standing permissions; the user supplies their actual authority. It cannot override a live hook, CI or host permission. New scoped rules and newly relevant operations must still be inspected. Do not install universal test authorization into every user's project, edit CLAUDE/AGENTS/settings, disable hooks or take over another router's records. `.agent-workflow` records from old releases are not read or migrated by this package. Use a pinned old installation for explicitly requested old-record operations, or agree an honest new scoped task without erasing its unresolved facts.

Store task-local temporary work under the authorized ignored `.featrace/` area with exact task ownership. No implicit /tmp/home/install fallback. Read-only reviewers get exact permitted inputs/output paths; no arbitrary temporary writes. Host confinement remains necessary: these instructions are not a filesystem sandbox. Existing project policy can be shared after privacy review; local execution artifacts are not automatically shared.
