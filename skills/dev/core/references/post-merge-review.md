# Review a merge after a feature was completed

This is a read-only relevance review, not another feature completion, a current-build pass, or a replacement for CI. Use it only when the feature was already `complete` at a documented delivered revision and Git later advanced through a merge or other commit. A new product rule, changed accepted behavior, or observed defect goes through `revise`/`fix` and normal Verify instead. An explicit request to certify the merged revision also uses normal Verify/check; do not turn its failing current-evidence gate green by renaming a historical result.

1. Read the accepted delivery report and canonical status; identify the **full** delivered commit SHA and original test/device versions. Do not infer that SHA from the current HEAD, an arbitrary quality report, or a chat summary. If the accepted revision cannot be established, stop and report the missing binding.
2. Run `python3 core/scripts/post-merge-review.py <PROJECT> <ID> --base <FULL_DELIVERED_SHA>`. This read-only helper checks that the base is an ancestor, lists every committed changed path and every staged/unstaged/non-ignored untracked path, and separates workflow records from project files. `NO_PROJECT_CHANGE` means only this limited Git path inventory found no project change; it is not a new test result. `REVIEW_REQUIRED` means inspect the full diff. Ignored sources, external services, generated artifacts and runtime configuration remain outside this inventory; investigate them when applicable.
3. For **each** changed project path, inspect its actual diff and the feature's implementation, tests, callers, shared state, navigation/lifecycle and registered impact dependencies. Check whether the merge changes build configuration, test selectors, source semantics, feature flags, backend contracts or other conditions used by the prior evidence. A path outside the feature folder or module is only a candidate for exclusion, never proof of irrelevance. If a direct or transitive dependency was missing from the old record, the result is **unknown**, even when this particular edit looks harmless; update the dependency understanding and obtain a fresh observation before claiming preservation. Note the actual paths and reason in the user-facing review or the existing delivery report only when a durable team record is needed; do not create a second feature status.
4. If all changed inputs are demonstrably unrelated, leave the original `complete` status, tested revision and report intact. Say: “Original delivery remains complete at revision A; merge scope reviewed at B; no affected behavior found; no old test was rerun and the merged build is not newly certified.” Do not rerun the old manual matrix merely to silence a stale check. An old `audit-delivery`/`check` result for A may report stale at B; that is correct and is not itself a feature defect.
5. If some behavior is affected, rerun only its applicable checks and manual observations at B; if impact is unknown, investigate or test before asserting it is safe. For an explicit claim that B as a whole is deliverable, run the current selected automatic gates and normal feature check/audit with appropriately refreshed records. Existing narrow `verification.py retain` applies only to reviewed preserved-impact manual rows with full prior provenance; it does not retain an automatic gate or an ordinary requirement acceptance row. Never rewrite `tested_revision` to B without testing B. Record any new failure under `fix` rather than revising the old passed observation.

The helper lists changed paths, not dependency completeness or semantic impact. It writes nothing and cannot decide which checks are safe to skip. Keep the merge review and the original accepted delivery as separate claims.
