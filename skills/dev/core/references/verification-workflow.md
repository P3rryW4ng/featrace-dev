# Verification checklist (0.5.35)

Use within `/dev check`, and after authorized develop/fix implementation when preparing acceptance. No new user-facing command. The Agent selects applicable commands, then generates the checklist and executes the automated portion. Ask the user only for remaining observations or business judgments. Respect requests for analysis-only or no execution.

For an explicit independent review request (`check --independent`), use `independent-verify.md` instead of the mutation/execution steps below. That pilot reviews existing evidence only; it does not replace ordinary check or prove delivery. If the user separately requests test execution, complete the authorized normal checks before capturing reviewer inputs.

At the start of Verify, run the internal, read-only input inventory before relying on source or quality claims:

```text
python3 core/scripts/verify-inputs.py <PROJECT> <ID>
```

Inspect the actual readable source files and hashes, source-index disagreement, Git HEAD/worktree changes, and the quality report's recorded test time/revision. Files in the feature's `sources/` directory that are not in the source index are listed as supplementary evidence, not silently treated as approved requirements. A report from an older HEAD may still be current after workflow-only commits; use the existing audit to decide currency. Exit 0 means the inventory was produced, not that verification passed. Missing or uncertain inputs remain explicit; do not infer that an absent file was read or borrow an old quality result. This step writes no project records, builds nothing, and does not replace `validate-feature.py`, `verification.py` or `audit-delivery.py`.

Complete requires active requirements confirmed against evidence, all tasks done, no unresolved fixes or pending conflicts, required sources reconciled or justified as not applicable, traceability and actual test evidence, and applicable quality gates passed for the delivered revision. Run `validate-feature.py --stage check` and `audit-delivery.py`, then inspect task/decision meaning, code and test assertions, and the delivery report. Both commands must pass; `DELIVERY_EVIDENCE_CURRENT` alone does not clear unresolved historical retests. Structural validity and audit currency do not prove semantic or UI correctness. Controlled requirement baselines additionally need delivery registration under `revision-workflow.md`. If checks cannot run, report unavailable and provisional rather than success.

## Deliver: save and review before complete

When the user authorizes delivery/closure, save the reviewed report at `<PROJECT>/.agent-workflow/features/<ID>/delivery-report.md`. This is the existing feature-local delivery artifact, not another canonical requirements record. An external assessment, scratchpad file or chat response does not replace it. Archive's report-draft helper remains for archive; delivery does not require archive or a new command.

Before setting `feature.status` to `complete`, in this order:

1. Inspect current requirements/tasks, decisions/fixes, source reconciliation, traceability and applicable verification results. Run the existing `validate-feature.py <PROJECT> <ID> --stage check` and `audit-delivery.py <PROJECT> <ID>`; inspect coverage and evidence, not only their success messages. Failed, missing or stale applicable evidence blocks completion. Reuse an actually current run when warranted; report writing alone does not justify repeating builds or tests.
2. Write/update the local report from that evidence. Wait for the write operation to return successfully before reading it. Include feature ID; delivered HEAD and, for uncommitted code, worktree identity/diff or file hashes; requirement/task and decision/fix outcomes; actual check commands, test time/revision and coverage; manual/Agent/device evidence types, waivers, remaining limitations and the supported delivery conclusion. Write an evidence verdict for an explicit report-save checkpoint: what the tested revision and actual checks support, plus genuine unresolved product, code, test or acceptance items. Do not assert `complete` before the saved report has been fully read. The report precedes its own read and any controlled-baseline registration/status mutation, so do not put those routine closure actions into an unqualified "remaining work" or final-conclusion list that will become false after completion. If describing their state at write time, label it explicitly as historical (with a time/checkpoint) and point readers to `spec/requirements.json` `feature.status`, `feature.status_note` and `feature.baseline.deliveries` for current closure status. A valid compact conclusion is: "At this report checkpoint, current evidence supports delivery of revision X; formal completion is determined by the canonical status and delivery registration after this report is reviewed." Distinguish historical runs from current evidence and writing time from test time. Preserve earlier failures and accepted-build history when updating; do not invent observer confirmation or retimestamp old results.
3. In a separate read-only tool call, actually read the entire saved report and wait for that call to return successfully. Use the host full-file Read or a full-file read-only equivalent. If output is truncated, read the remaining portions until the entire saved text has been returned; a missing, failed or incomplete read blocks completion. Do not batch this read with the write or any completion/status mutation. The draft in memory, Write input, file existence, hashes, grep matches or a header preview do not count as reading the saved report.
4. After receiving the full read result, compare its actual text with current inputs and results once more. In particular, test the conclusion against the prospective `complete` state: any present-tense claim that report read, revision registration or status update remains unfinished would then be false. Correct such wording in the same report and perform a new separate full read before registration or status mutation. If implementation, sources or authoritative meaning changed during closure, stop and return to the affected stage; do not relabel an old pass. For controlled baselines, register the fully read report under the existing revision delivery rules before setting `complete`; registration binds its exact hash. Only when that registration and all completion conditions hold, use a subsequent separate operation to update the existing feature status and regenerate its views. Do not put the read and status mutation into one shell/tool operation or parallel batch: the Agent must receive and assess the read result first. A mismatch or failed current-input check must stop the mutation, not merely print a diagnostic and continue. After setting `complete`, rerun read-only `validate-feature.py --stage check`; for newly initialized workflow v4 features it also requires a nonempty local report and a current delivery audit. If that final check fails, return the feature to `provisional` and keep the failure visible. Do not edit the report after hash registration just to announce `complete`: current status belongs in the canonical record; any material report correction requires renewed review and registration rather than a silent hash mismatch. Report the local path and actual remaining limits to the user.

If the saved-report read is missing, denied, failed or remains incomplete, stop completion and keep `provisional`. If the report is still writable, use a separate permitted write/update to the same project-local `delivery-report.md` to record **blocked/provisional**, the actual read failure or missing portion, which earlier evidence remains valid or historical, and the legitimate next step needed to unblock review. Replace any unconditional completion conclusion; do not leave the blocker only in an external assessment or chat. Preserve earlier failures, test timestamps and accepted-build history. Saving this partial report does not count as reading it or authorize completion. Do not bypass a denied read by changing permissions or claim a successful review from the Write input. If the report update itself is unavailable, preserve the scene and explicitly state that the local blocker could not be saved; use an external summary only as a truthful fallback, never claim the local report was updated. A later authorized retry must fully read the then-current saved report and compare current inputs before completing.

For other blockers, retain a truthful partial report and `provisional` for the unfinished delivery; file existence alone is not acceptance. Status/help/questions remain read-only and do not create a report or change status without authorized closure. Legacy complete records are not bulk migrated by this rule. No commit, push, PR or archive is implied. These are Agent execution obligations using existing helpers; the structural validators do not prove the report's semantic truth or enforce this entire sequence.

## Generate and review

Prepare the impact checklist under impact-review.md. Read `project-baseline.md` for quality candidate/selection semantics, then select concrete quality-gates.json commands under existing project rules. Run:

```text
python3 core/scripts/verification.py sync <PROJECT> <ID>
```

This creates/updates feature-local verification.json and verification.md, marks feature.verification_required, and preserves earlier result attempts. Active requirement acceptance criteria and impact behaviors each become manual rows; each selected quality command becomes an automatic row. Missing gate selection generates an unresolved row rather than success. Changed/removed source rows are retained in retired with their evidence; new meaning gets a new ID. Sync is not acceptance and does not execute commands. Legacy untouched features need no migration; continuing current validation adopts this list. Archived features require restore for mutations.

Review whether criteria cover the real feature. A script cannot discover missing requirements or turn a vague criterion into meaningful steps. Before asking for manual results, the Agent supplies concise preconditions (account/flags/build), actions and expected outcome per remaining row. Test/UI automation is available only if the project actually has executable commands and required devices/credentials; this version does not install a device driver or UI framework.

## Map and execute

Canonical list fields: schema_version=1, feature_id, items, retired. Generated item fields id/source/expected are derived from inputs. Editable execution fields are mode (manual/automatic), gates (selected gate names), coverage (why the actual assertions cover the whole expected behavior). For a preserved impact behavior that may later avoid unrelated retests, also register `dependencies` (the complete project files whose changes require this behavior's retest, including imported/called files needed to load or execute it) and `scope_reason` (actual caller/state/navigation investigation). Do this before recording the original result; `sync` preserves these fields. Missing, ambiguous or unreviewed transitive dependencies mean no scoped retention. History is written by the helper. Do not manually manufacture results.

To automate a behavior row, inspect the assertions, set mode=automatic, gates=[names], and a nonempty coverage explanation. Every mapped gate must pass. Compile success must never stand in for visual, navigation or product acceptance. Leave partial coverage manual, or refine the source acceptance criteria into independently verifiable parts through existing rules. Do not add arbitrary commands to the list; it reuses the selected quality configuration. Keep generated gate rows automatic.

```text
python3 core/scripts/verification.py run <PROJECT> <ID>
```

This first checks develop eligibility, then calls the existing project check runner once and captures its fresh results. It never borrows an old quality report when no new report was generated. It records command output, result, timestamp, content digest and full Git revision. Before/after changes prevent a passing claim. Manual rows remain untouched; failures stay in history on rerun. No automatic marking of feature complete, fixes verified or decisions applied.

Then run existing `validate-feature.py --stage check` and `audit-delivery.py` as appropriate; record failures and gaps honestly. The checklist runner does not replace those overall delivery checks. Nonzero run/status code 2 means rows remain unfinished, not necessarily a build failure; code 1 reports invalid input/environment. Sync and successful manual recording return 0 without claiming completion.

## Manual results and remaining work

`verification.py status <PROJECT> <ID>` prints each row's effective state, current digest and revision. Present the user only outstanding manual actions, automatic failures/unavailable checks, relevant waivers, and any retained old observation with its original tested revision and new scope-review revision; no need to resend passing rows each time.

Before repeating a manual check after a small edit, compare the actual full diff with each row's reviewed dependency paths. Classify each row as **affected** (retest), **unaffected with evidence** (eligible for retained old observation), or **unknown** (retest or investigate). Trace imports, callers and state/navigation dependencies of the behavior through changed files, not just the symbol used by the current assertion. If this investigation reveals any direct or transitive file omitted from the row's dependencies, the row is **unknown and ineligible for `retain`**, even when the current edit is a harmless-looking string or a local probe still passes. Do not create an exception by asserting that this particular edit cannot affect the behavior: the earlier pass was recorded against an incomplete dependency contract. Correct the contract and obtain a fresh observation before a later unrelated edit can use scoped retention. A changed clickable label may affect the click target or link span even when only a string resource changed; include the callback/consumer in the investigation. Shared state, navigation and lifecycle edits require their related regression checks. Never decide irrelevance from filename or extension alone. Historical verified fixes use regression-review's explicit `not_applicable` or `retest` disposition; retention of an impact row does not auto-disposition a historical fix.

For a previously passed manual `impact:<ID>` row whose `kind=preserve`, when **all** changed registered paths are outside its **complete, investigated** dependencies and the requirement/decision/impact contract and gate configuration are unchanged, the Agent may record a scoped carry-forward after reviewing every changed path. Before calling the helper, explicitly answer: (1) does any changed file load, get loaded by, call, or get called by a registered dependency on the behavior path; (2) did this review discover an omitted dependency; (3) is any relationship still unknown? Any yes/unknown answer blocks `retain` until investigation or a fresh observation; a local behavior probe does not waive this prerequisite. The helper validates declared paths and recorded identities, **not dependency completeness**:

```text
python3 core/scripts/verification.py retain <PROJECT> <ID> --item <row-id> --digest <current-digest> --changed-path <exact-path> --reason "Why this edit cannot affect the preserved behavior" --evidence "Actual diff and caller/dependency review"
```

Repeat `--changed-path` for every path reported by the helper. It rejects a missing or extra path, changed dependency, changed contract, missing prior file provenance, failed/waived result, or automatic gate row. The resulting status is `retained`, **not a newly executed pass**: `tested_revision` remains the old test version and `reviewed_revision` records the current commit. If a new change occurs, the retention becomes stale again. The delivery report must distinguish old observation, current relevance review, and any check actually rerun. Do not use `retain` for a newly changed acceptance criterion or as a substitute for required visual/functional observation. Existing rows without earlier file provenance need a genuine fresh result before they can use this mechanism.

A default `manual` row means it is not fully mapped to an executable gate; it does not mean every technical check must be delegated to the user. Under existing verification authorization, an Agent may actually inspect the current implementation/call paths and observe local behavior to verify a technical constraint (for example, a pure local parser with no external reads/writes). Record a **pass** only when those observations and actual tests together support the **whole** expected behavior. Record an observed technical counterexample as **failed**, with the concrete input, actual versus expected result and current evidence. Within authorized verification-record maintenance, correct an unsupported automatic mapping to manual while retaining history, then obtain the current digest and record the actual outcome through the existing helper; rerun applicable checks after mapping changes. Reporting an observed failure or withdrawing unsupported coverage is not a product choice. Do not leave a known failure solely in an external summary or request product approval merely to record it. Genuine ambiguity about the expected behavior remains an explicit gap and follows clarify/revise; it does not erase an independent clear failure. Evidence must identify Agent technical inspection, exact files/paths, executed checks, current worktree identity and limits; never label it user confirmation or automatic-test coverage. The mere absence of an I/O call name, a partial mock test, a green build or an assertion of purity is insufficient. Unknown external callees/environments remain unresolved. Product decisions, subjective acceptance and unobserved device behavior still require the relevant real authority/observer; this rule supplies neither a waiver nor an automatic pass.

After obtaining actual observations for that tested build, record each applicable manual row (the following example is for user evidence; use the real method and references for Agent technical inspection):

```text
python3 core/scripts/verification.py record <PROJECT> <ID> --item <row-id> --status passed --digest <captured-digest> --tested-revision <full-commit> --actual "Observed outcome" --evidence "User confirmation; build/device or screenshot reference"
```

Statuses: passed/failed/unavailable/waived. Not-run needs no result; an unavailable environment is not a pass. Waivers need reason, risk, follow-up and actual acceptance authority in evidence, and must appear in the delivery report. Automatic gate rows cannot be manually passed or waived through record. A stale digest or wrong current commit rejects manual acceptance; preserve old-build observations in report history, never relabel them as a new build. Full commit alone cannot prove installation identity: Agent must confirm package/device context with the user, particularly with uncommitted code.

## Integration and limits

At check, missing adopted lists, missing/failed/unavailable/stale rows block completion. Passed, explicitly waived, or narrowly retained preserved-impact rows satisfy only this record obligation. Impact behavior validation reads corresponding current list evidence directly, so no duplicate acceptance entry is necessary in impact.json. Prior impact verification remains historical when the new checklist is adopted.

The digest covers requirement records, decisions, current impact snapshot, selected quality config and item execution mapping; it excludes result histories and task progress files. Changes initially stale the whole list. The scoped review above can retain a previous pass for a **preserved impact behavior** after explicit per-path investigation; it does not automatically infer semantic non-impact. Automatic gates, changed requirements, and undecided rows remain stale. Related file changes are detected within declared impact coverage; ignored/unregistered files and external environments are not exhaustive. Agent must reassess relevance before rerunning or explicitly documenting reuse; never replace old digests to hide a change. Semantic coverage and evidence truth remain human/Agent responsibilities.

One canonical list plus one generated view per feature; attempts and retired rows retain history without timestamped directory copies. No automatic cleanup of history yet. Share after sensitivity review: command output may contain private information. Helpers use atomic single-file replacement, not cross-file transactions or concurrent session isolation; serialize mutations for the same feature. No automatic push or installation.
