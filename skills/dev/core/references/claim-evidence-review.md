# Focused claim-to-evidence review (workflow v6)

For explicitly prepared schema6/7 acceptance v1 or schema8 storage (retaining profile6/7), use [acceptance-contract.md](acceptance-contract.md) instead of the legacy stamp/carry/final-review sequence below. Capture does not require already-supported acceptance; final delivery still requires complete coverage and existing guards. Do not migrate from an ordinary stale-status message.

At the Verify → Deliver boundary, after current check/audit pass and before `complete`, capture the current review input with `python3 core/scripts/claim_review.py capture <PROJECT> <ID>`. This is a focused review of active acceptance rows, not the optional full independent Verify investigation. Do not rerun unchanged tests just to produce this review.

Give the captured input and project path to a **fresh-context, read-only reviewer**. The implementer must not sign off on its own acceptance claims. If the host cannot provide a fresh reviewer or the reviewer cannot inspect required source/test/device evidence, leave the feature provisional and report the gap. For each row, the reviewer reads the requirement's **full statement and criterion**, its original source or approved decision, actual assertions or observation artifacts, and tested build identity. `passed`, a test ID, or report prose alone cannot prove full coverage. Expand to relevant code and callers when a shared path or interface is involved.

A shared change analysis and artifact may support several findings: read the actual shared material once and cite exact locators for each claim, then expand when its conditions or dependencies differ. There is no fixed reviewer count and no requirement to reread an unchanged full file per row. Every active claim still needs its own current source/evidence/counterexample judgment; do not blindly inherit an older supported verdict or reduce review to only the changed rows. A single reviewer or a bounded partition is chosen for actual coverage and cost, not a mandatory multi-Agent matrix.

Return one finding per active requirement or impact row in `claim-review.json`: `id`, `verdict` (`supported`, `partial`, `unknown`, or `approved_waiver` only for an already waived row), `source_basis`, `required_scope`, `observed_scope`, `evidence_ref`, and `counterexample_check`. `required_scope` names all targets, exact preconditions, actions and outcomes. `observed_scope` distinguishes execution from inference and names the tested build. `counterexample_check` states a concrete case still permitted by the evidence and whether it violates the claim. Partial or unknown blocks completion; an approved waiver cites its existing approval and residual risk. Cite actual file/artifact locations. For OGFR-7700, one interface cannot stand for three, and a nearby language combination cannot stand for the specified combination. Do not substitute keyword matching for this judgment.

The router reconciles each finding with the canonical verification rows. If unsupported, change only affected rows to unavailable or obtain missing evidence/authorized waiver; preserve history. Do not narrow confirmed criteria to make old tests pass. When all findings are supported or validly waived, save `<PROJECT>/.agent-workflow/features/<ID>/claim-review.json` with exact `feature_id`, `input_digest` from capture, `reviewer` identity and `findings`; run `claim_review.py check <PROJECT> <ID>`. A change to requirements, source bytes, registered impact scope or recorded acceptance evidence makes the review stale. A workflow-only commit or gate-selection prose edit alone does not. This is a bound assessment, not a replacement for requirements, tests, audit or report. The deterministic check verifies identity, coverage and verdict fields; it cannot prove the reviewer's reasoning. Record cost and any miss in the case log.

Only newly initialized workflow v6 features require this record for `complete`. Existing v5 and older deliveries are not migrated.

Before importing a new reviewer return/receipt that can repeat private provenance, follow [output-privacy.md](output-privacy.md). Check the selected new return without dumping it; resolve only the affected privacy candidates and then recheck normal freshness. Do not scan/rewrite old evidence or use no_matches as semantic approval.

For changed asynchronous absence/removal claims, inspect trigger and observer evidence, assertion order, object identity and observation window. Try whether “never arrived,” “removal disabled,” “wrong object” or skipped execution would still pass. Removal requires witnessed presence or an independently bound event trace; a never-appear claim requires a real trigger and active observer rather than forbidden prior presence. Missing premises are partial/unknown, not automatic approval. Follow technical-test.md for the bounded scope; do not reopen unrelated accepted behavior.
