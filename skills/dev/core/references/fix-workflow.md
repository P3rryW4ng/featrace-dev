# Fix workflow (0.4.6)

If the feature has `feature.baseline`, changes to requirement meaning must follow [revision-workflow.md](revision-workflow.md). Reuse this workflow’s decisions and fix evidence; code-only fixes do not revise requirements. Preserve original sources and prior delivery conclusions.

Use for observed behavior that may differ from a feature's intended behavior. Keep a fix inside the existing feature; do not initialize another feature solely for a defect. For work spanning multiple features, choose the owning feature and cross-reference others in evidence/notes. `fixes.json` is the editable record; `fixes.md` is generated by `render-workspace.py`. Existing workspaces without fixes.json are treated as empty until a fix is reported.

## Register first

`python3 core/scripts/record-fix.py <PROJECT> <FEATURE-ID> "problem description" [--expected "..."] [--actual "..."] [--reproduction "..."]`

The script creates `FIX-001` etc. in an existing feature, leaves missing facts empty, avoids duplicate active descriptions (a new report after verified/closed gets a new ID), and renders fixes.md. If the feature was marked complete, registration moves it to provisional and records the former status. It does not decide cause, edit the PRD, run tests, or approve a change. For Claude, `/dev fix FEAT-001 <problem description>` is the Agent entry; Codex uses `$dev fix ...`. Agent invokes the script and follows the investigation below.

## Investigate and route

Read the actual behavior, original PRD/HTML/API/design evidence, current requirement, task, code and tests. Fill expected/actual, reproduction or unreproducible reason, observed evidence, and related requirement/task IDs. Do not invent an expected value from the user's short report.

- `implementation_defect`: code differs from an already confirmed rule. Fix code and regression tests; leave PRD/spec meaning unchanged.
- `interpretation_gap`: earlier mapping missed or misread existing evidence. Correct intake, requirements, tasks and tests; reread original and renew semantic review.
- `requirement_change`: the intended behavior has changed. Preserve the new source/approval, record an approved decision, then revise requirements and affected tasks/code/tests. Never overwrite the original PRD.
- `source_conflict`: authoritative sources disagree. Record both source refs and keep blocked until a scoped decision is approved.
- `environment`: reproduction depends on build, data or runtime conditions; explain any absent requirement link. Do not relabel a real behavior mismatch as environment solely to clear a gate.

Start with `unclassified` while the cause is uncertain. A confirmed user answer, such as “Back returns to the previous page”, is expectation evidence; inspect whether it reached decisions.json, requirements/acceptance criteria, the task description, and code. If that answer is already available in the current session, record its exact scope and confirmation reference without asking again. If it is not accessible on another machine, do not invent its wording or authority. The observed A → B → Back → B loop alone does not establish whether the task text, code, or both are wrong.

Use one primary `kind` plus optional `contributing_kinds` when several layers contributed. `task_description_gap` means a generated task omitted or misstated confirmed behavior. Record the original and corrected wording in `task_changes` with its task ID; update tasks.json and acceptance criteria only if their actual meaning also needs correction. A task gap may coexist with `implementation_defect`. `interpretation_gap` concerns the mapping from original evidence to requirements, while `requirement_change` requires new product intent. Treat a prior user clarification as an existing decision if it can be cited; do not classify it as a new PRD change merely because code ignored it.

Classification is Agent judgment based on evidence, not a script inference. Fix records refer to `decisions.json`, `requirements.json`, `tasks.json` and `traceability.json`; update those canonical files where actually affected. Keep stable IDs. For requirement_change/source_conflict, verified resolution requires an approved decision with a chosen option and a concrete `approval_ref`. A short problem description is not approval to change product intent.

## Resolve and verify

Edit fixes.json as evidence accrues. `reported` → `investigating` / `blocked` → `resolved` → `verified` describes record progress. Resolved/verified requires expected, actual, root_cause, resolution, observation evidence, reproduction or unreproducible_reason, and a requirement link or scope_reason. Code/meaning/task changes require affected task IDs; task description gaps require before/after task_changes and a source or decision reference; interpretation/requirement/source changes require source_refs. Verified additionally requires verification entries, `tested_revision` (commit or uncommitted working-tree identifier), and `regression_test_ids` linked to declared requirement tests or an explicit `regression_waiver`. Record changed code paths and test IDs in the fix where relevant; a test name alone is not a passed result.

Run `validate-feature.py --stage develop` while repairing; unresolved fixes warn but do not block all work. Run applicable project checks separately. `--stage check` refuses any fix neither verified nor validly closed; complete remains a manual decision after checking feature status, decisions, tasks and current quality evidence. Re-run `render-workspace.py` after edits. For a navigation case, the regression check should assert A → B → Back → A and also ensure B is not reopened. Record the actual run result and tested revision; a test ID alone or an unrun test does not prevent recurrence. A waiver records remaining risk, not equivalent protection. A fix may be verified only after checking the actual outcome. This is a feature-wide check gate, not task-level eligibility.

## Regression scope

This section protects the fix being handled now. For later features that may touch an already verified repair, follow [historical-regression.md](historical-regression.md); do not edit the old fix to claim a new run.

For `verified`, `regression_test_ids` is a string array of tests declared in requirements.json. Each selected test must belong to a requirement in this fix's `requirement_ids`, or to a requirement linked from its affected `task_ids`. A shared/end-to-end test declared elsewhere is allowed with `regression_scope_notes`, an object mapping that selected test ID to a non-empty explanation of how it covers this fix. Unknown test IDs and notes for unselected tests are rejected; a waiver does not bypass invalid links. For example:

```json
{"regression_scope_notes": {"E2E-LOGIN": "The shared login flow exercises the affected return path before submitting."}}
```

This is an explicit coverage assertion, not proof of execution or semantic adequacy. Keep actual run results in `verification` (string array) and the tested code identifier in `tested_revision`. Existing in-scope verified fixes remain compatible; older unrelated references now require review and an appropriate link or explanation. Do not automatically add a reason solely to clear validation.

## Close a report without claiming a repair

Keep the original report and set `status: closed` with a `closure` object. A closed report is separate from a verified repair. All closures require `outcome`, a non-empty `reason`, and a non-empty string array `evidence` containing actual findings or references:

| outcome | Additional evidence required |
|---|---|
| not_a_defect | Non-empty `expected` and `actual` on the fix, plus `source_refs` or an approved decision in `decision_ids` supporting the expected behavior. Check that they agree; inability to reproduce alone is insufficient. |
| withdrawn | An approved decision with a chosen option linked in `decision_ids`, and `closure.confirmation_ref` to the scoped user withdrawal. Reuse an existing confirmation; do not ask again or invent it. Withdrawal does not change requirements or waive other defects. |
| duplicate | `closure.duplicate_of` names another existing fix in this feature. Point directly to the original, never self or another duplicate. The original is still checked; closing its duplicate cannot hide an open original. |

```json
{"closure": {
  "outcome": "duplicate",
  "reason": "Same reproduction and affected behavior as the original report.",
  "evidence": ["Compared the recorded steps and observation with FIX-001."],
  "duplicate_of": "FIX-001"
}}
```

Use investigating/blocked for insufficient evidence or inability to reproduce; those are not terminal outcomes. A closed report does not require invented root cause, repair or regression fields. Render after edits, run validation, and review remaining work; closing alone never restores feature complete. Summaries count recorded closed and verified separately and do not certify evidence. New evidence after closure may be registered as a new report referencing the previous one, preserving history. Historical records are editable JSON, not an enforced immutable event log.

The fix record is not an automatic PRD version manager or source-diff engine. The validator checks fields and links, not whether root cause, approval, code, or test outcomes are truthful. Keep raw PRD/API/HTML artifacts immutable and apply existing review freshness rules whenever requirement semantics change.
