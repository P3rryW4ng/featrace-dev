# Lightweight change or standalone defect entry (0.8.0)

Use when the requested work changes an existing function but does not continue a previously recorded feature, or when a newly reported defect has no owning feature record. This is a **creation route into the existing workflow**, not a second specification, status machine or exemption from review and verification. `change` is optional for the user: ordinary language and `fix <problem>` may reach this route when the problem is clearly outside the selected feature. A fix clearly inside an existing feature continues under `fix-workflow.md`.

## Resolve ownership before writing

Inspect the selected feature, relevant archived records, module map and code as needed to decide whether the work is actually a continuation, an observed regression of a recorded fix, or a distinct product work item. Do not infer ownership merely because a feature is selected, the code file overlaps or there is only one record. If evidence leaves two plausible owners, ask one focused question and preserve the observation without mutating either record. Archived feature mutation requires restore; an unrelated new work item does not reopen or rewrite the archive. Link relevant historical decisions/fixes in the new feature's evidence and impact investigation rather than copying their conclusions as new approval.

For a **distinct** work item, require the product/work-item ID supplied by the user and their nonempty change or problem description. Do not invent an ID. A formal PRD, internal module label and pre-classified root cause are not prerequisites. Show `轻量变更准备 · 编号：<ID/待提供> · 描述：<已收到/待提供> · 模块：待调查`. Ask only for missing ID/description. A missing product authority for the *expected new behavior* is a later semantic blocker, not a reason to demand a long PRD before recording the report. Explicitly distinguish a request to investigate from authorization to change product behavior.

Save the user's original description, with its attribution, unchanged to a regular UTF-8 `.md` or `.txt` file in an authorized ignored project-local attempt directory under `.agent-workflow/scratch/<ID>/` (see `write-scope.md`). Do not paraphrase the source or include Agent guesses in that file. If text came from an attachment, preserve that accessible source using the ordinary registration route; do not treat an unreadable link as evidence. Check scratch is ignored and writable. Then invoke:

```text
python3 core/scripts/init-change.py <PROJECT> <ID> --kind change|defect|unclear --request-file <PROJECT>/.agent-workflow/scratch/<ID>/<ATTEMPT>/request.md
```

The helper rejects existing IDs and empty/invalid sources. It uses the normal initializer, copies the report into the feature's immutable `sources/prd-original.*`, marks `feature.entry_kind`, and leaves requirements, tasks, decisions and review unapproved. The path name is inherited from the current PRD schema; for a defect it means *original report*, not an approved product specification. `--kind defect` additionally registers one `FIX-001` with `status=reported`, `kind=unclassified` and blank expected/root-cause fields. `--kind unclear` keeps the classification open without a fix record. A failed or interrupted creation must be inspected and resumed; never rerun initialization over an existing folder. After successful draft analysis and validation, select the new ID in this conversation under `feature-selection.md`; this helper never changes session selection.

Inventory and review the short source under `prd-analysis.md`. A change request's asserted new behavior may be confirmed only to the extent the user's wording/approval actually supports it; missing boundary rules stay pending. A defect report proves the observation, not the expected behavior: investigate existing contracts, code and history, then confirm the expectation from evidence or ask for a product decision. Do not manufacture a requirement or mark it confirmed merely to pass develop. Update only the existing canonical JSON and generated views; map affected module roles and callers, protect old behavior through impact/historical-fix review, then follow the ordinary gates and selected checks. `change` does not create code changes automatically, waive manual acceptance, or certify completion.
