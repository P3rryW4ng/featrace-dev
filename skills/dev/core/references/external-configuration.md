# Externally owned configuration tasks

Load only when Scope evidence suggests a task is fulfilled by configuration in another system (for example, a server-delivered navigation target), rather than by changing the current project's code. This is a task-level route inside an ordinary feature, not a new user command or a second feature status. A mixed feature may still contain normal Build tasks.

## Decide the owner before promising implementation

Inspect the relevant client entry point, parser, destination contract, current configuration source and requirement. Distinguish what is already implemented from what the requested behavior still needs. Record in the existing task/traceability/decision records: the owner and environment of the external change; exact configuration keys, values and parameter encoding; the recipient or handoff location; the expected behavior; the current client code revision; and any missing authority or unknown contract. Use a source reference or approved decision for a product-visible destination. If a client change is actually needed, route that slice through normal Scope → Build; do not call the whole feature configuration-only merely because one task is.

Tell the user at the first supported Scope conclusion, before long checks: **“This task changes no code in the current project; implementation owner: …; deliverable: configuration handoff and application evidence; remaining verification: ….”** For a mixed feature, name the code tasks separately. Never present a records-only commit as client implementation or count unchanged tests as new behavior coverage.

## Hand off, observe, close

Prepare a concise configuration handoff with environment, owner, exact values and encoding, source/decision basis, expected response, deployment status and a rollback/contact path when known. Keep secrets and captured tokens out of shared records. Creating the handoff is not proof that the external owner applied it. Until the configuration is observed in the intended environment, report `pending external application` and keep its acceptance unresolved; do not mark the task's requirement delivered on a proposed payload alone.

After application, inspect the actual returned configuration or equivalent authoritative external receipt and perform the smallest end-to-end observation that tests the changed behavior. Record who observed it, environment, time, relevant client/build identity, actual result and any remaining environment limits. A local static parser check can support compatibility but cannot prove an external deployment. If the agent cannot access the external system, give the user the exact observation needed and resume when it arrives. Do not silently equate test-environment acceptance with stage or production rollout.

## Select checks by actual delta

For this task, select external contract/configuration checks and the narrow runtime smoke that can detect a wrong target or parameter. Do not run a client build, unrelated model tests, translation checks or an entire earlier UI matrix solely because this task was added. A merge, client change, shared dependency change or explicit certification of a new client revision is a separate reason to choose applicable client checks; state that reason and the paths it covers. Within a mixed feature, reuse a still-current quality report for unchanged client code under the existing snapshot rules rather than rerunning it for record edits or external configuration alone. If a new requirement baseline makes that report stale under the existing validator, expose the remaining gate work and its reason; this reference does not authorize changing digests or claiming an old run current. Review historical fixes/impact rows only where the configuration can affect their behavior, with actual evidence.

Existing `check`/`audit` validators still require applicable selected quality evidence; this guidance does not make an empty gate list pass or grant an automatic exemption. A standalone configuration-only feature with no executable local gate may remain `provisional` under the current validator. Report that tool limitation explicitly rather than inventing a no-op test, waiving an unrun check or calling a handoff `complete`. This narrower route is first intended to remove wasted Build and repeat checks from mixed features while preserving truthful closure.
