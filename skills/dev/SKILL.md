Use the returned item IDs/states or documented plan operations to update actual starts, completions and blockers. A blocked or failed item is not completed; use supported host states and explain the blocker briefly when needed. When scope changes, reconcile the existing list instead of making a parallel one. After context loss, load the selected task status/details and live applicable rules, then query/reconcile the host list when supported; if it cannot be recovered, reconstruct only from verified current work and do not invent prior ticks.

Check each display-tool result. ## One current-task path

For authorized development, select the actual current-task route: continue the same unfinished task, use `correct` for an error in a retained completed judgment, or `begin` for a new request/later change to a previously valid outcome. Read the relevant status/request first; host progress, a merge helper or a compressed next-step summary does not replace this route. Do not create a task for activation, a read-only query or each message/subtask within existing work. Investigate real code/configuration/tests and product intent, choose checks from causal impact, implement, run only necessary missing/changed checks, assess their actual sufficiency, and close when eligible. A UI-only refinement does not require reaccepting the whole parent PRD. Shared rendering expands rendering callers; logic tests need a causal path. Unknown effects need investigation, not an automatic maximal suite. Keep unknowns local to affected claims/checks; unrelated branch changes are context, not an automatic task-wide reacceptance trigger.

After a successful task `close`, explicitly tell the user which requirement/task has concluded, the delivered scope, actual validation and material remaining limitations, plus the known commit/push/merge state when relevant. A receipt or completed progress item alone is not the user-facing conclusion. Do not call a subtask or bounded requirement the whole project; do not announce closure when close failed or was not run. If this closes only part of the broader authorized request, give a brief progress notice and continue independent remaining work without asking for “continue”; report overall completion only when that request's actual scope is done.

At task start, separate permission to edit, commit, build, test and operate devices under the applicable rules. Reuse an earlier approval only when its wording covers the current work and operation. Across tasks, check the original scope and limits. An instruction to fix a follow-up does not by itself extend an approval explicitly limited to the prior task.

Immediately before sending a question that suspends the session, identify the exact operation or decision it blocks. Recheck the current plan for authorized steps that can run independently, including implementation in other layers. A blocked check or a pending product decision in one area blocks only dependent work. Check for independent authorized work such as static review, documentation, read-only review dispatch where authorized, or preparation of a walkthrough script. Finish that work before sending the blocking question. If an answer is needed earlier and the host supports a nonblocking request, send it and continue the independent work. Obtain missing permission before performing the affected operation. Ask only for a concrete unresolved decision, required credential or actual host restriction. Selecting this Skill does not grant unrelated account, payment, production, publication or configuration permissions.

The old feature ledger, schema preparation, historical carry/replay, module dossiers and parallel-worker contracts are **retired from this package**. Do not call their old commands or migrate/rewrite/delete `.agent-workflow` data. An explicitly requested continuation of an old record needs its pinned old installation or an explicit new scoped task decision; a new ID cannot erase an unresolved failure. Report that boundary once, rather than silently switching routes.

Use actual source contents, connectors/exports when needed, and code references. A hash, URL, category or successful build does not establish business correctness. Preserve unrecoverable intent, important constraints and unresolved issues in tests, adjacent comments or the project's existing concise records; no permanent per-feature archive is required.

For authorized development, commit each completed coherent subtask locally after its necessary scoped checks and selected-output privacy review; do not wait for final feature acceptance or closure. Stage only that subtask’s changes, including its related tests, and report the commit ID. Reuse valid checks instead of rerunning them merely because HEAD changes. Apply actual user/project commit restrictions and resolve only a genuine outstanding conflict; reuse existing same-scope permission without asking at every subtask. A subtask commit is not a feature-complete claim and does not authorize push, history rewriting or inclusion of unrelated work. See the subtask commit guidance in `core/references/task-workflow.md`.

## Execution and delivery boundaries

Use the action sections in `core/references/task-workflow.md` for execution, facts, judgment and lifecycle details:

- Before rerunning a stale check, use “Diagnose before rerunning” to distinguish changed inputs, missing evidence and execution permission. Preserve real dependencies; broad compiler inputs do not imply broad business reacceptance.
- Preserve actual result artifacts before overwrite and bind them to their original producer/time. A successful command does not prove nested tests ran. Android-specific handling belongs to the profile.
- Use `check-adopt` for eligible historical checks and `adopt` for eligible observations only with intact originals and current causal analysis. Neither is a new execution, a device permission or a way to erase failure. Use owned walkthrough rounds to preserve findings before later runs.
- Register partial/unknown review findings before repair; later support requires explicit disposition. Actual runtime failures require targeted resolution. Approved whole-promise deferrals need surviving handoff and never count as supported.

Before sharing selected output or committing additions, read `core/references/output-privacy.md`; use exact files, not a whole-history scan. Temporary work belongs in the authorized task's ignored local area; read-only review permits no arbitrary writes. Do not print logs or secrets merely to inspect them. Worker/reviewer write scope is explicit and host-enforced, not inferred from installed specialists.

For cleanup, correction or stopping unfinished work, read “Query, correct and retain” or “Stop without delivery” in the workflow. Cleanup follows project policy and ownership/handoff protection; it does not delete business originals or rewrite Git history. `correct` preserves an erroneous retained judgment and reassesses only affected claims; `retire` is explicitly authorized non-delivery, not failure resolution or rollback. A later new requirement uses `begin`.

New tasks use contract10. Formats1–9 require pinned tools: contract9 uses 0.33.3, contract8 uses 0.32.0 and contract7 uses 0.31.0. Do not migrate old records or reconstruct expired originals. Commit, push, PR and installation follow actual user scope; distinguish source behavior, validation limits and release/install identity.
